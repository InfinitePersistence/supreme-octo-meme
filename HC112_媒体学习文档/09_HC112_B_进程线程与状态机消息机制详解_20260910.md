## 1. 先回答：到底有多少进程、多少线程？

当前能确定的是：

| 统计对象 | 本次核对结果 | 这个数字的含义 |
|---|---|---|
| 核心摄像机业务进程 | `main_app` 这一个主业务程序 | 状态机、UI 逻辑、设备检测、媒体服务等主要在其地址空间中运行 |
| AP 功能启动的另外两个服务 | `hostapd`、`udhcpd` | 是独立进程，不是 `main_app` 的两个线程 |
| 应用层直接创建线程的调用位置 | **33 处** | 范围为 `source/camera/component`（排除 depth_perception）和 `source/camera/demo/dronecam/modules`，不计已注释的创建语句 |
| 上述调用对应的线程入口函数 | **29 种** | 合并 ADAS、Hisnet、SpaceMonitor 的系统分支，以及信息 OSD 的重复创建入口 |
| 当前设备实际进程总数 | 尚未取得板端快照 | 还包括 init、登录 shell、内核任务、临时命令等，不能由代码给出固定总数 |
| 当前 `main_app` 实际线程总数 | 尚未取得板端快照 | 还要加库内部线程，扣除未开启的功能、结束的临时线程，并按通道实例计算 |

**33 处创建点不等于 33 个线程，29 种入口也不等于设备只有 29 个线程。**例如：

- LED 只有一处 `pthread_create()`，但 `InitLedmng()` 用不同灯号调用两次，所以会创建两条线程。
- 产测 UART 和声控 UART 有两处创建语句，却共享一个上下文，正常情况下二选一。
- VENC 的取流入口只有一套，但可以为多个 VENC 通道分别创建线程。
- AAC 播报发送线程在播放时创建，完成后回收；它不是从开机到关机始终存在。
- HFSM、EventHub、Timer、录像库的线程，不一定能在 `source` 层搜到 `pthread_create()`。
- `CONFIG_LVGL=y` 不代表本次开机必然创建 LVGL 线程：当前 UI 初始化中的显示入口调用被注释了。

第 13 节给出板端只读采集命令。取得 `/proc/<main_app PID>/task` 后，才能回答“这次开机当前准确有多少条线程”。SSH 的 `192.168.100.45` 是编译服务器，在那里执行 `ps` 得到的是服务器进程，不能拿来当作摄像机的统计结果。

## 2. 进程、线程、回调、定时任务的区别

| 名称 | 在 HC112_B 中的例子 | 是否独立进程 | 是否必然增加一条线程 |
|---|---|---|---|
| 可执行程序 | `/app/bin/main_app` | 是，执行时产生进程 | 至少有主线程 |
| 工作线程 | `KEYMNG_CheckThread` | 否，属于创建它的进程 | 成功调用 pthread_create 时是 |
| 回调函数 | `PDT_STATEMNG_EventProc` | 否 | 否，由调用方所在的线程执行 |
| 状态处理函数 | `PDT_STATEMNG_RecStatesMsgProc` | 否 | 否，由状态机调度执行 |
| 定时任务 | 停车时长、APP 心跳检测 | 否 | 否，不是每建一个 timer 就必然建一个线程 |
| 摄像头/编码通道 | cam0、cam1、VENC 0 | 否 | 通道可能带工作线程，但通道本身不是线程 |
| `.ko` 驱动 | VENC、WiFi、AHD 驱动 | 否，加载到内核 | 驱动可能创建内核任务，但 `.ko` 文件本身不是进程 |
| 编译生成的 `.a/.so` | `libhfsm`、`libss_mapi_venc` | 否 | 库函数内部可能创建线程 |

同一进程中的线程共享全局变量、堆和文件描述符，各自有执行位置、寄存器状态、线程栈和 TID。`pthread_t` 是 pthread 库的线程标识，不应直接当作 Linux 的数字 TID。

所以 `main_app` 中一个线程破坏内存，可能影响另一个线程；一个线程调用 `exit()`，可能结束整个进程。某个线程只是睡眠或等锁，则不等于整个进程都停止。

## 3. 从上电到 main_app：进程是怎么建立的？

### 3.1 启动脚本链路

依据：[已生成的 inittab][inittab]、[rcS][rcs]、[S10mpp][s10]、[bootapp][bootapp]。

```text
Linux 内核
  └─ init（PID 1）
      ├─ /etc/init.d/rcS（启动期间执行）
      │   └─ S10mpp
      │       ├─ mount /app
      │       ├─ load_module -a（加载内核模块）
      │       └─ /app/bootapp
      │           └─ /app/bin/main_app &
      └─ 串口登录 shell（由 inittab 管理）

main_app 开启 AP
  ├─ 启动 hostapd
  └─ 启动 udhcpd
```

这个图表达“启动关系”。`hostapd -B` 等后台化后，最终 PPID 可能发生变化；不能保证运行时 `ps` 的父子树完全与启动调用关系一致。

```sh
# build/fs/rootfs/etc/inittab 节选
::sysinit:/etc/init.d/rcS
# init 启动时执行 rcS。

ttyAMA0::respawn:/bin/sh -c "login -f root"
# 串口登录进程退出后，init 按 respawn 规则重新拉起。
```

```sh
# source/camera/demo/dronecam/rootfs/rootfs_priv/etc/init.d/rcS 节选
/bin/mount -a
for initscript in /etc/init.d/S[0-9][0-9]*
do
    if [ -x $initscript ]; then
        $initscript                 # 顺序执行可执行的启动脚本
    fi
done
```

```sh
# S10mpp 节选
mount -t jffs2 /dev/mtdblock7 /app   # 挂载应用分区
cd /komod
./load_module -a                   # 加载驱动，不是创建“录像应用进程”
cd /app
./bootapp

# bootapp 节选
cd /app/bin
./main_app &                       # 后台启动主业务进程
```

`bootapp` 中的 `&` 只表示 shell 后台运行程序。它不表示“在 shell 进程里增加一个 pthread”。当前脚本也没有给 `main_app` 配置与串口 shell 相同的 `respawn`；主进程退出后的恢复不能简单解释为“init 自动重启 main_app”。

### 3.2 WiFi 为什么另有两个进程？

依据：[hal_wifi_ap.c][wifiap] 的 `HAL_WIFI_AP_HostapdStart()`、`HAL_WIFI_AP_DhcpdStart()`。

```c
/* 原代码节选：POSIX_SPAWN_FUNC 分支 */
td_char *szArgs[] = {
    HAL_WIFI_HOSTAPD_EXECUTE_FILE,  /* /usr/sbin/hostapd */
    "-B",                         /* 后台运行 */
    HAL_WIFI_HOSTAPD_CONFIG_FILE,
    NULL
};

s32Ret = posix_spawn(&pid, szArgs[0], NULL, NULL, szArgs, szEnv);
/* 创建外部程序的进程，不是 pthread_create。 */

s32Ret = waitpid(pid, &s32Status, 0);
/* 等待启动子进程状态；不表示等待后台 AP 服务整个生命周期。 */
```

另一编译分支通过 `SS_System(cmd)` 执行命令，结果仍是启动外部服务。

| 进程 | 工作 | 线程如何管理 |
|---|---|---|
| `main_app` | 摄像机产品逻辑、媒体、录像、APP 接口 | 由各模块保存 pthread_t、运行标志和锁；还有库内部工作线程 |
| `hostapd` | AP 认证、关联与无线接入控制 | 由 hostapd 自己管理；不能用摄像机应用的线程表推断其线程数 |
| `udhcpd` | 向连接 AP 的设备提供 IP 租约 | 由 DHCP 服务自身管理；实际数量读其 `/proc/PID/task` |
| `init` | 启动脚本、回收孤儿子进程、管理 respawn 项 | 系统初始化程序自己的执行上下文 |
| 登录 shell/命令 | 串口命令、脚本及临时维护操作 | 每个外部命令可能短暂增加进程 |
| 内核任务 | MMC、JFFS2、工作队列、驱动处理等 | Linux 内核管理，不属于 main_app 的 pthread |

`mediaserver` 出现在 NDK 目录名里，不代表此固件必然另起一个叫 mediaserver 的进程。[主程序 Makefile][mainmake] 将 MAPI、HFSM、EventHub、param2flash 等库链接到 `main_app`；这些函数在这里属于主进程调用链。

```make
# 主程序 Makefile 节选：这些是链接库，不是一串要启动的进程名。
VSS_LIB += -lss_mapi_sys -lss_mapi_vcap -lss_mapi_venc
VSS_LIB += -lhfsm -lfsm -leventhub -lmessagehandler
# 另有：-lparam_host -lparam2flash_host -lmedia -lstatemng 等。
```

## 4. main 主线程的工作，以及初始化的先后顺序

依据：[ss_product_main.c][main] 的 `main()`、`PDT_INIT_PreInit()`、`PDT_INIT_Init()`、`PDT_Init()`。

```c
/* 原代码关键调用节选；省略错误处理、条件编译和无关初始化。 */
td_s32 main(td_void)
{
    PDT_INIT_PreInit();             // 芯片/外设预初始化，加载参数
    SS_WATCHDOGMNG_Init(&watchdogMngCfg); // 启动喂狗管理线程
    PDT_INIT_Init();                // 事件中心、媒体、UI、设备管理等

    while (1) {
        sleep(1);                  // 主线程保持存活，让其他工作线程运行
    }
    return 0;
}
```

上面的函数为了教学省略了局部变量声明；真实代码见链接。主线程最后睡眠不意味着系统空闲，因为摄像机的日常业务已经交给其他线程和回调。

```text
PDT_INIT_PreInit
  ├─ CHIP_PreInit
  ├─ PERIPHERAL_Init
  └─ SERVICE_PreInit → SS_PDT_PARAM_Init → 参数保存线程

WATCHDOGMNG_Init → 喂狗线程

PDT_INIT_Init
  ├─ OS_Init
  ├─ InitEvent → SS_EVTHUB_Init + 注册各模块事件
  ├─ GSENSORMNG_Init → 碰撞检测线程
  ├─ SERVICE_Init → MAPI、媒体输入、OSD、音频、开机音等
  ├─ CHIP_PostInit
  └─ PDT_Init
      ├─ InitLedmng → 两条 LED 线程
      ├─ AHDMNG_Init、ACCMNG_Init
      ├─ TIMEDTASK_Init
      ├─ UI_Init → 事件订阅、AO 检查、提示音管理
      ├─ GPSMNG_Init/Start
      ├─ STATEMNG_Init → 建立并启动 HFSM
      ├─ InitStorage
      └─ PDT_ServiceDelayedStartThread
          ├─ InitKeymng
          ├─ NETCTRL_Init → HTTP、GPS 上报、网络订阅
          ├─ WiFi AP 启动
          └─ 后续温度等周期处理循环
```

当前 `PDT_ServiceDelayedStart()` 会 `pthread_detach(pthread_self())`，且末尾存在周期循环，所以它虽然叫“延迟启动”，完成前半段初始化后也不一定退出。

## 6. 平台层还会增加什么线程？

### 6.1 可直接看到源码的 NDK / middleware 线程

| 层级 | 入口 / 线程名 | 数量规则与职责 |
|---|---|---|
| VCAP/ISP | ISP 运行入口 / `pTIspRun%u` | 每个需要 ISP 的 pipe 按需创建；GC4653 RAW 前摄需要 ISP，不能把 AHD 后摄也无条件算成第二个 RAW ISP |
| VENC | `ProcVDataThread` / `pTVData_Chn%u` | 按初始化的 VENC 通道创建，等待编码数据、获取码流、交给后续消费链路 |
| AENC | `ProcAStreamThread` | 按音频编码通道；两路录像可共享 AENC，不能固定算两条 |
| OSD 内容 | `MAPI_OSD_UpdateContentThread` | OSD 初始化创建 1 条 |
| OSD 时间 | `MAPI_OSD_TimeUpdateThread` | 字体模块已初始化时创建 1 条 |
| OSD GPS | `MAPI_OSD_GPSUpdateThread` | 同上；读取已得到的 GPS 数据更新 OSD，并非 GPS UART 采集线程 |
| Storage | `STG_DEVMONITOR_Routine` / `mw_devmonitor` | 存储设备监控上下文创建时启动，感知设备事件 |
| Storage 状态循环 | `MessageLooper::Looper` | 每个相应 looper 启动一条，按队列处理存储状态消息 |
| 网络监听 | `NETWORK_LISTENER_Process` / `NetlistenProc` | live/RTSP 服务使用的监听线程，按监听上下文创建 |
| RTSP 会话 | `RTSPSVR_StreamSessionProcess` / `RtspSessProc` | 按 RTSP 会话创建；APP 预览连接/断开可能改变数量 |
| 调试/选配 | YUV Dump、RAW Dump、IVE、UVC 等 | 只有开启对应功能才计算；不能把全部候选线程加入日常录像数量 |

依据：[mapi_vcap.c][vcap]、[mapi_venc.c][venc]、[mapi_aenc.c][aenc]、[mapi_osd.c][mapiosd]、[Storage MessageLooper][looper]、[stg_devmonitor.c][devmonitor]、[网络监听][listener]、[RTSP 会话][rtsp]。

```c
/* mapi_venc.c：每个 vencHdl 都有自己的上下文和线程句柄。 */
ret = pthread_create(
    &g_vencContext.procVDataThread[vencHdl].procVDataThreadId,
    TD_NULL,
    ProcVDataThread,
    &g_vencContext.vencChnCfg[vencHdl].vencHandle
);
// 同一行被不同 vencHdl 调用，得到多条线程。
// 所以“一处 pthread_create”不等于“设备只有一条 VENC 线程”。
```

```c
/* ProcVDataThread 的主要判断，原代码节选。 */
if (isVencChnStart == TD_TRUE) {
    MAPI_VENC_ProcVideoStream(vencHdl, &timeoutVal);
    // 该函数中 select 等待编码通道 fd，然后读取码流。
} else {
    MAPI_COMM_CondTimeWait(&gobalPrcThd->procVDataThdCond,
                         &gobalPrcThd->procVDataThdLock,
```

**暂时停止录像未必立即减少线程数**：通道线程可能仍保留，只是处于等待状态；完整 Deinit/媒体重建才可能 join 并重新创建。所以切换前后 TID 变化也可能是正常现象。

### 6.2 当前主要以库形式提供、不能从 source 搜索穷尽的部分

HFSM、EventHub、MessageHandler、Timer 相关目录能看到头文件和 `.a/.so`，没有完整的对应实现源码。本次还在服务器只读检查了符号：

```text
libmessagehandler.a：引用 pthread_create
libeventhub.a：引用 SS_MSGHDL_Create / Start / SendAsyncMessage / Stop / Destroy
libeventhub.a：存在 EventHubSubscriber::HandleMessage / Init / Notify 等符号
```

这些证据说明事件/消息分发内部有线程机制。**仅凭符号不能推导“一定每个订阅者一条线程、总共固定几条”**，也不能编造 HFSM 私有实现的循环源代码。

录像在应用层调用 `SS_REC_Create()`、`SS_REC_Start()`，封装、ring buffer 消费、文件写入等内部工作需要结合录像库及运行时线程名继续定位。场景调优和语音算法库也可能建立自己的内部线程。

因此工程运行线程数应按以下口径理解：

```text
main_app 实际线程数
 = 主线程 1
 + 当前已经创建且尚未退出的应用层线程实例
 + 当前初始化通道对应的 NDK 线程
 + 事件、HFSM、Timer、Storage、REC、Scene、网络及算法库内部线程
 + 此刻存在的短生命周期线程
```

## 7. pthread_create 到底做了什么？

### 7.1 用按键线程看四个参数

依据：[ss_keymng.c][key] 的 `SS_KEYMNG_Init()`。

```c
g_keymngCtx.checkTskRun = TD_TRUE;  // 先准备运行条件

ret = pthread_create(
    &g_keymngCtx.checkTskId,         // 输出：保存线程句柄
    TD_NULL,                       // 属性为空：使用 pthread 默认属性
    KEYMNG_CheckThread,             // 新线程开始执行的入口函数
    TD_NULL                        // 传给入口函数的参数，这里不用
);

if (ret != TD_SUCCESS) {
    // 创建失败要处理；不能假定线程已经存在。
    // pthread_create 返回的是错误号，分析时要看 ret。
}
```

`pthread_create()` 成功后，调用者继续向下执行，新线程也可以立即获得调度。不能假定“一定等 Init 函数 return 后，新线程才开始跑”。这就是共享上下文通常要先初始化、再创建线程的原因。

### 7.2 线程主体：循环、睡眠和事件

```c
/* KEYMNG_CheckThread 节选。 */
prctl(PR_SET_NAME, "KEY_CHECK", 0, 0, 0); // 给当前线程命名，便于 /proc 对照

while (g_keymngCtx.checkTskRun) {
    KEYMNG_KeyCheck(&g_keymngInfoSet);   // 检查按键状态和按下持续时间
    SS_Usleep(KEYMNG_CHECK_INTERVAL * 1000);
    // KEYMNG_CHECK_INTERVAL=50，基础等待 50ms。
}
return TD_NULL;                         // 入口函数返回，线程结束
```

线程名称在 Linux `comm` 中通常只保留前 15 个可见字符，`GSENSOR_LEVEL_CHECK` 等长名字可能被截断。不要因此误判为另一个函数。

### 7.3 停止和回收

```c
/* SS_KEYMNG_Deinit 节选。 */
g_keymngCtx.checkTskRun = TD_FALSE;      // 通知循环退出
ret = pthread_join(g_keymngCtx.checkTskId, TD_NULL);
// 等待线程真正退出，并回收 joinable 线程资源。

ret = SS_HAL_KEY_Deinit();              // 线程不再读按键后，才释放对应 HAL
g_keymngCtx.isInitialized = TD_FALSE;
```

`join` 不会自动替你设置退出条件。如果线程一直卡在无法返回的 I/O 中，或者持有互相等待的锁，join 的调用者也会一直等。

另一个模式是 `pthread_detach(pthread_self())`，当前延迟启动线程和异步 sync 线程都用了它：线程结束后自动回收，不再由其他线程 join。**detach 不会杀线程，也不会把它变成独立进程。**这些 pthread 基础语义可对照 [Linux pthread_create 手册](https://man7.org/linux/man-pages/man3/pthread_create.3.html)。

## 8. 各线程怎样协作？看五个真实例子

### 8.1 LED：共享结构 + 一灯一线程

```c
/* InitLedmng() 中分别初始化两个 LED。 */
ret = SS_LEDMNG_Init(OT_LEDMNG_LED_IDX_0, &Ledcfg);
ret = SS_LEDMNG_Init(OT_LEDMNG_LED_IDX_1, &GPSLedcfg);

/* SS_LEDMNG_Init() 内部：idx 不同，传入的上下文不同。 */
ret = pthread_create(&g_ledmngCtx[idx].checkTskId, TD_NULL,
                     LEDMNG_CheckThread, &g_ledmngCtx[idx]);
```

UI 改变 LED 状态配置，LED 线程按配置输出亮灭。UI 不需要为了闪 10 次就同步睡眠 10 个周期。注意局部变量名 `GPSLedcfg` 不能直接当作硬件灯身份；要看调用的 LED 索引和 HAL GPIO 映射。

### 8.2 参数保存：设置标志和实际写 Flash 是两个时间点

依据：[ss_param2flash.c][paramsave]。

```c
/* PARAM2FLASH_SaveTsk 原代码节选。 */
while (tskCtx->run) {
    SS_Usleep(1 * 1000 * 1000);   // 每秒检查一次
    if (tskCtx->saveFlg == TD_TRUE) {
        tskCtx->saveFlg = TD_FALSE;
        OT_MUTEX_LOCK(tskCtx->mutexLock);
        td_s32 ret = PARAM2FLASH_SaveParam(); // 此处才实际保存
        OT_APPCOMM_LOG_IF_EXPR_FALSE(ret == TD_SUCCESS, "save param failed");
        OT_MUTEX_UNLOCK(tskCtx->mutexLock);
    }
}
```

`SS_PARAM2FLASH_SetSaveFlg()` 表示“需要保存”；`SS_PARAM2FLASH_SyncSaveParam()` 则持同一个保存锁直接保存。这里讲的是产品参数机制，**不能据此推断所有 TESTBIT 保存也自动使用这个线程和这把锁**，产测有自己的调用链。

### 8.3 提示音：生产者、队列、消费者

依据：[ss_product_ui.c][ui] 的 `PDT_UI_AudioPlayManager_AddRequest()`、`AudioPlayThread()`。

```c
/* AddRequest 节选：把播报请求放到环形队列。 */
pthread_mutex_lock(&g_audioManager.queueMutex);

g_audioManager.playQueue[g_audioManager.queueTail].audioType = audioType;
g_audioManager.queueTail =
    (g_audioManager.queueTail + 1) % g_audioManager.maxQueueSize;
g_audioManager.queueSize++;

/* 省略：原函数的队列满检查、去重，以及首次请求时创建 AudioPlayThread 的分支。 */
pthread_cond_signal(&g_audioManager.queueCond); // 唤醒等待请求的消费者
pthread_mutex_unlock(&g_audioManager.queueMutex); // 释放队列锁
```

```c
/* AudioPlayThread 节选：等待请求，不持续消耗 CPU。 */
pthread_mutex_lock(&g_audioManager.queueMutex);
while (g_audioManager.queueSize == 0 && g_audioManager.isThreadRunning) {
    pthread_cond_wait(&g_audioManager.queueCond, &g_audioManager.queueMutex);
    // 等待期间释放 queueMutex；被唤醒后重新持有它，再检查条件。
}

if (g_audioManager.queueSize > 0) {
    request = g_audioManager.playQueue[g_audioManager.queueHead];
    g_audioManager.queueHead =
        (g_audioManager.queueHead + 1) % g_audioManager.maxQueueSize;
    g_audioManager.queueSize--;
    hasRequest = TD_TRUE;
}
pthread_mutex_unlock(&g_audioManager.queueMutex);

/* 取出请求后，在队列锁外执行耗时播放。 */
if (hasRequest) {
    ret = PDT_UI_PlayAacInternal(request.audioType);
}
```

这里的 `maxQueueSize=10` 是最多排队 10 个请求，不是开 10 条播报线程。

底层播放又创建临时发送线程，所以“一个播报消费者 + 播放期间一个发送线程”并不矛盾：

```c
/* SS_SYSTEM_PlayAAC 节选。 */
struct ThreadArgs localArgs;
localArgs.aacHdl = aacHandle;

ret = pthread_create(&sendThread, NULL,
                     SendFrameToADecThread_Single, &localArgs);
// 传的是当前函数栈上 localArgs 的地址。

clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_sec += 30;
ret = pthread_timedjoin_np(sendThread, NULL, &ts);
if (ret != 0) {
    pthread_cancel(sendThread);
    pthread_join(sendThread, NULL);
}
// 调用者等待发送线程结束，才允许 localArgs 的作用域结束。
```

当前代码有播放锁、队列锁等不同锁。锁保护的是各自覆盖的数据/调用区间，不能笼统说“有一把音频锁，所有音频和媒体重建就完全串行了”。

### 8.4 喂狗：为什么一个线程卡住不一定马上重启？

```c
/* WATCHDOGMNG_CheckTsk 原代码节选。 */
while (g_watchdogMngCtx.tskRunning) {
    sysStatus = WATCHDOGMNG_CheckStatus();
    if (sysStatus == TD_TRUE) {
        SS_HAL_WATCHDOG_Feed();
    }
    SS_Usleep(1 * 1000 * 1000);  // 实际每秒检查/喂一次
}
```

`main()` 将 `watchdogMngCfg.intervalTime` 设为 10，初始化中传给 HAL；不能据旁边“10s feed dog”注释，就断言实际喂狗线程每 10 秒醒一次，循环明明是 1 秒。

当前初始化的 `checkStatus` 回调为空，而这一 SMP 分支默认状态检查返回真。因此状态机或 APP 请求线程卡住时，喂狗线程可能仍正常运行，设备会“业务无响应但不重启”。反过来，main_app 整体退出会连同喂狗线程一起消失。这是分析重启/卡住时需要分清的两种情况，不是对某份历史日志的直接定因。

### 8.5 定时任务：16 个槽位，不是 16 条固定线程

依据：[ss_timedtask.c][timer]。

```c
#define TIMEDTASK_MAX_NUM 16
#define TASK_CHECK_INTERVAL 300000

g_timerGroup = SS_Timer_Init(TD_FALSE);       // 创建/初始化定时器组
SS_Timer_SetTickValue(g_timerGroup, TASK_CHECK_INTERVAL);

/* SS_TIMEDTASK_Create() 节选。 */
for (td_u32 i = 0; i < TIMEDTASK_MAX_NUM; ++i) {
    if (g_timedTaskCtx[i].used == TD_TRUE) {
        continue;
    }
    /* 填入 timer_proc、interval_ms、periodic、clientData 等。 */
    g_timedTaskCtx[i].timerHdl = SS_Timer_Create(g_timerGroup, &timerConf);
    g_timedTaskCtx[i].used = TD_TRUE;
    *handle = i;
    return TD_SUCCESS;
}
return OT_ENORES;                           // 没有空闲任务槽
```

这里可明确得出的限制是该包装模块最多占用 16 个任务槽位。Timer 库内部有自己的调度实现；`SS_TIMEDTASK_Create()` 本身没有逐任务 pthread_create。APP 心跳、停车超时、屏幕超时各占任务资源，但不是每项必占一个 Linux 线程。

## 9. 怎么给状态机发消息？

### 9.1 消息结构：先分清字段意义

依据：[ot_message.h][message]。

```c
#define MESSAGE_PAYLOAD_LEN 512

typedef struct ot_MESSAGE_S {
    TD_S32 what;                 // 消息编号：开始录像、停止录像、设置参数等
    TD_S32 arg1;                 // 参数1：含义由具体 what 约定
    TD_S32 arg2;                 // 参数2：很多产品消息用来标识工作模式
    TD_S32 s32Result;            // 返回结果，发请求时并不代表操作已经成功
    TD_U64 u64CreateTime;        // 时间字段；单位由使用方约定，不能凭名字猜
    TD_CHAR aszPayload[512];     // 附加参数字节区
} OT_MESSAGE_S;
```

尽量使用 `OT_MESSAGE_S msg = {0};`。不要在异步消息中把临时局部对象地址当作长期有效数据；inline payload 的生命周期与裸指针的生命周期不同。

### 9.2 入口一：UI/APP 发产品命令

依据：[SS_PDT_STATEMNG_SendMessage()][statemng]。

```c
/* 原函数核心节选，保留真正影响消息顺序的操作。 */
MAPI_MUTEX_LOCK(stateMngCtx->mutex);

if (stateMngCtx->isInProgress == TD_TRUE) {
    MAPI_MUTEX_UNLOCK(stateMngCtx->mutex);
    return OT_STATEMNG_EINPROGRESS; // 当前命令未完成，拒绝再接一条终端命令
}

ret = SS_HFSM_SendAsyncMessage(stateMngCtx->hfsmHdl, (OT_MESSAGE_S *)msg);
if (ret == TD_SUCCESS) {
    stateMngCtx->isInProgress = TD_TRUE;
    // 只表示命令已经发入 HFSM，后面的工作仍由状态机处理。
}

MAPI_MUTEX_UNLOCK(stateMngCtx->mutex);
return ret;
```

```c
/* 教学示意：发开始录像命令，不是本文新增进工程的代码。 */
OT_MESSAGE_S msg = {0};
msg.what = OT_EVENT_STATEMNG_START;
msg.arg2 = OT_PARAM_WORKMODE_NORM_REC;

td_s32 ret = SS_PDT_STATEMNG_SendMessage(&msg);
if (ret == TD_SUCCESS) {
    // 入队成功。不能在这里直接认定“录像文件已经建立并写盘成功”。
    // 最终结果需要看状态机回应事件的 s32Result。
}
```

`isInProgress` 是产品命令的忙标志，不是 Linux 线程状态，也不表示每一条底层事件都被禁止入队。

### 9.3 入口二：事件中心转发设备/录像事件

依据：[g_stateMngEvents / PDT_STATEMNG_EventProc][statemng]。

```c
/* 状态机订阅的异步事件回调节选。 */
static td_s32 PDT_STATEMNG_EventProc(const OT_EVENT_S *event, const td_void *arg)
{
    /* 原代码先检查 event 和状态机是否初始化。 */
    PDT_STATEMNG_Context *stateMngCtx = PDT_STATEMNG_GetCtx();
    return SS_HFSM_SendAsyncMessage(stateMngCtx->hfsmHdl,
                                   (OT_MESSAGE_S *)event);
    // 这里直接进 HFSM，不经过上面的终端命令 isInProgress 拒绝逻辑。
}
```

典型被直接转发的事件包括 SD 挂载/拔出、录像 FILE_END、录像错误、AHD 插拔。ACC 和普通按键主要先到 UI，由 UI 根据停车设置、APP 状态等决定发哪条状态机命令。

两条入口最后使用同一个产品 HFSM，但入口检查不同。因此“队列有空位”不保证 `SS_PDT_STATEMNG_SendMessage()` 会接受请求，也不能认为“isInProgress=true 时 AHD、FILE_END 一定进不了队列”。

## 10. 状态机内部怎么处理？

### 10.1 创建：一个 HFSM 实例、一个消息队列配置

依据：[PDT_STATEMNG_CreateHFSMInstance()][statemng]。

```c
OT_HFSM_ATTR_S hfsmAttr = {0};
hfsmAttr.fnHfsmEventCallback = PDT_STATEMNG_HfsmEventProc;
// 无法处理消息、状态切换失败时通知产品层。

hfsmAttr.u32StateMaxAmount = OT_PARAM_WORKMODE_BUTT + 1;
// 状态容量包含 Base。不是线程数。

hfsmAttr.u32MessageQueueSize = 64;
// 消息队列配置容量。不是能并行执行 64 项媒体操作。

ret = SS_HFSM_Create(&hfsmAttr, &PDT_STATEMNG_GetCtx()->hfsmHdl);
```

随后初始化 Base、录像、拍照、升级等状态，调用 `SS_HFSM_SetInitialState()`，再 `SS_HFSM_Start()`。

### 10.2 每个状态只是一组函数指针

依据：[ss_hfsm.h][hfsm]。

```c
typedef struct StateInfo {
    OT_STATE_ID stateID;          // 状态编号
    TD_CHAR name[64];             // 状态名
    TD_S32 (*enter)(TD_MW_PTR argv);
    TD_S32 (*exit)(TD_MW_PTR argv);
    TD_S32 (*processMessage)(const OT_MESSAGE_S *msg,
                             const TD_MW_PTR argv,
                             OT_STATE_ID *stateID);
    TD_MW_PTR argv;              // 该状态的上下文
} OT_STATE_S;
```

```c
/* PDT_STATEMNG_RecStatesInit 原代码节选。 */
static PDT_STATEMNG_StateAttr normalRec = {
    {
        OT_PARAM_WORKMODE_NORM_REC,
        PDT_STATEMNG_STATE_REC_NORMAL,
        PDT_STATEMNG_RecStatesEnter,     // 进入录像状态时调用
        PDT_STATEMNG_RecStatesExit,      // 离开录像状态时调用
        PDT_STATEMNG_RecStatesMsgProc,   // 收到消息后在这里分派
        TD_NULL
    }
};
normalRec.state.argv = &normalRec;
ret = SS_HFSM_AddState(PDT_STATEMNG_GetCtx()->hfsmHdl,
                      &normalRec.state,
                      &baseState->state);
// 把 NormalRec 挂在 Base 下；不是为它新建一个 pthread。
```

```text
产品 HFSM
  Base：通用消息与状态转换
    ├─ NormalRec：录像开始/停止、紧急录像、缩时切换等
    ├─ Photo 相关状态：拍照工作模式
    └─ Upgrade：升级工作模式
```

**普通录像与缩时录像并不是各占一个永远运行的线程。**当前 `NormalRec` 的处理函数中就有 `LASPE_START`、`LASPE_STOP` 分支。源码接口名将 LAPSE 拼为 LASPE 的地方，调用时必须使用现有标识符。

### 10.3 分派：看 what，调用具体业务函数

依据：[PDT_STATEMNG_RecStatesMsgProc()][recstate]。

```c
/* 原 switch 节选，中间省略其他 case。 */
switch (msg->what) {
    case OT_EVENT_STATEMNG_START:
        PDT_STATEMNG_RETURN_IF_WORKMODE_INVALID(
            OT_PARAM_WORKMODE_NORM_REC, msg->arg2, msg);
        ret = PDT_STATEMNG_RecStateProcStartRecMsg();
        break;

    case OT_EVENT_STATEMNG_STOP:
        PDT_STATEMNG_RETURN_IF_WORKMODE_INVALID(
            OT_PARAM_WORKMODE_NORM_REC, msg->arg2, msg);
        ret = PDT_STATEMNG_RecStateProcStopRecMsg(msg);
        break;

    case OT_EVENT_STATEMNG_LASPE_START:
    case OT_EVENT_STATEMNG_LASPE_STOP:
        ret = PDT_STATEMNG_RecStateProcLapseMsg(msg);
        break;

    /* 通用消息可 return OT_PROCESS_MSG_UNHANDLER，交给父状态继续处理。 */
}

(td_void)PDT_STATEMNG_PublishMsgResp(msg, ret);
return OT_PROCESS_MSG_RESULTE_OK;
```

这里有两个容易混淆的“成功”：

- `ret`：本次开始/停止/切换业务的执行结果，作为回应中的 `s32Result`。
- `OT_PROCESS_MSG_RESULTE_OK`：向 HFSM 表示“这个状态已经处理这条消息”。它不能代替业务结果。

状态切换通过 HFSM 的父子状态关系、状态处理返回值和目标状态完成，不应把“调用 RecStatesEnter”理解成“创建了录像线程”。真正的媒体线程由 Enter 内调用的媒体/录像库另行管理。

### 10.4 回应：先清忙，再发布结果

依据：[PDT_STATEMNG_PublishMsgResp()][utils]。

```c
OT_EVENT_S event;
ret = memcpy_s(&event, sizeof(OT_EVENT_S), msg, sizeof(OT_MESSAGE_S));
if (ret != EOK) {
    return;                         // 原代码还打印错误
}

event.s32Result = result;            // 业务执行结果
MAPI_MUTEX_LOCK(stateMngCtx->mutex);

MAPI_MUTEX_UNLOCK(stateMngCtx->mutex);

ret = SS_EVTHUB_Publish(&event);     // 通知 UI/APP 等订阅者
```

因此完整链路有“请求”和“结果事件”两段。若某异常分支没有清忙或漏发回应，就可能表现为后来一直忙、APP 一直等。分析具体问题时要沿相应失败分支核查，不能仅看到请求打印就说状态机已经处理完。

```c
/* ui_state_msg_mng.c 原代码节选。 */
```

## 12. APP 的同步消息为什么会等待？

依据：[product_netctrl_msg.c][netmsg]。

```c
/* PDT_NETCTRL_SendSyncMsg 原代码节选。 */
OT_MUTEX_LOCK(g_msgCtx.msgMutex);     // 串行保护 APP 消息事务
g_msgCtx.isMsgProcessed = TD_FALSE;
/* 原代码把 what、arg1、arg2、payload 复制到 g_msgCtx.messgse。 */

ret = SS_PDT_STATEMNG_SendMessage(message);
/* 发送失败时，原函数恢复标志、释放锁并返回。 */

while ((sem_wait(&g_msgCtx.netctrlSem) != TD_SUCCESS) && (errno == EINTR));
// 等待结果事件；当前用 sem_wait，没有显式超时时间。

*result = g_msgCtx.msgResult;         // 取业务结果
g_msgCtx.isMsgProcessed = TD_TRUE;
OT_MUTEX_UNLOCK(g_msgCtx.msgMutex);
return TD_SUCCESS;
```

是谁唤醒它？同文件的 EventHub 回调：

```c
if (!g_msgCtx.isMsgProcessed) {
    if (g_msgCtx.messgse.what == (td_s32)event->EventID &&
        g_msgCtx.messgse.arg1 == event->arg1 &&
        g_msgCtx.messgse.arg2 == event->arg2) {
        g_msgCtx.msgResult = event->s32Result;
        ret = sem_post(&g_msgCtx.netctrlSem); // 结果匹配，唤醒等待的 APP 请求
    }
}
```

这里有两层结果：函数返回值表示同步调用通路是否完成，`*result` 表示实际状态机业务结果。APP 看似“卡住”，可能是业务慢，也可能是结果事件没有匹配/返回，不能简单说线程数量不够。

### 12.1 学习时用这几个问题追踪卡住点

1. 命令是否经过 `SS_PDT_STATEMNG_SendMessage()`？返回了什么？
2. 是否出现 `will process message what(...)`？没有则看入队、队列积压和线程状态。
3. 具体业务函数卡在媒体停止、文件关闭、设备操作还是等待锁？
4. 有没有调用 `PDT_STATEMNG_PublishMsgResp()`，`result` 是什么？
5. EventHub 有没有把结果送到正确订阅者，what/arg1/arg2 是否匹配？
6. 是一个线程等待，还是整个 main_app 已退出？喂狗是否还在？

## 13. 板端如何准确统计进程和线程？

**以下在摄像机串口 shell 上执行，不是在 `yh@192.168.100.45` 的编译服务器上执行。**命令只读取 `/proc`，不停止录像、不杀进程。执行命令本身会短暂增加 shell 工具进程，因此全系统计数是近似同一时间段的快照。

### 13.1 查 main_app 总线程数

```sh
pidof main_app

# 通常只有一个 main_app；下面逐个处理，避免把多个 PID 拼成无效路径。
for app_pid in $(pidof main_app); do
    printf '\nMAIN_APP PID=%s\n' "$app_pid"
    sed -n '/^Name:/p; /^State:/p; /^Tgid:/p; /^Pid:/p; /^PPid:/p; /^Threads:/p; /^VmRSS:/p; /^VmSize:/p' \
        "/proc/$app_pid/status"
    # Threads 是内核报告的该进程线程数，包含主线程。
done
```

### 13.2 列每个进程及其线程数量

```sh
printf '%-8s %-8s %-8s %s\n' PID PPID THREADS NAME
process_count=0
task_count=0
for process_dir in /proc/[0-9]*; do
    [ -r "$process_dir/status" ] || continue
    process_count=$((process_count + 1))
    awk '/^Name:/{n=$2} /^Pid:/{p=$2} /^PPid:/{pp=$2} /^Threads:/{t=$2}
         END{printf "%-8s %-8s %-8s %s\n",p,pp,t,n}' "$process_dir/status"
    n=$(sed -n 's/^Threads:[[:space:]]*//p' "$process_dir/status")
    case "$n" in ''|*[!0-9]*) ;; *) task_count=$((task_count + n));; esac
done
printf '可见进程目录数=%s，累计 task 数=%s\n' "$process_count" "$task_count"
```

这里把 `/proc` 中可见的内核任务也计入，不是“用户业务进程数”。不要把所有方括号内的内核任务当作 main_app 创建的线程。

### 13.3 每条线程的名字、状态、等待位置

```sh
for app_pid in $(pidof main_app); do
    printf '\nPID=%s 的线程\n' "$app_pid"
    printf '%-8s %-18s %-4s %s\n' TID NAME STATE WCHAN
    for task_dir in /proc/$app_pid/task/[0-9]*; do
        [ -r "$task_dir/status" ] || continue
        tid=${task_dir##*/}
        name=$(cat "$task_dir/comm")
        state=$(sed -n 's/^State:[[:space:]]*\([^[:space:]]*\).*/\1/p' "$task_dir/status")
        wchan=$(cat "$task_dir/wchan" 2>/dev/null)
        printf '%-8s %-18s %-4s %s\n' "$tid" "$name" "$state" "$wchan"
    done
done
```

`/proc/PID/task/TID` 表示某进程下的线程目录，见 [proc_pid_task 手册](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html)。线程可能在采集期间退出，个别读取失败并不等于故障。

| 现象 | 首先如何理解 |
|---|---|
| `S` + futex 等待 | 常见于等锁、条件变量、信号量；空闲播报线程这样是正常的 |
| `S` + 定时睡眠 | 常见于 ACC、LED、喂狗轮询周期 |
| `S` + select/poll 等待 | 编码取流、网络收包等可能正在等数据 |
| `D` | 常见于内核不可中断等待；结合 SD、文件系统、驱动路径检查 |
| `R` 长期高 CPU | 可能大量有效计算，也可能重试/空转，需结合 CPU 采样 |
| 某模式切换后 TID 被替换 | 可能是媒体线程被正常销毁重建 |
| 每次切换后 Threads 只增不减 | 需要核查线程是否泄漏，不能只凭一次高数量判定 |

`wchan` 只给出内核等待点，不能单独定位到哪一个 C 函数，也不能单独证明死锁。获取用户态调用栈通常需要调试器/符号，属于另一个排查步骤。

### 13.4 建议记录的场景

| 场景 | 重点观察 |
|---|---|
| 未插后路，普通录像，APP 未连接 | 基线 PID、Threads、VENC 取流线程 |
| 插上后路，普通双录 | cam1 对应取流/录像任务是否新增 |
| APP 实时预览 | RTSP 会话和预览通道变化 |
| ACC OFF，进入缩时，等待切换完成 | 旧媒体线程回收、新线程出现，业务状态稳定 |
| ACC ON，回普通录像 | 线程数是否回到对应普通录像范围 |
| 连续切换数轮 | 排除线程/资源逐轮增长 |
| 播报期间与结束后 | 临时 AAC 发送线程的出现和回收 |

最好同步记录时刻、AHD 状态、APP 是否连接、是否播报，否则两次线程数不同没有可比性。

## 14. 线程最多能开多少个？

没有从 `CONFIG_MEM_TOTAL_SIZE=128` 直接算出的“最多 N 个线程”。实际受以下约束共同限制：

- Linux 的系统 task/PID 上限。
- 进程/用户资源限制（root 等权限情况要单独考虑）。
- 用户态线程栈、TLS、线程库控制结构，以及内核每 task 开销。
- 地址空间和可用 Linux 内存。
- CPU 调度压力与实时业务期限。
- 应用自身的句柄、队列和通道数量限制。

Linux 的 pthread 创建在资源不足或触及相关限制时可以返回 `EAGAIN`；见 [pthread_create 的错误说明](https://man7.org/linux/man-pages/man3/pthread_create.3.html)。即使“还能创建”，也不等于“还能稳定双录”。

### 14.1 HC112_B 的内存不能全给线程使用

当前 `config.conf`：

```text
CONFIG_MEM_TOTAL_SIZE="128"
CONFIG_MEM_LINUX_SYS_SIZE="0x02B00000"
CONFIG_MEM_LINUX_MMZ_SIZE="0x5500000"
CONFIG_MEM_PARAM_SIZE="0x0"
CONFIG_MEM_RES_SIZE="0x0"
```

```text
0x02B00000 / 1024 / 1024 = 43 MiB Linux 系统区
0x05500000 / 1024 / 1024 = 85 MiB MMZ 总区
43 + 85 = 128 MiB
```

43 MiB 还要容纳内核、main_app、网络进程、文件系统和其他普通内存开销，不全是线程栈预算。85 MiB 的 MMZ 主要给媒体使用，不能按“还有几十 MiB MMZ 空闲”直接推出能再开几百个 pthread。

`anonymous` 在 `mmz_zones` 里是媒体 MMZ 区名；它与 Linux 普通匿名页内存不是同一个概念。具体 anonymous/ringbuf 分割应以板端 `/proc/cmdline` 和 MMZ 实际使用信息为准。

### 14.2 默认线程栈不能直接套 PC Linux 的数值

当前选择 `CONFIG_MUSL=y`，大量代码 `pthread_create(..., TD_NULL, ...)` 使用库默认属性。默认栈大小受工具链 libc、构建选项等影响；不能把 glibc PC 上常见的 8 MiB 直接套到这块板上。

比如 Hisnet 源码的 128 KiB 显式栈设置在 `__HuaweiLite__` 分支里；当前 Linux 分支传的是 `TD_NULL`。不能看见那行 128 KiB 就说本机 HTTP 线程固定 128 KiB。

下面是**可选测量程序示意，本次没有新增到工程或编译运行**：

```c
/* 教学示意：在对应工具链/设备上查看默认新线程栈属性。 */
#include <pthread.h>
#include <stdio.h>

int main(void)
{
    pthread_attr_t attr;
    size_t stack_size = 0;
    if (pthread_attr_init(&attr) != 0) {
        return 1;
    }
    int ret = pthread_attr_getstacksize(&attr, &stack_size);
    if (ret == 0) {
        printf("default thread stack=%zu bytes\n", stack_size);
    }
    pthread_attr_destroy(&attr);
    return ret != 0;
}
```

这只能测默认属性，已创建线程可能使用自定义属性；不能用单一默认值替代所有线程的实际占用。

### 14.3 预算怎么计算？

假设（仅举例）经测量后，扣除正常业务及保留余量，还有 4 MiB 可以用于新线程，每条新线程按 128 KiB 栈预算：

```text
只计算栈的理论数量 = 4 × 1024 / 128 = 32 条
```

这个 32 仍没有算 TLS、内核栈、task 结构和新功能数据，更没有算 CPU 负载，所以**不是建议增加 32 条线程**。实务上先算少量新增线程的资源，再跑双录、APP、缩时切换等负载验证。

板端可读的上限和当前占用：

```sh
cat /proc/sys/kernel/threads-max
cat /proc/sys/kernel/pid_max
cat /proc/meminfo
for app_pid in $(pidof main_app); do
    cat "/proc/$app_pid/limits"
done
```

`/proc/PID/limits` 是该进程的资源限制快照，见 [proc_pid_limits 手册](https://man7.org/linux/man-pages/man5/proc_pid_limits.5.html)。`ulimit -s` 是当前 shell 的限制，不能单独代表所有已有线程的真实栈分配。

### 14.4 哪些数字不是线程上限？

| 工程数值 | 真正含义 |
|---|---|
| HFSM `u32MessageQueueSize=64` | 队列消息容量 |
| `TIMEDTASK_MAX_NUM=16` | 本包装模块定时任务槽位数量 |
| 播报 `maxQueueSize=10` | 待播报请求数 |
| `g_venc_max_chn_num` | VENC 通道资源配置，不是整个进程线程数 |
| cam0、cam1 | 摄像头逻辑编号，不是 PID/TID |
| `threads[2]` | 存放句柄的数组容量，实际创建多少要看循环次数 |

## 15. 对这份代码的线程管理应怎样评价？

当前总体结构是“各模块管理自己的线程，跨模块通过事件和状态机协调”，没有一个统一的产品线程池管理所有工作。Linux 调度器决定哪个可运行线程获得 CPU，产品状态机决定录像/参数/模式操作如何按消息执行；二者是不同层次。

以下是阅读时应知道的具体限制，不是本次已经修复的内容：

1. 网络 GPS 的两次 pthread_create 在调用处没有检查返回值；不能仅凭 NETCTRL_Init 成功就认定两条线程都创建成功。Deinit 片段主要改退出标志，完整回收是否充分要沿线程退出路径检查。
2. `SS_SYSTEM_MuteDeinit()` 只置退出标志；不等同于已经 join。声控 Deinit 也包含 cancel 后清句柄的路径，不能把“发出了取消请求”等同于“线程已经退出”。
3. APP 同步消息采用无显式超时的 sem_wait；若回应漏发或未匹配，调用上下文可能持续等待。
4. 当前 UI 的 AAC 播放前还有等待媒体重建标志的循环。它会占用播报消费者的处理位置，不能当作一个新的工作线程。
5. `FILEMNG_GetMovieSpace()` 当前临时统计数组只有前路一项。本文只据它确认创建 1 条临时线程，没有据此判断整个空间统计逻辑一定正确。
6. 状态机忙标志只覆盖它的约定范围，不是 Flash、音频、UI 和所有设备线程共享的一把总锁。

学习或排查时，优先把 **线程入口 → 共享上下文 → 等待条件 → 发出什么事件 → 谁来消费 → 如何结束/回收** 六项连起来。这样看到“ACC 线程仍在打印但 APP 没回应”，就能继续检查 UI、HFSM 和结果事件，而不是笼统地把所有问题归为“程序卡死”。
