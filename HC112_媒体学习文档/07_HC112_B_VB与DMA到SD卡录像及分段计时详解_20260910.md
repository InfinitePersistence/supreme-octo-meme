## 1. 先纠正最容易混淆的一句话

**正常录像不是“把 VB 块直接写进 SD 卡”。**

VB 主要服务于原始图像／处理后图像的媒体缓冲管理。正常录像写入 SD 卡的是编码后的 H.264／H.265 数据，加上音频、GPS 等数据，经录像库调度、TS 封装形成文件。

```text
前摄 GC4653 ─→ MIPI／VI／ISP ─→ VPSS（缩放、翻转、水印等相关处理）─→ VENC 0
后摄 AHD ─→ AHD 芯片／MIPI／VI ─→ VPSS                         ─→ VENC 3
                     │                 │                            │
                     └─ 图像 VB／模块缓冲／前路卷绕缓冲 ─────────────┘
                                                                    ↓
                                                     编码码流缓冲：H.265/H.264
                                                                    ↓
                                               取流线程 GetStream → 录像回调
                                                                    ↓
                                             SS_REC_WriteData → 录像 ringbuf
                                                                    ↓
                                         录像库分段／音视频组织 → TS 封装回调
                                                                    ↓
                                             SS_TS_WriteFrame → 文件格式库
                                                                    ↓
                                         fwrite／文件缓存 → Linux 文件系统
                                                                    ↓
                                           块层／MMC 主机驱动 → SD 卡控制器
                                                                    ↓
                                                   SD 卡内部控制器／闪存
```

这是**数据流概览**，不是说每个箭头都发生一次 CPU memcpy，也不是说所有模块都使用同一个 VB 块。在线链路、离线链路和卷绕模式的内存行为不同。

音频侧是 `AI/ACAP → AENC → RECMNG_ProcAencData()`，随后进入录像库。GPS 私有数据也可作为轨道进入封装，与图像 VB 是不同入口。

### 2.1 五类缓冲并不是一回事

| 缓冲 | 保存什么 | 谁管理 | 是否直接就是录像文件 |
|---|---|---|---|
| 图像 VB | RAW／YUV 等图像或模块所需帧数据 | VB／VI／VPSS 等媒体模块 | 否 |
| 前路 VPSS→VENC 卷绕缓冲 | 按行组织、循环使用的图像处理数据 | VPSS/VENC 驱动与硬件 | 否 |
| VENC 码流缓冲 | 编码器输出的压缩码流包 | 编码驱动及 GetStream/ReleaseStream | 否 |
| Recorder ringbuf | 等待录像消费者处理的编码帧、时间戳等 | recorder_pro | 否 |
| 文件写缓存／内核页缓存 | 封装后的文件字节 | 文件格式库、libc、Linux 文件系统 | 是文件数据的缓存，但未必已落到闪存 |

因此：增加 `recbuffer_time0` 不会直接增加图像 VB 池，也不会把默认 60 秒录像变为 3.6 秒录像。

## 3. VB 是怎样从 INI 变成真实内存池的？

### 3.1 从 INI 读取每块大小和块数

前摄 4K 文件当前有以下配置，文件名虽带 `2160p30`，内部实际枚举是 2160P25：

```ini

[vb.pool.0]
blk_size  = "5529600" ; 2560 × 1440 × 3 / 2
blk_count = "3"       ; 这种大小的块准备 3 块

[vb.pool.1]
blk_size  = "3110400"
blk_count = "0"       ; 本项配置数量为 0，不等于整个系统无需 1080P 内存

[vb.pool.2]

```

[product_iniparam_cammedia.c][inivb] 中 `PDT_INIPARAM_LoadCamVBSpecCfg()` 读取它们：

```c
/* 源码节选＋注释：读取池配置，并没有在此处 malloc 图像内存。 */
ret = sprintf_s(nodeName, PDT_INIPARAM_NODE_NAME_LEN,
                "%s.pool.%u:blk_size", vbName, vbIdx);
ret = SS_CONFACCESS_GetInt(PDT_INIPARAM, iniModule,
                          nodeName, 0, &tempValue);

// blkSize：池中单个块的字节数。

ret = sprintf_s(nodeName, PDT_INIPARAM_NODE_NAME_LEN,
                "%s.pool.%u:blk_count", vbName, vbIdx);

                          nodeName, 0, &tempValue);
```

INI 是配置来源，通常要经过参数生成／载入流程。不能由上述函数推出“板端每次启动一定直接读取这份源目录下的文本 INI”。

```text
空闲块
  → VI/VPSS 等生产者取得使用权
  → 硬件写入图像数据
  → 下游持有帧／缓冲引用，读取图像
  → 各使用者完成并释放引用
  → 可重新用于后续帧
```

这是缓冲生命周期模型，不代表每个环节总是同一个物理块：缩放、格式转换、压缩、离线输出等可能产生新的输出缓冲。正常绑定链路由模块调度，不需要应用循环“取 VB → memcpy → 送下一模块”。

### 4.1 图像块大小怎么算？

仅对**不压缩、8 位、YUV420、无额外对齐开销**的理想情况：

```text
Y 平面：宽 × 高
UV 总量：宽 × 高 / 2
合计：宽 × 高 × 3 / 2

2560 × 1440 × 3 / 2 = 5,529,600 B = 5.2734375 MiB
3 块 = 16,588,800 B = 15.8203125 MiB

3840 × 2160 × 3 / 2 = 12,441,600 B = 11.865234375 MiB
```

不能把最后一行直接当作当前 4K 每个实际 VB 块大小。当前前路输出使用了卷绕，以及 10 bit／压缩相关配置；还有 stride、header、对齐和模块私有内存。

后摄 INI 的公共 VB 块数为 0，也不表示后摄不占内存。还存在模块缓冲、编码缓存和录像缓存；实际分配要看初始化输出及 `/proc`。

## 6. DMA 在链路中怎样工作？CPU 又做什么？

### 6.1 DMA 不是一条“复制线程”

DMA 指硬件按驱动准备的地址、长度、格式等进行内存访问。CPU 配置和调度，硬件搬运或处理数据，完成后通过中断／状态／队列通知软件。

| 环节 | CPU／软件主要工作 | 硬件主要工作 |
|---|---|---|
| VI/ISP | 配置输入、帧率、模式、缓冲和启动 | 接收传感器数据、处理图像，按模式访问内存 |
| VPSS | 配置输出尺寸、端口、翻转、卷绕等 | 图像处理及对应内存读写 |
| VENC | 配置编码、绑定、开始收帧、取流 | 读取图像、压缩、写出编码码流 |
| Recorder/TS | 管理编码帧、切片、轨道、文件 | 不应直接理解成另一台 DMA 编码器 |
| SD/MMC | 文件系统和驱动准备块请求 | 主机控制器传输数据；具体 DMA/PIO 取决于驱动和运行配置 |

前摄 INI 的 VI/VPSS 模式为 `2`，注释对应 VI online / VPSS offline；后摄为 `0`，对应 VI offline / VPSS offline。它们提醒我们：**不能把前后摄每一级都画成相同的“完整帧落 DDR 后再读出”。**最终模式还要核实运行中的设置。

### 6.2 绑定接口就是应用交出逐帧搬运控制权的重要位置

[media_venc.c][mediavenc] 通过 `MEDIA_BindVencChn()` 调用 `SS_MAPI_VENC_BindVproc()`，最终在 [mapi_venc_adapt.c][vencadapt]：

```c
/* 源码节选＋注释：非拼接的 VPSS → VENC 绑定分支。 */
srcChn.mod_id = OT_ID_VPSS;
srcChn.dev_id = vprocHdl;
srcChn.chn_id = vportHdl;

destChn.mod_id = OT_ID_VENC;
destChn.dev_id = vencDevHdl;
destChn.chn_id = vencHdl;

ret = ss_mpi_sys_bind(&srcChn, &destChn);
// 建立媒体模块关系；这里没有 fread/fwrite，也没有逐像素 memcpy。
```

绑定不等于“这一句已经编码了一帧”，还要有前后级初始化、启用及收帧。其后的帧流转和 DMA 寄存器设置在 SDK/驱动内部，不是应用直接将 SD 文件地址写给 VI。

### 6.3 物理地址、虚拟地址和 DMA 地址不能混用

CPU 解引用的是虚拟地址；设备使用 DMA 可访问的总线地址。两者是否与物理地址数值相同取决于平台。**不能将 `void *` 强转整数后直接当 DMA 地址。**Linux 的正式说明见 [DMA 地址与映射指南](https://docs.kernel.org/core-api/dma-api-howto.html)。

```c
/* 教学示意：不是 HC112_B 驱动原文，也不表示这里使用某个具体 DMA API。 */
buffer = obtain_buffer_from_media_pool();
device_address = get_device_accessible_address(buffer);

prepare_buffer_for_device(buffer); // 涉及缓存一致性和所有权交接
program_device(device_address, stride, width, height);
start_device();

/* 完成中断／状态到来后，驱动交付帧描述，而不是凭延时猜传输完成。 */
on_device_done() {
    deliver_frame_with_pts(buffer);
}
```

这段只为解释“谁启动传输、谁通知完成”。本次没有拿到并逐行确认 CV610 专有 VI/VENC 内部 DMA 描述符实现，也没有板端 MMC 的 DMA 模式快照，因此不编造寄存器地址、DMA 通道号或“必然走 ADMA”的结论。

### 6.4 cached MMZ 不等于自动完成所有 DMA 同步

缓存映射只是一种 CPU 访问属性。涉及 CPU 与非一致性设备交换数据时，需要遵守驱动/API 的同步和所有权约定；不能自行到处加 cache flush，也不能认为 `alloc_cached` 能解决所有问题。此处原理参考上面的 Linux DMA 指南，具体动作仍以 SDK 接口为准。

尤其要分清：Recorder ringbuf 在 MMZ 中，不代表 SD DMA 会直接读取这块 ringbuf；本工程仍走 TS 文件写入链路。

### 7.3 录像帧描述没有把图像 YUV 当 H.265

```c

frameData.u32SliceCnt = 0;
frameData.u64TimeStamp = vencData->dataPack[vencData->packCount - 1].timeStamp;

                       &recmngTrackSrc->trackSrc, &frameData);
// 交给当前录像对象，不是立即把 YUV 写卡。
```

Linux 下分片地址这样提取：

```c
/* 源码节选＋注释：每个编码 pack，去掉 offset 前的非有效部分。 */

td_u32 frameOffset = vencData->dataPack[packIdx].offset;
```

重要规则：回调结束后，上游会 ReleaseStream。新增异步代码不能只保存这些临时指针、稍后再读；必须遵守数据生命周期，或复制到自己拥有的缓冲中。

### 8.1 环形缓存怎样缓冲 SD 卡写入抖动？

```text
生产者：VENC 取流回调 → 把编码帧交给 recorder
                         ↓ 写位置推进
                 [已经消费][尚未消费][空闲区域]
                              ↑ 读位置推进
消费者：录像库 → TS 封装 → 文件写入
```

SD 偶发慢写时，消费者落后，未消费数据积累。缓存能吸收一部分抖动；如果持续入流大于写出能力，再大缓存也会耗尽。

例如仅做码流量级估算，按 1 Kbps = 1000 bit/s：

```text
前路：20480 × 1000 / 8 × 3.6 = 9,216,000 B ≈ 8.79 MiB
后路：10240 × 1000 / 8 × 3.2 = 4,096,000 B ≈ 3.91 MiB
```

这**不是 recorder 当前精确申请公式**。实际还有码率解释、帧头、关键帧、音频、缩时速度、对齐和库策略；还可能有参数覆盖。不能拿相加结果直接断言“恰好够用”或“已经溢出”。真实依据是 `alloc bufSize[...]` 日志及 MMZ 占用。

`RingBufWriteMainFrame ... check write over` 一类日志发生在编码后录像缓存侧，不应直接解释为原始 VB 创建失败。应联查写卡耗时、缓存占用、消费者是否阻塞、分段／停录是否进行中。

### 9.4 当前库能确认到哪一层？

本次只读检查了当前 `libts.a` 和 `libfileformat.a`：

```text

  TsMuxer::WriteFrame
```

[ss_ts_format.h][tsh] 也明确给出：

```c

```

文件字节经用户态缓存和 Linux 文件系统交给块设备层。MMC 主机驱动把块请求转成卡协议命令和数据传输；卡内部还要完成闪存编程。**SD 卡控制器不理解 VB、H.265、关键帧或者“录 1 分钟”，它处理的是块读写请求。**

### 9.5 哪个返回值才叫“已经落盘”？

| 观察到的事件 | 可以说明什么 | 不能直接说明什么 |
|---|---|---|
| `SS_REC_WriteData` 成功 | 录像库接受了该数据 | 已写到 SD 闪存 |
| `SS_TS_WriteFrame` 成功 | 本次封装接口成功 | 已完成卡内部持久化 |
| `fwrite` 成功 | 字节被该 IO 层接受 | 全部字节已经持久化 |
| 文件结束事件 | 录像流程进入文件结束阶段 | 当前所有异步关闭和设备写入都完成 |
| `fflush` / `fclose` 成功 | 用户态缓冲提交／文件流关闭 | 单凭它不能证明断电后一定不丢数据 |
| 正确的持久化及设备完成流程 | 更接近安全断电条件 | 仍依赖驱动、卡行为、错误处理及供电余量 |

Linux 明确说明 `write()` 成功不保证持久化；`fsync()` 是要求同步文件数据及相关元数据的接口。见 [write 手册](https://man7.org/linux/man-pages/man2/write.2.html)、[fsync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)。本文没有据此建议在每帧后加 fsync，也没有断言当前工程完全没有同步操作。

当前还存在 `RECMNG_SUPPORT_ASYNC_STOP` 的异步关闭机制，见 [recordmng_muxer_async.c][muxasync]。分析下电／格式化问题时，要确认录像停止、异步销毁、文件关闭和卸载的先后，不能只看 UI 已经显示停止。

## 11. “精准计时”必须区分四种时间

| 时间 | 来源／用途 | 能否直接代替其他时间 |
|---|---|---|
| 媒体 PTS | 编码帧携带，用于媒体时序 | 不等于年月日文件名 |
| 文件名墙钟时间 | `gettimeofday`、本地时间格式化 | 不能精确代表第一帧 PTS |
| 系统日志打印时间 | 调度到打印位置的时刻 | 包含线程排队与执行延迟 |
| 文件写入完成时间 | 文件系统／设备完成状态 | 不是“最后一帧拍摄时刻” |

### 11.1 PTS 在当前源码中如何传递？

[mapi_venc_adapt.c][vencadapt]：

```c
/* 源码原语句＋注释 */
outVStream->dataPack[i].timeStamp = stream->pack[i].pts;
// 从 MPI 码流包取时间戳，向上层传递。
```

之后：

```text
MPI pack.pts
 → MAPI dataPack.timeStamp
 → OT_REC_FRAME_DATA_S.u64TimeStamp
 → Recorder 时序／分段处理
 → OT_TS_FRAME_DATA_S.u64TimeStamp
 → TS 内部容器时基处理
```

不能把 TS 播放器看到的时间基数与上游微秒计数混用。换算要看各层单位和库处理，不能把同一个整数直接当作“秒”。

### 11.2 当前录像库的计时证据与边界

当前没有找到 `rec_split.c` 的 C 源文件；`librecorder_pro.a` 中可确认存在 `rec_split.o`，以及 `RecSplitUpdateInfo`、`RecSplitSetSplitBound`、`RecSplitFile` 等符号。

本次对当前输出库的 `RecSplitUpdateInfo` 做了只读局部反汇编，能看到：

```asm
; 当前 ARM 库的节选，注释为分析说明；不是厂家 C 源码。
subs r0, r0, r3      ; 64 位差值的低 32 位
mov  r3, #0         ; 设置除数高 32 位；此指令不改动前一步的进位标志
sbc  r1, r2, r1      ; 64 位差值的高 32 位
mov  r2, #1000
bl   __aeabi_uldivmod ; 64 位除法：将差值按 1000 换算
```

同时有初始基准保存、时间回退比较和补偿后阈值比较路径，说明不是应用 `sleep(60)` 后简单关文件。上面保留这五条指令的顺序，省略了机器码、地址以及前后分支。

结合上游 PTS 传递，可判断分段存在基于媒体时间的判断路径。**不能从这一段就声称已还原精确阈值、容差、所有缩时分支或关键帧策略。**库中还有帧间隔相关补偿；本文不伪造 `RecSplitIsAchiveTime()` 的完整 C 实现。

教学上，普通录像可先这样理解时间量纲：

```c
/* 教学示意：不是当前库的完整分段算法，省略了实际补偿与状态。 */
uint64_t elapsed_us = current_pts_us - segment_base_pts_us;
uint64_t elapsed_ms = elapsed_us / 1000;
uint64_t target_ms = (uint64_t)split_seconds * 1000;

if (elapsed_ms >= target_ms) {
    request_segment_boundary();
    // 请求达到边界，不等于这时 SD 硬件已经关闭旧文件。
}
```

例如普通录像若首帧 PTS 为 10,000,000 µs，目标 60 秒对应约 70,000,000 µs 的边界。25 fps 相邻正常帧间隔约 40,000 µs。这个例子解释单位，不表示该库一定在正好这个值上切割。

### 11.3 为什么关键帧影响独立播放与切片边界？

新文件需要可解码的起点和参数信息。P 帧通常依赖其他帧，不能随便挑一段字节当作新录像的完整起点。

[recordmng_source.c][recsource] 的 `RECMNG_GetVencFrameType()` 把 H.264/H.265 的 IDR、ISLICE、SPS 等类型映射为 `bKeyFrameFlag`，将边界所需信息交给 recorder：

```c
/* 源码节选＋注释：H.265 分支。 */
if ((vencDataType->h265EType == OT_MAPI_VENC_H265E_NALU_IDRSLICE) ||
    (vencDataType->h265EType == OT_MAPI_VENC_H265E_NALU_ISLICE) ||
    (vencDataType->h265EType == OT_MAPI_VENC_H265E_NALU_SPS)) {
    frameData->bKeyFrameFlag = TD_TRUE;
} else {
    frameData->bKeyFrameFlag = TD_FALSE;
}
```

此处的标志是工程定义的抽象，包含 SPS；**不能因此把每个 `bKeyFrameFlag=true` 都解释成新增了一幅 IDR 图像。**

当前普通模式 INI 的 GOP=25、帧率=25，名义 GOP 间隔约一秒。一般来说，分段需要协调时长阈值与可解码边界；具体选择阈值前还是后、是否主动请求 IDR、如何分配边界帧，要以 recorder 实现／实际文件检查为准。本文不承诺“永远正好 60.000 秒”或“误差一定小于一帧”。

## 12. 当前 HC112_B 还有一条会影响分段时间的真实代码

这不是泛泛而谈的 SD 慢写，而是工作区里明确存在的前后路文件名时间修正。

### 12.1 文件名按墙钟计时，还做了四舍五入

[ot_dtcf.c][dtcf] 的 `SS_DTCF_GetTime()`：

```c
/* 源码节选＋注释 */
gettimeofday(&tv, NULL);
if (tv.tv_usec > 500000) {
    tv.tv_sec++;              // 超过半秒，把文件名秒数进一位
}

if (enDir == DTCF_DIR_NORM_FRONT) {
    front = tv.tv_sec;        // 记录前路最近一次命名时间
} else if (enDir == DTCF_DIR_NORM_REAR) {
    rear = tv.tv_sec;         // 记录后路最近一次命名时间
}
localtime_r((time_t *)&tv.tv_sec, &t);
```

因此，文件名相差一秒不必然意味着视频丢了一秒，也不能用文件名差值代替逐帧 PTS 检查。

### 12.2 检测到命名秒数差为 2 时，会请求双路手动分段

```c
/* 源码节选＋注释：DTCF_CheckFileTime。 */
checkCount = abs(front - rear);
if (checkCount > 1 && checkCount <= 2) {
    return TD_TRUE; // 当前条件对应整数秒差为 2
}
return TD_FALSE;
```

[ss_recordmng.c][recmng] 的 `RECMNG_PreProcFileEvent()`：

```c
/* 源码节选＋注释：新文件开始事件。 */
case OT_REC_EVENT_NEW_FILE_BEGIN:
    if (DTCF_CheckFileTime() && lapseMode != TD_TRUE) {
        CheckTimeFront = TD_TRUE;
        CheckTimeRear = TD_TRUE;
        SS_RECMNG_MySplit(0);
        SS_RECMNG_MySplit(1);
        // 除自动按时分段之外，又向前后录像任务发出手动分段请求。
    }
    /* 后续还有文件事件处理与发布。 */
    break;
```

`SS_RECMNG_MySplit()`：

```c
/* 源码节选＋注释 */
manualSplitAttr.enManualType = OT_REC_POST_MANUAL_SPLIT;
manualSplitAttr.stPostSplitAttr.u32AfterSec = SplitTimeSec;
ret = SS_REC_ManualSplit(taskCtx->recObj, &manualSplitAttr);
// POST manual split 的窗口长度来自当前 SplitTimeSec。
```

这部分源码原注释明确写到：为了修正前后路文件名不一致，可能使几十个视频中出现一个 1 分 01、1 分 02 秒的情况。

结论：当前段长受**自动时长规则、媒体边界、手动分段请求**等共同影响，不能只看 `split_time=60` 就断言每个文件应严格 60 秒。

本文没有删除或修改此策略，也不据此断言已经发生丢帧。要判断连续性，必须看相邻文件尾帧／首帧的 PTS 和画面，而不是只看文件名。

## 13. 4K 插帧、缩时录像与分段时长的关系

“插帧”与“分段”是不同维度：

- 图像尺寸：例如输出 3840×2160。
- 实际输入／编码帧率：每真实秒有多少张不同的图像被编码。
- 补帧／播放帧率：容器播放时间线如何组织。
- 文件切片：何时结束这一段、开始下一段。

当前 [ss_recordmng.c][recmng] 中 `playFps`、`fSpeed`、`isInsertFrame` 有分支控制；[recordmng_source.c][recsource] 还存在 `RECMNG_InsertVencFrame()`：

```c
/* 源码节选＋注释：只有 isInsertFrame 为真才进入。 */
if (!recmngTrackSrc->isInsertFrame) {
    return;
}

/* 计数条件满足后产生空数据补帧输入。 */
frameData->apu8SliceAddr[0] = TD_NULL;
frameData->au32SliceLen[0] = 0;
frameData->bKeyFrameFlag = TD_FALSE;
frameData->u32SliceCnt = 1;

ret = SS_REC_WriteData(*recmngTrackSrc->recObj,
                       &recmngTrackSrc->trackSrc, frameData);
```

这些不是 VI 又 DMA 采集了一张新的图像。也不能仅因为存在该函数，就认定当前普通 4K 或缩时运行时一定启用了它；须核对具体模式的 `playFps`、`fSpeed` 和 `isInsertFrame`。

对于“一真实秒录一帧、按 30 fps 播放”的缩时，纯帧数关系是：

```text
真实采集 30 秒 → 得到约 30 帧 → 约 1 秒播放时间
真实采集 1800 秒 → 得到约 1800 帧 → 约 60 秒播放时间
```

这是无丢帧、无额外补帧的示例，不是宣布当前 recorder 的 `split_time=60` 在缩时下必定等于真实 1800 秒。缩时分段还涉及 `fSpeed`、库内时序换算和手动分段策略，必须将文件播放时长与真实采集时间分别验证。

**普通录像的 60 秒检查方法不能不加区分地套在缩时上。**“文件显示 30 fps”也不能证明每真实秒采集 30 帧。

## 14. 怎样实际验证“写卡正常”和“分段精准”？

### 14.1 板端只读查看

以下在摄像机串口 shell 执行，不是在编译服务器执行；先用 `ls` 确认节点存在：

```sh
cat /proc/cmdline
cat /proc/mounts
ls /proc/umap

for name in vb vi vpss venc; do
    if [ -r "/proc/umap/$name" ]; then
        printf '\n--- %s ---\n' "$name"
        cat "/proc/umap/$name"
    fi
done

if [ -r /proc/media-mem ]; then
    cat /proc/media-mem
fi
```

观察点：VB 块是否紧张、实际通道与帧率、VENC 输入／输出是否持续增长、ringbuf 所在分区、卡实际挂载格式、错误发生前后的变化。不同 SDK 的 proc 字段有区别，不硬套别的机型列号。

### 14.2 最小验证矩阵

| 场景 | 连续采集要求 | 重点 |
|---|---|---|
| 普通前摄 4K，不接 AHD | 每个 1/2/3 分钟档至少连续 3 段 | 首段与后续段分开统计 |
| 普通前后双录 | 每档至少连续 3 段；长期再验证几十段 | 前后文件名、首尾 PTS、边界连续性 |
| 缩时双录 | 同时记录真实经过时间和播放时长 | 每真实秒采集数，不能只看 avg_frame_rate |
| 停止录像／ACC 切换 | 记录最后短段 | 主动停止的短文件不能直接算自动切片错误 |
| 卡接近满 | 观察正常循环删除和分段 | 删旧文件耗时、慢写、ringbuf 积压 |

不要为了验证而在录像中执行 `dd` 写卡压测、反复 `drop_caches` 或强制卸载；这些会改变负载甚至破坏测试条件。本文没有执行这些操作。

### 14.3 在电脑上用 ffprobe 检查文件，而不是只看文件名

对已经安全复制到电脑的录像使用以下只读命令；文件路径换成实际路径：

```sh
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,width,height,r_frame_rate,avg_frame_rate,time_base \
  -show_entries format=start_time,duration,size \
  -of json "2026_09_10_120000_00.TS"
```

继续查看逐帧或逐包时间：

```sh
ffprobe -v error -select_streams v:0 \
  -show_packets \
  -show_entries packet=pts_time,dts_time,duration_time,size,flags \
  -of csv=p=0 "2026_09_10_120000_00.TS"

ffprobe -v error -select_streams v:0 \
  -show_frames \
  -show_entries frame=best_effort_timestamp_time,pkt_duration_time,key_frame,pict_type \
  -of csv=p=0 "2026_09_10_120000_00.TS"
```

判断方法：

1. 分别记录首个有效视频时间戳和最后一个有效视频时间戳。
2. 最后帧的结束时间还要加该帧持续时间；只做“末帧 PTS 减首帧 PTS”通常会少一帧时长。
3. 检查下段是否具备可解码起点，以及两段交界处是否缺帧／重复。某些封装会重置或变换时间戳，不能在未确认时基连续的情况下直接相减。
4. 容器 `format.duration` 可用于初筛，不能替代逐包／逐帧校验。音视频尾部不同步也会影响容器时长。
5. 同时查日志中的 `splitType/timelen`、文件开始／结束、`zxd-----Split`、ringbuf 和写卡错误。

建议记录如下表，而不是只写“能播放”：

| 段号 | 前/后 | 设置时长 | 文件播放时长 | 首帧时间 | 末帧结束时间 | 手动 Split 日志 | 画面/解码异常 |
|---|---|---|---|---|---|---|---|
| 1 | 前 | 60 s | 实测 | 实测 | 实测 | 有/无 | 有/无 |
| 1 | 后 | 60 s | 实测 | 实测 | 实测 | 有/无 | 有/无 |

## 15. 最后用一句话记住各模块职责

| 模块 | 最核心的职责 |
|---|---|
| VB | 管理媒体图像缓冲池与块的使用 |
| DMA／媒体硬件 | 按驱动配置读写、处理内存数据，不理解文件名和分钟数 |
| VI/ISP/VPSS | 产生和处理图像 |
| VENC | 将图像编码成压缩码流 |
| 取流线程 | 获取编码输出，调用消费者，归还编码输出 |
| Recorder ringbuf | 缓冲编码帧，解耦生产与录像消费 |
| Recorder 分段逻辑 | 根据时间、媒体边界和手动请求安排文件切换 |
| TS muxer／文件格式库 | 组织轨道、封装、文件 IO |
| 文件系统／MMC／SD 卡 | 将文件字节映射为块传输并保存 |
| DTCF 文件名逻辑 | 决定年月日路径／名字；当前还间接触发命名时间修正分段 |

最重要的三个结论：

1. **VB 图像内存、VENC 编码缓存、Recorder ringbuf、文件写缓存是不同层次。**
2. **1／2／3 分钟在产品参数与 recorder 层控制，不由 DMA 或 SD 卡自行计时。**
3. **精确文件时长不等于文件名差值，也不等于打印“结束录像”的日志时间；当前还需考虑明确存在的前后路手动分段修正代码。**

## 17. APP 预览到底用 TCP 还是 UDP？先给出工程结论

**当前代码同时支持 RTP/UDP 和 RTP/TCP interleaved。RTSP 控制连接使用 TCP；预览媒体最终选哪一种，由 APP 的 SETUP 请求及设备响应中的 Transport 字段确定。**

本次没有抓取手机实际预览会话，不能把“源码支持 UDP”写成“你的 APP 当前一定用 UDP”。也不能看到 TCP 554 连接，就断言视频也走 TCP：即使视频走 UDP，RTSP 控制连接仍然存在。

| 对象 | 本工程中的作用 | 已确认的事实 |
|---|---|---|
| RTSP | 建立、配置、开始和结束预览会话 | TCP 监听端口 554 |
| RTP/UDP | 将编码数据分包后发送给手机 | 支持；使用 SETUP 提供的 client_port |
| RTP/TCP interleaved | 将 RTP 数据嵌入 RTSP 所在的 TCP 字节流 | 支持；复用已建立的 RTSP socket |
| RTCP | 媒体会话的控制／统计通道 | SETUP 中有对应端口或 interleaved 通道；不是视频正文 |
| WiFi | 设备与手机之间的无线网络承载 | 不直接决定上层选择 TCP 还是 UDP |
| APP CGI | 查询设备、修改设置、切换前后预览等 | 不要和 RTSP 的视频传输通道混为一谈 |

### 17.1 监听端口和包大小从哪里来

位置：[ss_liveserver.c][livecore]，`LIVESVR_InitRtspServer()`。

源码节选＋中文注释：

当前产品层的 `PDT_STATEMNG_LIVESVR_MAX_CONNECT_CNT` 为 **1**，在 [状态定义头文件][livestate] 中。库接口允许更大的数值范围，不代表产品当前允许那么多手机同时预览；`listen()` 的等待队列长度也不是允许预览客户端数。

### 17.2 决定 TCP／UDP 的真正分支

位置：[ot_rtspserver_session.c][rtspsession]，`RTSPSVR_GetMediaSessionInfo()`。

源码节选＋注释，省略可选 VTP 分支及错误处理：

## 19. TCP 三次握手在什么地方做？

### 19.1 源码为什么找不到手工发送 SYN 的代码

位置：[ot_network_listener.c][netlistener]，`NETWORK_LISTENER_CreateSocket()` 及连接接收逻辑。

源码关键语句节选＋注释，省略 socket 选项和错误处理：

```c
// 建立 TCP 监听 socket，不是 UDP。
s32ListenSockfd = socket(PF_INET, SOCK_STREAM, 0);

// svrAddr 中：AF_INET、INADDR_ANY、htons(s32ListenPort)。
// liveserver 传入的 s32ListenPort 是 554。
bind(s32ListenSockfd, (struct sockaddr *)&svrAddr, sizeof(struct sockaddr));
listen(s32ListenSockfd, DEFAULT_MAX_FDNUM);

// 后续接收连接处调用 accept()，获取这个客户端的连接 socket。
// 监听 socket 保留，已连接 socket 用于收发 RTSP 和可选的交织媒体。
```

握手由 **Linux TCP 协议栈**完成，应用通过 `socket/bind/listen/accept` 使用它。`accept()` 不等于应用发送“第三次握手”；它取出内核已经可供应用接受的连接。

### 19.2 三次握手的直观过程

教学示意；手机 IP、端口、序号仅举例：

```text
手机 192.168.0.100:40000                    HC112_B 192.168.0.1:554
        │                                               │
        │── SYN，seq=x ─────────────────────────────────→│  第一次
        │←─ SYN+ACK，seq=y，ack=x+1 ──────────────────────│  第二次
        │── ACK，seq=x+1，ack=y+1 ───────────────────────→│  第三次
        │                                               │
        │        TCP 已建立，随后交换 RTSP 文本           │
        │── OPTIONS／DESCRIBE／SETUP／PLAY … ────────────→│
```

SYN 消耗一个序号，所以确认值是初始序号加一；双方分别确认彼此的发送方向和序号起点。协议依据：[RFC 9293 §3.5](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5)。

**WiFi 连接认证、TCP 三次握手、RTSP SETUP 是三个不同层面的动作。** WiFi 已连接不等于预览已经建立；TCP 已连接也不等于 APP 已发送 PLAY。

### 19.3 视频也走 TCP 时，有没有再握手一次

本工程使用的是 **RTP over RTSP TCP interleaved**。对应源码 [RTSPSVR_GetTcpReceiveChannel()][rtspsession]：

```c
pMediaSession->pRtpSession->enMediaTransMode = RTP_TRANS_TCP_ITLV;
pMediaSession->pRtpSession->enPackType = PACK_TYPE_RTSP_ITLV;
pMediaSession->pRtpSession->s32RTPSendSock = pSess->s32SessSock;
// 复用 RTSP 已有连接，不是给 RTP 另连一个 TCP 端口。
```

APP 请求中的关键字段示例：

```text
Transport: RTP/AVP/TCP;unicast;interleaved=0-1
```

`0-1` 是这条 TCP 字节流内的 RTP／RTCP **逻辑通道编号**，不是手机或设备的端口 0、端口 1。

交织媒体块格式示意：

```text
+----------+----------+------------------+------------------------+
| '$' 1 B  | 通道 1 B | 长度 2 B，网络序 | RTP 包或 RTCP 包       |
+----------+----------+------------------+------------------------+
                  前面总计 4 字节
```

这是 RTSP 1.0 的嵌入二进制数据机制：[RFC 2326 §10.12](https://www.rfc-editor.org/rfc/rfc2326.html#section-10.12)。工程也有其他 TCP 传输枚举，但“枚举存在”不等于已实现；这里确认的路径是 `TCP_ITLV`，不是所有名为 TCP 的模式都可用。

## 20. 如果媒体走 UDP，没有三次握手又怎么“连接”？

### 20.1 UDP 无握手，RTSP 负责协商目的地址和端口

示例流程，端口 50000/50001、60000/60001 为教学示例，不是工程固定配置：

```text
1. 手机先与设备建立 TCP 554 的 RTSP 控制连接。
2. 手机准备 UDP 接收端口，例如 RTP=50000、RTCP=50001。
3. 手机 SETUP 请求：
   Transport: RTP/AVP;unicast;client_port=50000-50001
4. 设备响应协商结果，例如：
   Transport: RTP/AVP;unicast;client_port=50000-50001;
              server_port=60000-60001;ssrc=…;mode="PLAY"
5. 手机发 PLAY。
6. 设备向“手机 IP:50000”发送 RTP 视频；RTCP 使用协商的控制通道。
```

它建立了应用层的“播放会话”，但没有给 UDP 增加 TCP 那样的 SYN/ACK 握手。`client_port` 是手机的接收端口，`server_port` 是设备对应端口，不要反过来。

### 20.2 对应源码

位置：[ot_rtp_session.c][rtpsession]，`RTP_SessionStartUdp()`，及 [ot_network_common.c][netcommon]。

源码关键语句节选＋注释：

```c
// 在设备端创建并绑定本地 UDP socket。
TD_S32 s32TempSock = SS_NETWORK_UdpOpenSocket(pSess->s32SvrRTPPort);

// SS_NETWORK_UdpOpenSocket() 内使用：
// socket(AF_INET, SOCK_DGRAM, 0)
// bind(... INADDR_ANY + 本地 UDP 端口 ...)

// 原函数检查 socket 创建成功后，保存 socket 并构造目的地址。
pSess->s32RTPSendSock = s32TempSock;
SS_NETWORK_GetPeerSockAddr(pSess->aszClientIP, pSess->s32CliRTPPort,
    &(pSess->stCliAddr));
// stCliAddr 保存 sendto() 要发往的手机目的地址。
```

位置：[ot_rtp_packetize.c][rtppacket]，`RTP_SendBuffToSock()`，以下为原分支加注释：

```c
if (pPeerSockAddr == NULL) {
    // TCP：socket 已经关联对端，直接向连接发送字节。
    s32Size = send(s32WritSock, pBufferPos, *u32RemSize, MSG_DONTWAIT);
} else {
    // UDP：本次发送携带手机目的 IP/端口，不需要先做三次握手。
    s32Size = sendto(s32WritSock, pBufferPos, *u32RemSize, 0,
        (struct sockaddr*)pPeerSockAddr, sizeof(struct sockaddr));
}
```

这里的 `send/sendto` 返回成功，表示数据被本机发送路径接受，**不是手机已经完成解码的确认**。UDP 本身不保证端到端交付；TCP 提供有序可靠字节流，但也不保证每一帧都及时显示。

### 20.3 两种方式对预览卡顿有什么不同

| 情况 | RTP/UDP | RTP/TCP interleaved |
|---|---|---|
| 无线偶发丢包 | RTP 数据可能缺失，影响当前帧或后续依赖帧 | TCP 通常重传，缺口前后的字节交付可能等待 |
| 网络持续小于编码输出速率 | 队列满、丢包、图像不完整 | 排队积压、延迟增长、发送阻塞或超时 |
| 视频包的边界 | 每个 UDP 数据报有边界 | TCP 没有应用消息边界，APP 按交织头重新拆包 |
| 是否天然保证无卡顿 | 否 | 否 |

WiFi MAC 层也可能有确认、重试，它与 TCP 的端到端重传不是同一件事。“UDP 无可靠交付保证”不等于“无线芯片绝不重试”。本表说明一般机制，不是在判定当前设备存在某一种丢包故障。

### 21.3 真正发送视频的数据路径

```text
用户态 main_app／RTSP 服务
  H.264 数据 → RTP 分包 → send() 或 sendto()
                  ↓ 系统调用
Linux 内核
  TCP 或 UDP → IPv4 → 路由／邻居解析 → wlan0 发送队列
                  ↓
ATBM6062 WiFi 驱动及 USB 主机传输
                  ↓
WiFi 芯片 MAC／PHY：无线帧、适用的加密、重试、调制发送
                  ↓ 无线信道
手机 WiFi 芯片／驱动 → IP → UDP 或 TCP
                  ↓
APP：RTSP交织解包（如果走TCP）→ RTP重组 → H.264解码 → 显示
```

这是分层示意，不是断言每层都复制一次，也不是声称已核实芯片内部 DMA 的每个描述符。USB／无线底层传输由驱动和硬件处理，业务层没有“每一张图由自己指定 WiFi DMA 地址”的调用。

**VB DMA 与 WiFi DMA／USB 传输不是一条直接贯通的通道。** VB 承载媒体图像，VENC 先压缩成码流，网络库再分包；各硬件环节即使都使用 DMA，也有不同的缓冲、所有权和完成条件。

## 22. “传输大小”到底由谁定？必须分成六个数

| 层次 | 本文中的例子 | 决定因素 |
|---|---|---|
| 每秒编码数据量 | 预览 H.264 配置 2048 Kbps | VENC 码率控制、场景复杂度 |
| 每帧／每个 NAL 大小 | 帧大小不是固定值 | 帧类型、纹理、运动、编码器 |
| 编码输出缓冲 | 预览模板 bufsize=294912 | VENC 配置；不是发包长度 |
| 网络媒体缓存 | mbufferSize=2000000 | liveserver 添加流时传入 |
| RTP 分包预算 | s32PacketLen=1500 | RTSP 配置及分包函数 |
| IP／链路传输单元 | MTU、TCP MSS、WiFi 聚合与速率 | 网络接口、协商、内核、驱动、信道 |

### 22.1 2048 Kbps 怎样换算为字节、帧平均大小

按十进制网络码率举例计算，不包含音频、RTP、IP、WiFi 等额外开销：

```text
2048 Kbit/s × 1000 = 2,048,000 bit/s
2,048,000 ÷ 8     =   256,000 byte/s
256,000 ÷ 1024    =       250 KiB/s

如果实际每秒编码 25 帧：
256,000 ÷ 25      =    10,240 byte/帧（平均约 10 KiB）
```

CBR 也不是“每帧都恰好 10,240 字节”。I 帧通常明显更大，P 帧大小也随画面变化；实际瞬时网络负载有波动。

如果用 2,000,000 字节缓存除以这个平均视频速率，得到约 **7.81 秒**的理论视频容量。这只是容量除以速率，忽略音频、元数据、缓存策略等因素；**不是固定预览延时，不是该库承诺缓存 7.81 秒，也不是录像 recbuffer_time**。

前录 4K 码率改成 20480 Kbps，并不自动使 VENC 5 的预览码率也变成 20480；二者配置位置不同。

### 22.2 一帧为什么会拆成多个 RTP 包

一帧 H.264 数据可能包含多个 NAL 单元；NAL 太大时再做 FU-A 分片。APP 先重组分片，再送解码器，不能把收到的任意一个 UDP 包直接当作一整帧。FU-A 的起止标识用于分片重组，协议说明见 [RFC 6184 §5.8](https://www.rfc-editor.org/rfc/rfc6184.html#section-5.8)。

位置：[ot_rtp_session.c][rtpsession]，`RTP_MultipleSendH264RtpData()`。

源码节选＋注释，省略边界处理及拷贝段；以下关注长度预算，不是完整可复用分包代码：

```c
TD_U32 packPayloadLen = (TD_U32)packetLen;
TD_U32 headOffset = 2; // H.264 FU-A 的附加头

// 当剩余数据放不下一个包时：
sendLen = packPayloadLen - sizeof(RTP_HDR_S) - headOffset;
// 大包中真正可放的 NAL 分片数据，要扣掉 RTP 头和 FU-A 头。

TD_U32 rtpSendLen = sendLen + sizeof(RTP_HDR_S) + headOffset;

// 原函数在这里构造 FU-A 头并 memcpy_s() 分片数据。
rtpHdr->marker = marker;
SS_RTP_Packet(tmpPackBuf, *rtpHdr);
rtpHdr->seqno++; // 每个 RTP 包都有自己的序号，不是每帧才加一次

ret = SS_Send_RTPPacket(session, session->s32RTPSendSock,
    tmpPackBuf, rtpSendLen, &session->stCliAddr);
```

平均约 10 KiB 的一帧，常常需要多个接近 1.5 KB 的 RTP 包；约 7 包只是粗略量级，实际需考虑 NAL 划分和各类头部，I 帧可能更多。

### 22.3 关键发现：这里的 1500 不能直接当作 IP MTU 1500

从 liveserver → RTSP 上下文 → stream session → 上面的 UDP 分包函数，`s32PacketLen` 作为打包长度传下去。分包函数扣的是 **RTP 头和 FU-A 头**，此处没有再扣 IPv4 和 UDP 头。

根据 [RTP_HDR_S 定义][rtpheader]，无扩展、无 CSRC 时 RTP 基本头为 12 字节。按 IPv4 无选项、UDP 普通头、未加其他封装计算：

```text
本工程 packetLen = 1500 时，一个填满的 H.264 FU-A RTP 包：
NAL 分片数据 = 1500 - 12(RTP) - 2(FU-A) = 1486 B
UDP 数据长度 = 1500 B
IP 包总长度  = 20(IPv4) + 8(UDP) + 1500 = 1528 B

如果路径 MTU 实际为 1500，想避免这种 IPv4 分片：
UDP 数据长度上限 = 1500 - 20 - 8 = 1472 B
FU-A 分片数据上限 = 1472 - 12 - 2 = 1458 B
```

因此，若实际使用 UDP、确实发出填满的这种包、路径 MTU 为 1500，就需要检查 IP 分片或超长报文错误。Linux UDP 在路径 MTU 发现启用时可能返回 `EMSGSIZE`，其他配置下可能发生分片，不能笼统写成“一定自动分片而且完全没影响”。依据：[Linux udp(7)](https://man7.org/linux/man-pages/man7/udp.7.html)。

**这是一项静态分析发现的条件性风险，不是已经实测到的当前 APP 故障，也没有据此修改工程。** TCP 模式下不能照搬上述 UDP 计算认定失败；它交给内核的是字节流。

### 22.4 TCP 模式下，一次 send() 不等于一个网包

```text
应用交给 TCP：[$头+RTP包A][$头+RTP包B][$头+RTP包C]……

内核按 MSS、窗口、拥塞和发送条件组织 TCP 段：
[一部分A] [A尾部+B的一部分] [B尾部+C……]

APP 按字节流读取，再根据 $ 头中的长度恢复媒体块边界。
```

MTU 1500、IPv4 和 TCP 都没有选项时，基础计算的 TCP 数据空间为 `1500 - 20 - 20 = 1460 B`；选项、协商等可能使实际段内载荷不同。TCP 的分段和流量控制由内核实现，而不是把 `LIVESVR_RTSP_PACKET_LEN` 当作硬件每次发送尺寸。[RFC 9293 §3.7](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7)

再到 WiFi 层，还可能存在无线聚合、重试及加密开销，所以 **一个编码帧 ≠ 一个 RTP 包 ≠ 一次 send ≠ 一个 IP 包 ≠ 一个无线帧**。

## 23. 不改代码，怎样确认手机实际走哪条路径

本节是提供给你操作的检查方法，本次文档整理没有占用串口、没有启动抓包，也没有断开任何正在录像的设备。

### 23.1 先看接口、驱动和 MTU

以下在摄像机 Linux shell 执行，不是在编译服务器执行：

```sh
# 只读：确认接口/IP。实际接口不是 wlan0 时替换名称。
ifconfig wlan0
cat /sys/class/net/wlan0/mtu

# 只读：确认加载的 WiFi 模块。
lsmod

# TCP 554 存在只能证明控制连接，不能证明视频也使用 TCP。
netstat -nt
cat /proc/net/tcp
cat /proc/net/udp
```

固件未提供 `netstat` 时看 `/proc`；其中端口 554 的十六进制是 `022A`，TCP 状态 `0A` 是 LISTEN、`01` 是 ESTABLISHED。UDP 表里有 socket，也不足以单独证明它正在传当前预览视频。

### 23.2 最有决定性的证据：SETUP 的 Transport 请求和响应

如果板端已经有 tcpdump，可在准备打开 APP 预览时临时运行下面的限包抓取。它不改源码，但会消耗少量 CPU，测试时再使用：

```sh
# 先确认是否已安装；没有则不要为了本次学习临时改固件。
command -v tcpdump

# 限 40 个包；看 TCP 554 的 RTSP 请求与响应。
# 没有达到包数时可 Ctrl+C 停止。
tcpdump -i wlan0 -nn -s 0 -A -c 40 'tcp port 554'
```

抓取内容可能有设备标识或认证字段。发日志给别人前，只保留需要的 SETUP／Transport 行，并遮盖 `Authorization`、密码等信息。TCP 拆包时终端文本可能不完整，需要能重组 TCP 流的分析工具确认；没有捕获到 SETUP 不能据此判断协议。

| 请求和成功响应中的关键字段 | 可以确认什么 |
|---|---|
| `RTP/AVP/TCP`、`interleaved=...` | RTP/RTCP 复用 TCP 连接 |
| `RTP/AVP` 或 `RTP/AVP/UDP`、`client_port`、`server_port` | 协商 UDP 媒体端口 |
| 仅看到 OPTIONS／DESCRIBE | 还不能确认最终媒体传输方式 |

普通电脑连接同一个热点后，通常不能仅靠普通模式抓包直接看到另一台手机的全部单播流量；优先设备端抓取或受控网络分析，不要把“电脑没抓到视频包”当成设备没有发送。

### 23.3 怎样看卡顿发生在哪一层

建议按以下顺序逐层对照，而不是看到卡顿就先调大录像 ringbuf：

1. 看 VENC 5 是否持续产生帧，实际帧率、分辨率、码率是否符合当前模式。
2. 看 liveserver 写帧返回值，是否有 mbuffer 满或 WriteVencFrame 错误。
3. 看 socket 发送是否超时，UDP 是否出现超长包／分片，TCP 是否反复重传或接收窗口过小。
4. 看 WiFi 信号、干扰、吞吐、丢包／重试及 USB 驱动异常。
5. 看手机端 RTP 重组、解码、渲染是否跟得上。

`ringbuf_handle_0/1` 的录像库错误与 APP 网络 mbuffer 错误不是同一个层级。可能有共同的 CPU／内存／带宽压力，但不能仅凭名字里都有“buffer”，就用同一个参数处理。

## 25. 声音怎样采集，怎样与图像一起进入录像文件？

本节追加于 2026-09-10，依据 HC112_B 当前工作区的 INI、媒体层、MAPI/MPI 适配层和录像封装接口。下面的源码摘录做了局部精简，中文注释仅用于本文讲解。数值是源码默认配置；板端最终参数还可能受 Flash 当前参数、录音开关和录像类型影响。

录像里的声音来自音频输入链路。麦克风信号经过音频前端和采样，形成 PCM 样本，AI/ACAP 将样本组织成帧；AENC 把 PCM 编码成 AAC，录像管理再把带时间戳的音频帧、视频帧交给同一个录像任务。文件中保存各自的轨道与时间信息，播放器据此安排声音输出和画面显示。

两条链路可以这样看：

```text
声音：
麦克风/音频前端 → ACODEC、AI/ACAP → PCM帧 → AENC0 → AAC帧+时间戳
                                                               │
                                  RECMNG_ProcAencData() ─────────┤
                                                               ▼
                                                          recorder任务
                                                               │
                                  RECMNG_ProcVencData() ─────────┤
                                                               │
画面：                                                         │
GC4653/AHD → VI/ISP → VPSS → VENC0或VENC3 → 视频码流帧+PTS ────────┘
                                                               │
                                                               ▼
                                           音视频轨道 → TS封装 → 文件系统 → SD卡
```

这里的 AENC 是音频编码，VENC 是视频编码。ACAP 是项目对音频采集的封装，底层进入 AI（Audio Input）。提示音播放使用 ADEC/AO：从提示音文件解码后输出到扬声器，是另一条方向相反的链路。

因此，“听得到开机提示音”只能说明对应播放路径在当时工作，不能据此确认录像中的麦克风音轨正常。扬声器提示音可能通过空气被麦克风再次录入，但这也不等于把提示音文件直接混进录像音轨。

### 25.1 当前默认采集参数

来源：[媒体公共 INI][av-common-ini] 的 `[acapture.0]`、`[acapture.0.chnl.0]` 和 `[aenc.0.aac]`。

| 参数 | 当前 INI 值 | 实际含义 |
|---|---:|---|
| ACAP 设备/通道 | 0 / 0 | 启用的采集输入 |
| 采样率 | 16000 Hz | 每个声道每秒 16000 个 PCM 样本 |
| 位宽 | 16 bit | 每个 PCM 样本 2 字节 |
| 声道 | mono | 单声道 |
| AAC 分组样本数 | 1024 | 每个编码输入帧的样本数量 |
| 重采样目标 | 16000 Hz | 配置的目标采样率；与输入相同不代表必然执行重采样 |
| 输入增益 | 40 | 采集增益参数，不能直接解释成“40%音量” |
| 通道 VQE 开关 | 1 | 媒体层请求启用录音语音增强，成功与否还要看调用结果 |
| AAC 类型 | AAC-LC | 当前默认非 MP3 分支 |
| AAC 目标码率 | 48000 bit/s | 约 48 kbit/s |
| AAC 传输格式配置 | ADTS | AAC 编码输出格式配置 |

`product_iniparam_mediacomm.c` 在 `CONFIG_AUDIO_MP3_SUPPORT` 分支读取 MP3 参数，否则读取 AAC-LC 参数。不能因为同一份 INI 里同时有 AAC 和 MP3 小节，就认为同时生成两种音频。

`mixer_mic_mode = 2` 的 INI 注释标为 IN_D。代码能确认它被交给 Codec 输入选择接口；仅凭这个字段不能反推出板上麦克风的具体接线或器件型号，硬件细节还需结合原理图。

### 25.2 把采样率换算成“多久出来一帧声音”

按当前 16000 Hz、单声道、16 位 PCM 配置：

```text
每秒PCM字节数 = 16000 × 1 × 16 ÷ 8
              = 32000 B/s

每组PCM字节数 = 1024 × 1 × 2
              = 2048 B

一组1024样本所代表的时间 = 1024 ÷ 16000
                         = 0.064 s
                         = 64 ms

每秒音频组数 = 16000 ÷ 1024
             = 15.625 组/s
```

15.625 是长期平均速率，不代表某一秒一定只出现整数个固定音频包。包会跨越人为划分的整秒边界，线程调度也可能让多个已就绪包集中送到回调。

按 AAC 目标 48000 bit/s 估算，64 ms 对应的平均编码量约为：

```text
48000 ÷ 8 × 0.064 = 384 B
```

这是平均量级。编码帧实际长度、ADTS 头以及 TS/PES 封装开销会使具体文件大小不同。2048 B 是一组原始 PCM 的大小，384 B 是上述码率下的平均编码量，二者属于不同阶段。

## 26. 声音采集与编码的实际函数链

### 26.1 初始化 ACAP，启动 AI 设备和通道

[media_audio.c][av-media-audio] 中 `MEDIA_InitAcap()` 遍历启用的音频输入，大致执行：

```c
SS_MAPI_ACAP_Init(acapHdl, &acapAttr);  // 提交采样率、位宽、声道等属性
SS_MAPI_ACAP_Start(acapHdl, chnHdl);   // 开启采集设备/通道
SS_MAPI_ACAP_EnableRecordVqe(...);     // 配置要求时请求启用VQE
SS_MAPI_ACAP_SetVolume(acapHdl, audioGain); // 设置采集增益
```

再往下，[mapi_acap_adapt.c][av-acap-adapt] 使用：

```c
ss_mpi_ai_set_pub_attr(acapHdl, &aioAttr);
ss_mpi_ai_enable(acapHdl);
ss_mpi_ai_enable_chn(acapHdl, acapChnHdl);
```

Codec 的配置在 [mapi_acodec_adapt.c][av-codec]：打开 `/dev/acodec`，通过 ioctl 设置采样率、麦克风输入选择和输入音量等。代码中可以看到 `OT_ACODEC_SET_I2S1_FS`、`OT_ACODEC_SET_MIXER_MIC` 和 `OT_ACODEC_SET_INPUT_VOLUME`。

从硬件原理上，采样模块按采样时钟连续得到样本，通过底层缓冲和传输机制交给 AI。上层应用通过上述接口配置、启动和取帧，不会每隔 62.5 µs 手动读一次麦克风。具体 ADC 电路、DMA 描述符、缓冲中断和最初打时间戳的位置，不能仅凭这些适配层函数还原；本文确认到 MPI 和 Codec 接口边界。

### 26.2 把 AI0/通道0 绑定到 AENC0

`MEDIA_InitAenc()` 注册编码器并调用 `SS_MAPI_AENC_Init()`。开始使用音频源时，`MEDIA_StartAencChn()` 执行绑定和启动：

```c
SS_MAPI_AENC_BindACap(acapHdl, acapChnHdl, aencHdl);
SS_MAPI_AENC_Start(aencHdl);
```

[mapi_aenc_adapt.c][av-aenc-adapt] 中绑定的实质是：

```c
srcChn.mod_id = OT_ID_AI;
srcChn.dev_id = acapHdl;
srcChn.chn_id = acapChnHdl;

destChn.mod_id = OT_ID_AENC;
destChn.dev_id = 0;
destChn.chn_id = aencHdl;

ss_mpi_sys_bind(&srcChn, &destChn);
```

绑定后，普通录像音频由底层 AI→AENC 链路传送。虽然工程也提供 `ss_mpi_ai_get_frame()` 和手工送音频帧接口，但不能把那些接口都画成当前普通录像中必须逐个经过的步骤。

### 26.3 AENC 取流线程如何工作

[mapi_aenc.c][av-aenc-core] 的 `ProcAStreamThread()`：

1. 检查 AENC 是否处于 started 状态。
2. 取得 AENC 文件描述符。
3. 使用 `select()` 等待码流可读。
4. 有数据且存在回调时，调用 `MAPI_AENC_GetAData()`。
5. 进入 `MAPI_AENC_GetAStream()` 获取码流、通知回调，然后归还码流。

[single 进程取流实现][av-aenc-os] 的顺序为：

```text
MAPI_ADAPT_AENC_GetStream
    → MAPI_AENC_ProcAStream（逐个调用已注册消费者）
    → MAPI_ADAPT_AENC_ReleaseStream
```

释放码流很重要：回调收到的是底层编码缓冲中的数据描述。消费者如果要延后处理，必须遵守相应接口的数据生命周期，不能长期保存这个地址并假设内容永远不变。

## 27. 两路录像为什么都有同一份声音？

[录像工作模式 INI][av-record-ini] 的前后路均配置：

```ini
; 前路：VENC0 + AENC0
[normal.0.filenum.0.fileattr]
venc_hdl0 = "0"
aenccnt   = "1"
aenc_hdl0 = "0"

; 后路：VENC3 + AENC0
[normal.1.filenum.0.fileattr]
venc_hdl0 = "3"
aenccnt   = "1"
aenc_hdl0 = "0"
```

这表示前后文件都选择主机 AENC0 的声音来源，并不是后摄另带一个独立麦克风。

`RECMNG_StartAudioSrc()` 为各录像轨道注册 `RECMNG_ProcAencData()`，各回调通过自己的 `privateData` 找到相应 recorder 对象。[MAPI 音频回调分发][av-aenc-os] 遍历已注册回调，所以一份编码音频可以送给多个消费者。

`MEDIA_StartAencChn()` 还有 `aencStartCnt[]` 引用计数与互斥锁：计数从 0 开始时才执行底层绑定和启动，后续使用者增加计数；停止时按计数管理底层停用。这是共享音频输入的资源管理，和按照时间戳播放的音视频同步是两件事。

前后文件不保证第一帧或最后一帧声音完全相同。两个录像任务的开始、停止、分段、缓冲状态可能不同，尽管它们的音频来自同一个 AENC0。

## 28. 音视频同步的关键：保留媒体时间戳

### 28.1 图像和声音各自从哪里拿时间戳？

视频路径在 [mapi_venc_adapt.c][av-venc-adapt] 中把 MPI 包的 PTS 传到 MAPI：

```c
outVStream->dataPack[i].timeStamp = stream->pack[i].pts;
```

随后 [recordmng_source.c][av-rec-source] 的视频回调执行：

```c
// 当前实现选择本次返回码流的最后一个pack的时间戳。
frameData.u64TimeStamp =
    vencData->dataPack[vencData->packCount - 1].timeStamp;

SS_REC_WriteData(*recmngTrackSrc->recObj,
                &recmngTrackSrc->trackSrc, &frameData);
```

音频路径在 [mapi_aenc_adapt.c][av-aenc-adapt] 中：

```c
ss_mpi_aenc_get_stream(aencHdl, &audioStream, TD_FALSE);
stream->timeStamp = audioStream.time_stamp;
```

随后 `RECMNG_ProcAencData()` 执行：

```c
frameData.u32SliceCnt = RECMNG_AUDIO_SLICE_COUNT;
frameData.u64TimeStamp = audioData->timeStamp;
frameData.apu8SliceAddr[0] = audioData->stream;
frameData.au32SliceLen[0] = audioData->len;
frameData.bKeyFrameFlag = TD_FALSE;

SS_REC_WriteData(*recmngTrackSrc->recObj,
                &recmngTrackSrc->trackSrc, &frameData);
```

两种帧都通过 `OT_REC_FRAME_DATA_S.u64TimeStamp` 进入录像库，轨道类型区分音频和视频。回调没有用“这一刻线程被调度到的时间”替换原来的媒体时间戳。

### 28.2 为什么不能用回调到达时间来同步？

假设同一真实时刻发生“手掌合上并发出响声”。图像要经过曝光、ISP、VPSS 和视频编码；声音要收集足够的 PCM 样本，再经过音频处理与编码。两边的数据到达应用回调的时间通常不同。

若用回调执行时刻作为播放时间，线程调度、编码延迟和缓存抖动都会被误当作事件实际发生时间。保留采集/媒体链路产生的时间戳，才有可能把经历不同处理延迟的数据放回可比较的时间轴。

这里需要区分证据：当前源码已确认“应用透传底层时间戳”的路径；SDK 也提供 `ss_mpi_sys_get_cur_pts()`、`ss_mpi_sys_init_pts_base()`、`ss_mpi_sys_sync_pts()`。但这些接口的存在本身不能证明具体音视频模块的硬件打点时刻或延迟补偿算法。共同时间基准是正确同步的前提，最初如何赋值仍需 SDK 实现/文档或板端测量确认。

### 28.3 25 fps 画面和 64 ms 声音怎样对应？

下面用相对时间解释正常速度播放，假设两轨已经换算到相同起点，暂不考虑启动偏移和编码器延迟：

```text
视频25fps：
V0:   0 ms
V1:  40 ms
V2:  80 ms
V3: 120 ms
V4: 160 ms

音频16kHz，每组1024样本：
A0: 代表约   0～ 64 ms 的声音
A1: 代表约  64～128 ms 的声音
A2: 代表约 128～192 ms 的声音
```

播放到 80 ms 时，画面处于 V2 对应时刻，声音已经进行到 A1 内部：

```text
A1内部已播放时间 = 80 - 64 = 16 ms
对应样本数       = 16000 × 0.016 = 256 个
```

播放器解码一个音频包后会连续输出样本，视频按自己的显示时刻更新。一个音频包覆盖不止一帧视频是正常的，音频包数和视频帧数不需要相等。上述表是解释性例子，不是实测 PTS，也不是对首个 PCM 样本打点位置的承诺。

### 28.4 音视频同步和“同时写SD卡”有什么关系？

音视频包可以先进入不同缓存，再被录像库组织、交错封装。SD 卡写入发生在其后，写入调用的时间不等于媒体采集时间，也不决定播放器何时发出声音。

只要数据及时间信息正确保存，SD 写入有短暂抖动并不必然造成播放不同步。不过，持续写入不及时会耗尽缓存并造成丢帧或写入失败，此时保留时间戳也无法补回已经丢失的画面和声音。

## 29. Recorder 与 TS 封装分别承担什么？

[ss_recordmng.c][av-rec-core] 为录像流建立视频轨道和音频轨道。`RECMNG_GetAudioInfo()` 提供音频类型、声道数、每帧样本数、采样位宽和采样率等信息。

Recorder 收到音视频帧后负责录像任务、缓存和向封装器输出帧。当前工程的关键 recorder 调度和 TS 封装实现主要在库中，本节没有逐条反汇编这些库，因此不能声称已确认“首帧必定丢弃多少音频”“严格按最小PTS轮流写入”或“必然动态重采样校时”等具体算法。

[recordmng_muxer_ts.c][av-ts] 可见的输出路径是：

```c
OT_TS_FRAME_DATA_S tsFrameData = {0};
tsFrameData.bKeyFrameFlag = frameData->bKeyFrameFlag;
tsFrameData.pu8DataBuffer = frameData->apu8SliceAddr[0];
tsFrameData.u32DataLength = frameData->au32SliceLen[0];
tsFrameData.u64TimeStamp = frameData->u64TimeStamp;

SS_TS_WriteFrame(muxerObj, trackObj, &tsFrameData);
```

它把 recorder 输出帧的时间戳交给 TS 库。这里能确认的是适配层继续传递时间信息；不能推断 recorder 输出时间戳在所有模式下都和输入完全相等，特别是缩时/变速路径。

同样，播放器最终使用的是解复用器得到的文件时间信息，而不是 Windows 文件创建时间。TS 容器内部的时间基换算和时钟字段写入由封装库处理，本次不把接口中的整数直接等同于 TS 文件内未经换算的原始字段。

### 29.1 分段时为什么需要继续检查声音？

分段既涉及可独立解码的视频边界，也涉及音频包跨越边界时的处理。25 fps 的视频名义间隔为 40 ms，当前 AAC 音频组为 64 ms，两种边界通常不重合。

不能要求每段最后一个视频帧和最后一个音频包都正好在同一毫秒结束。验证重点是段内声画偏差是否稳定，以及相邻文件接续时是否出现明显声音缺口、重复或新增偏移。具体容差必须结合实际文件和产品要求判断，不能仅由 40/64 ms 两个间隔给出保证。

## 30. 普通录像、缩时录像和提示音要分开看

### 30.1 当前缩时任务明确去掉音频轨道

[product_statemng_record.c][av-state-record] 创建录像任务时有以下判断：

```c
if ((recordType == OT_PARAM_TYPE_LAPSE) ||
    (recordType == OT_PARAM_TYPE_SLOW) ||
    (isNeedStartAudio == TD_FALSE)) {
    recTask->recAttr.fileAttr[j].dataSrc.aencCnt = 0;
}
```

所以，即使原始 INI 写了 `aenccnt = 1`，进入缩时、慢动作或业务要求不启用录音时，最终录像任务也会把音频轨道数置为 0。

“缩时文件没有声音”在这段任务逻辑下属于预期行为。它不等于系统 ACAP、声控或扬声器必然全部关闭，其他模块仍可能使用音频资源。

### 30.2 为什么缩时不能直接塞入正常速度的声音？

举例：如果真实每秒保留 1 帧，文件按 30 fps 播放，真实 30 秒的画面会在约 1 秒内播完。同期麦克风却采了 30 秒声音。

要把它们放入同一秒播放，需要额外设计音频变速、丢弃或其他处理。当前任务选择去掉音频轨道，因此普通录像中的声画对齐模型不能直接套到缩时文件。

录像库中还有 `playFps`、`fSpeed` 和 `RECMNG_InsertVencFrame()` 等时间/帧处理路径。不能把“提高分辨率的4K处理”“正常编码帧率”“文件播放速度”“录像库补帧”混为同一个参数。分析缩时应分别测真实经过时间、编码帧间隔、文件时长和实际音轨是否存在。

### 30.3 退出缩时后如何确认声音真正恢复？

需要确认新的普通录像任务重新带有音频轨道，AENC 回调持续提供数据，最后文件里也确实存在可播放的音频包。

“Recording Started 播报了”是 ADEC/AO 输出结果，不能代替这三个条件。反过来，没有播放提示音也不必然意味着 SD 文件没有音轨。

## 31. 怎样实际验证HC112_B的音视频同步？

### 31.1 最直观的拍手测试

打开普通录像的录音开关，让前摄能清楚看到双手，并在镜头附近拍手。比较画面中双手合上的时刻与音轨中尖锐脉冲的时刻。

建议分别保留：

1. 开始录像后很快发生的拍手。
2. 连续录像几分钟后发生的拍手。
3. 分段前后发生的拍手。
4. 缩时恢复普通录像后发生的拍手。

尽量使声源靠近设备，减少声传播距离和画面判断误差。若比较后路，后路拍到的事件仍要与主机麦克风能收到的声音对应，不能把摄像头距离与麦克风位置造成的差异直接归因于同步算法。

固定偏移提示检查采集/处理延迟与起始对齐；越录越偏提示检查时钟速率、采样率解释和时间轴增长；只在切换后异常提示检查重建后旧帧、轨道恢复和时间基连续性。这些是排查方向，不是仅凭现象即可确定的根因。

### 31.2 用ffprobe看实际音轨与包时间

以下命令供电脑安装 FFmpeg 后执行；本次文档更新没有对设备录像做实测。

```bash
ffprobe -v error -show_entries stream=index,codec_type,codec_name,sample_rate,channels,time_base,start_time,duration,avg_frame_rate -of json "录像文件.TS"
```

查看音频包：

```bash
ffprobe -v error -select_streams a:0 -show_packets -show_entries packet=pts_time,dts_time,duration_time,size -of csv=p=0 "录像文件.TS"
```

查看视频包：

```bash
ffprobe -v error -select_streams v:0 -show_packets -show_entries packet=pts_time,dts_time,duration_time,size,flags -of csv=p=0 "录像文件.TS"
```

当前普通录像默认参数下，可先关注音频相邻有效时间戳是否接近 0.064 s，25 fps 视频是否接近 0.040 s。存在重排序时要区分 DTS、PTS 和显示顺序；字段缺失、封装差异或特殊模式也需要单独解释。

`time_base` 表示原始整数时间戳的单位。使用工具已经换算后的 `pts_time` 更容易比较，不要直接拿两个不同时间基的原始整数相减。

首包时间差只能检查轨道起始关系，不能独自证明拍手时声画同步。正确的最终验证要同时看时间戳和实际内容。

### 31.3 怎样理解ringbuf溢出对同步的影响？

`RingBufWriteMainFrame ... check write over error` 表示录像缓存写入路径异常，应结合同时间段视频/音频回调错误、SD 写入耗时和最终文件检查。

缓存变大能承受更长的消费阻塞，但不会自动修正错误的 PTS、错误采样率或变速设置。若只是后路视频持续丢帧，而 AENC0 音频仍连续，播放可能出现画面停顿而声音继续；播放器可以按时间轴继续播放，却无法恢复丢失画面的动作细节。
