# HC112_B 媒体参数从 INI 到运行生效的完整链路

## 1. 文档目的

本文基于当前 `Z:\HC112_B_SPC020` 双摄工程，说明媒体参数如何从 INI 文件进入 C 结构体，如何生成参数镜像，设备运行时又如何从 Flash 读取并最终作用到录像、拍照、VCAP、VPSS、VENC 和 OSD。

重点回答以下问题：

- 当前编译到底选择了哪个 INI 目录。
- `config_cfgaccess_entry.ini` 有什么作用。
- INI 中的字符串、整数和布尔值如何写入 C 结构体。
- `param.bin`、`paramdef.bin`、`rawparam` 分别是什么。
- 运行时为什么不是直接读取原始 INI。
- 分辨率、码率、预缓存时间、镜像翻转等参数最终如何生效。
- 为什么有时修改了 INI，烧录后却看不到变化。

> 结论先行：当前 HC112_B 不是在每次开机时逐个解析 INI。INI 主要在构建和打包阶段由 `ini2bin` 解析成 `PARAM_Cfg` 二进制数据，再生成 `param.bin`、`paramdef.bin` 和 rawparam 镜像。板端运行时读取的是 Flash 参数区中的二进制结构；只有当前参数损坏或校验失败时，才用 `paramdef.bin` 恢复默认参数。

## 2. 当前 HC112_B 选择的配置

当前 `config.conf` 中的关键配置为：

```text
CONFIG_SNS0_GC4653=y
CONFIG_SNS1_AHD_MIPI=y
CONFIG_MEM_TOTAL_SIZE="128"
CONFIG_NONESCREEN=y
# CONFIG_PARAM_FROM_FILE is not set
# CONFIG_PARAM_READ_ONLY is not set
```

含义如下：

| 配置 | 含义 |
|---|---|
| `CONFIG_SNS0_GC4653=y` | 前摄为 GC4653 |
| `CONFIG_SNS1_AHD_MIPI=y` | 后摄为 AHD MIPI 链路 |
| `CONFIG_MEM_TOTAL_SIZE="128"` | 128 MiB 内存配置 |
| `CONFIG_NONESCREEN=y` | 无屏产品 |
| `CONFIG_PARAM_FROM_FILE` 未开启 | 运行参数从 rawparam Flash 分区读取，而不是直接从 `/app/param/param.bin` 读取 |
| `CONFIG_PARAM_READ_ONLY` 未开启 | 运行时修改后的参数允许保存 |

`source/camera/demo/dronecam/build/base.mak` 第 77～101 行根据芯片、屏幕类型、前摄、后摄和总内存拼接 INI 路径。当前组合最终得到：

```text
Z:\HC112_B_SPC020\source\camera\demo\dronecam\modules\param\inicfg\hi3516cv610\nonescreen\gc4653_ahd_128M
```

构造逻辑可以简化为：

```makefile
PDT_INICFG_PATH := $(PDT_INICFG_ROOT)/$(CHIP)/$(CFG_DRONECAM_TYPE)/\
                   $(CFG_SENSOR_TYPE0)_$(CFG_SENSOR_TYPE1)_$(CONFIG_MEM_TOTAL_SIZE)M
```

所以，修改其他目录中的同名 INI 文件不会影响当前 GC4653+AHD 固件。

## 4. 第一步：确定哪些 INI 会被读取

### 4.1 配置入口文件

当前目录下的入口文件是：

```text
config_cfgaccess_entry.ini
```

该文件不是媒体参数本身，而是 INI 模块注册表。当前声明：

```ini
[module]
module_num = "24"
module1 = "media_common"
module2 = "workmode_common"
module3 = "workmode_record"
...
```

后面再把每个逻辑模块名映射到真实文件，例如：

```ini
[workmode_record]
cfg_filename = "config_product_workmode_record.ini"

[cam0_mediamode4]
cfg_filename = "config_product_mediamode_cam0_record_2160p30.ini"

[cam1_mediamode0]
cfg_filename = "config_product_mediamode_cam1_record_1080p30.ini"
```

代码读取时通常传入的是 `workmode_record`、`cam0_mediamode4` 这样的逻辑模块名，配置访问层再根据注册表找到对应文件。

### 4.2 注册表常见问题

- 新建了 INI 文件，但没有在 `config_cfgaccess_entry.ini` 中登记：文件不会被读取。
- 增加了 `module25`，却没有把 `module_num` 从 24 改成 25：新增模块可能不会被遍历。
- 模块名写错：加载函数找不到正确文件。
- 改了物理文件名，但没有同步 `cfg_filename`：构建阶段加载失败或仍加载旧文件。

## 5. 第二步：ini2bin 把 INI 填入 C 结构体

### 5.1 顶层入口

文件：

```text
source/camera/demo/dronecam/modules/param/ini2bin/src/product_iniparam_ini2bin.c
```

`PDT_INIPARAM_LoadCfg()` 是主要入口，流程为：

1. 调用 `SS_CONFACCESS_Init(PDT_INIPARAM, PDT_INIPARAM_PATH)` 初始化配置访问模块。
2. 依次读取设备管理、文件管理、媒体公共参数、工作模式、值域和各摄像头媒体参数。
3. 将结果全部写入静态变量 `g_paramCfg`。
4. 调用 `SS_CONFACCESS_Deinit()` 结束解析。

其核心调用关系可概括为：

```c
static PARAM_Cfg g_paramCfg;

SS_CONFACCESS_Init(...);
PDT_INIPARAM_LoadDevMngConf(...);
PDT_INIPARAM_LoadFileMngConf(...);
PDT_INIPARAM_LoadMediaCommConf(...);
PDT_INIPARAM_LoadWorkModeConf(...);
PDT_INIPARAM_LoadValueSetCfg(...);
PDT_INIPARAM_LoadCamMediaCfg(g_paramCfg.camMediaCfg, ...);
SS_CONFACCESS_Deinit(...);
```

### 5.2 顶层数据结构

`PARAM_Cfg` 定义在：

```text
source/camera/demo/dronecam/modules/param/core/src/product_param_inner_struct.h
```

其中最重要的成员是：

```c
typedef struct {
    PARAM_Header header;
    PARAM_WorkModeCfg workModeCfg;       /* 录像、拍照、USB等工作模式 */
    PARAM_MediaCommCfg mediaCommCfg;      /* 全局媒体公共参数 */
    PARAM_CamMediaModeCfg camMediaCfg[];  /* 各摄像头的各媒体模式 */
    PARAM_FileMngCfg fileMngCfg;
    PARAM_DevMngCfg devMngCfg;
    ...
    td_u32 magicEnd;
} PARAM_Cfg;
```

媒体参数可以理解为三层：

1. **全局公共层**：音频、显示、全局 VB 等所有模式共用的数据。
2. **工作模式公共层**：录像、拍照等工作模式自己的路由和公共属性。
3. **具体媒体模式层**：某个摄像头在 4K25、1080P30、5 fps 等模式下的分辨率、帧率、码率、VPSS 和 VENC 数据。

运行时不是只取一个 INI，而是把这三层合并为一份有效媒体配置。

### 5.3 单个键值如何读取

文件：

```text
source/camera/demo/dronecam/modules/param/ini2bin/src/product_iniparam_common.c
```

以整数为例，`PDT_INIPARAM_LoadIntValueByNodePrefix()` 先把节前缀和键名拼为：

```text
节点前缀:键名
```

然后调用：

```c
SS_CONFACCESS_GetInt(PDT_INIPARAM, iniModule, iniNodeName,
    notFoundValue, value);
```

其他类型类似：

| INI 数据类型 | 读取接口 |
|---|---|
| 整数 | `SS_CONFACCESS_GetInt` |
| 布尔值 | `SS_CONFACCESS_GetBool` |
| 字符串 | `SS_CONFACCESS_GetString` |
| 枚举字符串 | 先读字符串，再由项目转换函数映射成枚举值 |

例如：

```ini
[normal.0.filenum.0.fileattr]
recbuffer_time0 = "3600"
```

代码组合出的完整节点为：

```text
normal.0.filenum.0.fileattr:recbuffer_time0
```

读取后存入：

```c
PARAM_RecAttr.dataSource[0].bufferTimeMsec[0]
```

## 6. 第三步：生成 param.bin、paramdef.bin 和 rawparam

### 6.1 生成两个参数二进制文件

`product_iniparam_ini2bin.c` 的 `main()` 先清零 `g_paramCfg`，写入结构长度和首尾魔数，再调用 `PDT_INIPARAM_LoadCfg()`。解析成功后，直接把完整的 `PARAM_Cfg` 内存数据写入：

```text
param.bin
paramdef.bin
```

二者初次生成时内容相同，但运行时职责不同：

| 文件/区域 | 用途 |
|---|---|
| `param.bin` | 构建阶段生成的当前初始参数；随后可被封装为 rawparam |
| `paramdef.bin` | 默认参数备份，当前参数损坏或读取失败时用于恢复 |
| `rawparam` | 写入 Flash 参数分区的镜像，设备正常启动时优先读取 |
| `rawparambak` | rawparam 的备份分区 |

### 6.2 rootfs 打包阶段

文件：

```text
source/camera/demo/dronecam/rootfs/Makefile
```

`param:` 目标大致执行：

1. 把当前 `PDT_INICFG_PATH` 下的 INI 复制到参数暂存目录。
2. 根据构建配置替换版本号、型号等字段。
3. 复制并运行 x86 版本的 `ini2bin`。
4. 生成 `param.bin` 和 `paramdef.bin`。
5. 当前未开启 `CONFIG_PARAM_FROM_FILE`，因此再运行 `bin2image` 生成 rawparam 镜像。
6. 将 rawparam/rawparambak 放到烧录输出目录，并按构建选项删除最终文件系统中不需要的原始 INI 和工具。

`bin2image` 的入口在：

```text
source/camera/demo/dronecam/modules/param/bin2image/src/ss_product_param_bin2image.c
```

输入是 `./param.bin`，输出是 `./rawparam`。

## 7. 第四步：板端从 Flash 装载参数

### 7.1 默认参数先进入内存

文件：

```text
source/camera/demo/dronecam/modules/param/core/src/ss_product_param_comm.c
```

`PDT_PARAM_COMM_LoadDefaultBin()` 读取：

```text
/app/param/paramdef.bin
```

随后参数初始化流程调用：

```c
SS_PARAM2FLASH_InitParam(&binCfg);
```

### 7.2 优先使用当前 Flash 参数

文件：

```text
source/camera/demo/dronecam/modules/param2flash/host/ss_param2flash.c
```

当前未开启 `CONFIG_PARAM_FROM_FILE`，因此运行时主路径是读取 rawparam Flash 分区。读取后会检查：

- 头部魔数。
- 尾部魔数。
- `sysLen`/结构长度。
- 参数版本及基本合法性。

如果 Flash 参数正常，就继续使用已有参数；如果读取失败或校验错误，则加载 `paramdef.bin` 中的默认参数，并把默认值重新保存到参数区。

### 7.3 获得当前参数结构体

`ss_product_param_comm.c` 中：

```c
inline PARAM_Cfg *PDT_PARAM_GetCfg(td_void)
{
    return (PARAM_Cfg *)SS_PARAM2FLASH_GetParam()->cfg;
}
```

因此后续所有 `GetCamParam`、`SetCamParam` 和 `GetMediaCfg` 操作，实质上都是访问当前内存中的 `PARAM_Cfg`。

当 APP 或业务代码调用 Set 接口改变可保存参数时，参数模块先更新内存并设置保存标志，后台保存线程再把变化写回 Flash。所以下次重启时，保存过的当前值通常仍会保留。

## 8. 第五步：把多层参数合并成可运行的媒体配置

### 8.1 获取当前摄像头媒体模式

业务层通常调用：

```c
SS_PDT_PARAM_GetMediaCfg(workMode, &mediaCfg);
```

其内部流程为：

```text
SS_PDT_PARAM_GetMediaCfg
  └─ SS_PDT_PARAM_GetMediaCfgbyMediaMode
      └─ PDT_PARAM_GetMediaCfg
          ├─ PDT_PARAM_GetCamMediaCfg
          │   └─ PDT_PARAM_GetCamMediaCfgByMediaModeIdx
          └─ PDT_PARAM_GetVideoInCfg
```

### 8.2 按 camId 和 mediaMode 查找配置

`product_param_videoin.c` 中的 `PDT_PARAM_GetCamMediaCfg()`：

1. 先按 `camId` 找到 cam0 或 cam1 的 `PARAM_CamMediaModeCfg`。
2. 再遍历该摄像头的媒体模式列表。
3. 用 `OT_PARAM_MEDIAMODE_2160P_25` 等枚举找到匹配项。
4. 调用 `PDT_PARAM_GetCamMediaCfgByMediaModeIdx()` 合并公共层、录像/拍照层和具体模式层。
5. 再根据当前录像类型、制式、裁剪等运行状态刷新动态参数。

### 8.3 生成最终 OT_PARAM_MediaCfg

`PDT_PARAM_GetVideoInCfg()` 将所有已启用摄像头的结果合并到最终 `OT_PARAM_MediaCfg`，其中包括：

- VCAP 设备、Pipe、Channel。
- ISP 输入尺寸和帧率。
- VPSS Group 和 Port。
- VENC 通道、编码类型、分辨率、帧率、GOP、码率。
- VB 池和系统内存需求。
- OSD 绑定关系。
- 没有启用的摄像头和通道会被关闭或跳过。

最终媒体配置再由初始化模块和状态机交给媒体层，用于创建录像任务、拍照任务、预览链路及媒体重建。

## 9. 四个具体参数的完整追踪示例

### 9.1 前路默认模式：4K25

工作模式文件：

```text
config_product_workmode_record.ini
```

当前内容：

```ini
[common.mediamode.config.0]
camid     = "0"
mediamode = "OT_PARAM_MEDIAMODE_2160P_25"

[common.mediamode.config.1]
camid     = "1"
mediamode = "OT_PARAM_MEDIAMODE_1080P_25"
```

它说明录像工作模式默认选择：

- cam0：`OT_PARAM_MEDIAMODE_2160P_25`。
- cam1：`OT_PARAM_MEDIAMODE_1080P_25`。

`PDT_INIPARAM_LoadRecMediaCfg()` 读取这两组数据，存入录像工作模式的媒体模式配置。运行时 `SS_PDT_PARAM_GetMediaCfg()` 再据此查找具体模式参数。

> 注意：具体文件名叫 `config_product_mediamode_cam0_record_2160p30.ini`，但文件内部 `[common]` 中写的是 `OT_PARAM_MEDIAMODE_2160P_25`。程序按内部枚举匹配，不按文件名中的 `2160p30` 判断。文件名只是历史命名，不是最终生效依据。

### 9.2 前路 4K 分辨率和码率

文件：

```text
config_product_mediamode_cam0_record_2160p30.ini
```

当前关键值：

```ini
[common]
mediamode = "OT_PARAM_MEDIAMODE_2160P_25"

[vcap.dev]
sensor_type   = "30"     ; GC4653
sensor_width  = "2560"
sensor_height = "1440"

[vpss.0.vport.0]
res_width     = "3840"
res_height    = "2160"
src_framerate = "25"
dst_framerate = "25"

[venc.0]
res_width     = "3840"
res_height    = "2160"
gop           = "25"
src_framerate = "25"
dst_framerate = "25"
h265bitrate   = "20480"
h264bitrate   = "20480"
```

代码路径：

```text
PDT_INIPARAM_LoadCamMediaCfg
  └─ 读取 cam0_mediamode4 模块
      ├─ 加载 VCAP/ISP 属性
      ├─ 加载 VPSS vport 属性
      └─ PDT_INIPARAM_LoadCamVencSpecAttr
          ├─ res_width/res_height
          ├─ src_framerate/dst_framerate
          ├─ gop
          └─ h265bitrate/h264bitrate
```

最终数据进入 `PARAM_MediaModeVencAttr`，运行时合并进入 `OT_PARAM_MediaCfg` 的 VENC 配置。

这里还能看出当前 4K 的形成方式：GC4653/ISP 输入为 2560×1440，VPSS 主输出配置为 3840×2160，随后 VENC0 编码为 3840×2160。

### 9.3 录像预缓存 recbuffer_time0

当前录像工作模式文件中：

```ini
[normal.0.filenum.0.fileattr]
venc_hdl0       = "0"
recbuffer_time0 = "3600"   ; 前路，毫秒

[normal.1.filenum.0.fileattr]
venc_hdl0       = "3"
recbuffer_time0 = "3200"   ; 后路，毫秒
```

解析函数位于 `product_iniparam_workmode_rec.c`：

```text
PDT_INIPARAM_LoadRecFileAttr
  └─ SS_CONFACCESS_GetInt(... recbuffer_timeN ...)
      └─ PARAM_RecAttr.dataSource[].bufferTimeMsec[]
```

含义：录像模块为相应 VENC 数据源保留多少毫秒的环形预缓存。它不是最终录像文件时长，也不是 `prerec_time`。

容易混淆的三个值：

| 参数 | 单位 | 作用 |
|---|---:|---|
| `recbuffer_time0` | ms | 对应编码数据源的 RingBuffer 预留时长 |
| `prerec_time` | s | 业务上的预录时长 |
| `split_time` | s | 单个录像文件的分段时长 |

### 9.4 镜像和翻转

镜像翻转至少存在两个层面：

1. `config_product_mediamode_camX_comm_record.ini` 中的 `mirror`、`flip`，对应 VPSS/VPort 或录像路由的公共属性。
2. 具体媒体模式文件中的 `isp_mirrorflip`，对应 Sensor/ISP 方向属性。

解析位置主要在 `product_iniparam_cammedia.c`：

```text
mirror / flip       → PDT_INIPARAM_LoadBoolValueByNodePrefix
isp_mirrorflip      → PDT_INIPARAM_LoadIntValueByNodePrefix
```

当前后摄公共录像配置中部分输出端口的 `mirror = "1"`，前摄多数为 `0`。修改方向时必须先确认要控制的是 Sensor/ISP、VPSS 的某个端口，还是 APP 保存的动态状态；否则可能出现预览、录像、拍照方向不一致。

## 10. 为什么修改 INI 后可能不生效

### 10.1 修改了错误目录

当前目标只读取 `gc4653_ahd_128M`。修改 `gc4023_128M`、`gc4653_128M` 或其他传感器目录不会进入本次参数镜像。

### 10.2 文件没有注册

新增或重命名 INI 后，`config_cfgaccess_entry.ini` 未同步登记，`ini2bin` 不会通过逻辑模块找到它。

### 10.3 只重新编译 main_app，没有重新生成参数镜像

INI 属于参数打包链路，不是普通 C 源码。只更新 `main_app` 不代表 `param.bin`、`paramdef.bin`、rawparam 和 appfs 中的参数文件已重新生成。

修改 INI 后应确认：

- 参数打包目标确实重新执行。
- `param.bin`/`paramdef.bin`/rawparam 的时间戳或哈希发生了预期变化。
- 烧录时更新了真正承载变更的分区。

是否必须执行完整 `make all` 取决于工程当前 Makefile 依赖是否会自动重建这些产物；不能仅凭 `main_app` 编译成功判断 INI 已生效。

### 10.4 旧 rawparam 当前值覆盖新默认值

设备正常启动时优先使用 Flash 中现有 rawparam。`paramdef.bin` 是失败恢复用的默认值，不会在每次启动时无条件覆盖当前参数。

因此若只更新 appfs 内的 `paramdef.bin`，但没有更新/擦除 rawparam，设备可能继续使用旧参数。验证默认值时需要确认：

- 是否强烧了 rawparam 和 rawparambak。
- 是否执行了会恢复默认参数的流程。
- APP 以前保存的参数是否仍在 Flash 中。

### 10.5 改了文件名含义，却没改内部枚举

### 10.6 cam0/cam1 或句柄对应错误

双摄中至少要同时核对：

- `camid`。
- `vpsshdl`、`vporthdl`。
- `venchdl`/`venc_hdl0`。
- OSD 的绑定通道。
- 前后路录像文件的数据源。

句柄配置错位可能表现为“改的是前路，实际影响后路”，或录像、预览、拍照只有其中一路生效。

## 15. HC112_B 码率、文件大小与录像缓存的计算

本节于 2026-09-11 按 `Z:\HC112_B_SPC020` 当前工作区核对。以下配置值属于源码默认值，不代表已经读取板端当前 Flash 参数或测得实际码流。计算示例以普通前路 4K25＋后路 1080P25、H.265 双录为前提。

### 15.1 码率是什么，是否由分辨率自动算出

码率是单位时间内编码数据的比特数。`b` 是 bit（比特），`B` 是 Byte（字节），两者相差 8 倍：

```text
1 Byte = 8 bit
数据速率（Byte/s）= 码率（bit/s）÷ 8
```

分辨率描述一帧包含多少像素，帧率描述每秒多少帧，码率描述压缩后每秒多少数据。这三个量相关，但不能仅凭“3840×2160、25 fps”唯一算出 H.265 码率。画面运动、噪声、细节、量化参数及码控方式都会影响压缩结果。

当前工程的普通录像码率是从 INI 读取的配置值，并非用宽×高×帧率自动推导。例如前路 `20480` 表示当前选择的码率目标；把 3K 放大成 4K，也不意味着码率必须按像素比例同步增加。

### 15.2 当前前后路实际配置来源

### 15.3 INI 码率怎样进入编码器和录像模块

参数层文件：

```text
Z:\HC112_B_SPC020\source\camera\demo\dronecam\modules\param\core\src\product_param_videoin.c
```

`PDT_PARAM_GetVideoVencH265Attr()` 根据码控模式，把同一个 INI 值放入不同字段：

| 码控模式 | 最终字段 | 含义 |
|---|---|---|
| CBR | `cbrAttr.bitRate` | 码率控制目标，不保证每一秒、每一帧都一样大 |
| VBR | `vbrAttr.maxBitRate` | 码率控制的上限参数，不等同于每帧瞬时峰值限制 |
| QVBR | `qvbrAttr.targetBitRate` | 结合质量约束使用的目标码率，实际输出可以波动 |

当前 H.265 主录像走 QVBR 分支：

```c
h265QVbr->qvbrAttr.targetBitRate = vencSpecAttr->h265BitRate;
```

所以，配置了 `10240` 并不代表后路任何一秒都必须写入相同大小的数据。静止画面、低细节画面可能更小；运动、复杂纹理和噪声会改变实际输出。I 帧和 P 帧大小也不同。

### 15.4 本工程为什么计算时经常使用 1024

标准单位中，1 kbit/s = 1000 bit/s；1 KiB = 1024 Byte，1 MiB = 1024×1024 Byte。不要把标准十进制单位和工程内部换算混用。

本工程录像模块存在明确的二进制换算。文件：

```text
Z:\HC112_B_SPC020\source\camera\component\recordmng\src\recordmng_define.h
Z:\HC112_B_SPC020\source\camera\component\recordmng\src\recordmng_source.c
```

相关代码为：

```c
#define RECMNG_KBIT_TO_BIT 10

/* RECMNG_GetH265Attr() 的 QVBR 分支 */
videoSrcInfo->u32BitRate =
    qvbr->qvbrAttr.targetBitRate << RECMNG_KBIT_TO_BIT;
```

左移 10 位等于乘以 1024。因此，本节按录像模块传递码率信息的口径，令 INI 中的值为 B，得到：

```text
录像模块码率信息（bit/s）= B × 1024
对应数据速率（Byte/s）  = B × 1024 ÷ 8
对应数据速率（MiB/s）   = B ÷ 8192
```

这里证明的是录像模块的换算方式，不能据此保证编码器实际输出一定等于该值。若工具用十进制 kbps 报告实测码率，应按 1000 换算；例如 20480 kbit/s 的十进制计算结果为 2.56 MB/s，约 2.441 MiB/s，与下文工程口径的 2.5 MiB/s 不同。

### 15.5 前后路每秒数据量如何计算

前路：

```text
20480 × 1024 = 20,971,520 bit/s
20,971,520 ÷ 8 = 2,621,440 Byte/s
2,621,440 ÷ 1024 ÷ 1024 = 2.5 MiB/s
```

后路：

```text
10240 × 1024 = 10,485,760 bit/s
10,485,760 ÷ 8 = 1,310,720 Byte/s
1,310,720 ÷ 1024 ÷ 1024 = 1.25 MiB/s
```

两路合计的名义视频数据量：

```text
2.5 + 1.25 = 3.75 MiB/s
```

该结果没有计入音频、TS 封装、其他文件写入和文件系统开销，也不是 SD 卡“保证不掉帧”的最低性能指标。SD 卡短时写入停顿、分段、删除旧文件及 I 帧峰值仍需要缓冲空间。

### 15.6 一分钟和 2～4 秒录像应该有多大

按目标码率估算视频有效数据：

```text
视频数据量（MiB）≈ B ÷ 8192 × 时长（s）
```

| 持续时间 | 前路 20480 | 后路 10240 | 两路合计 |
|---:|---:|---:|---:|
| 2 秒 | 5 MiB | 2.5 MiB | 7.5 MiB |
| 3 秒 | 7.5 MiB | 3.75 MiB | 11.25 MiB |
| 4 秒 | 10 MiB | 5 MiB | 15 MiB |
| 60 秒 | 150 MiB | 75 MiB | 225 MiB |

这些是“实际平均码率接近配置目标”时的估算，不是录像文件大小验收阈值。QVBR、有效帧数、实际录制时长、音频和 TS 封装都会造成差异。短视频尤其不能只用文件名的时间差判断时长，应检查视频时间戳、帧数和解码完整性。

反过来，由文件估算平均总码率：

```text
平均总码率（bit/s）= 文件字节数 × 8 ÷ 有效时长（s）
标准 kbps         = 上式 ÷ 1000
工程 1024 口径值  = 上式 ÷ 1024
```

例如一个 3 MiB、有效时长 3 秒的后路文件：

```text
3 × 1024 × 1024 × 8 ÷ 3 = 8,388,608 bit/s
标准单位：8388.608 kbps
工程口径：8192
```

这是整个文件的平均值，包含音频和封装；要测视频本身，应累计视频包字节数。若结果明显低于配置，需结合 QVBR、实际帧数和丢帧日志判断，不能仅凭文件小就认定掉帧。

### 15.7 为什么不能认为每帧都同样大

若按 25 fps 均摊上述目标数据量：

```text
前路平均：2,621,440 ÷ 25 = 104,857.6 Byte/帧 = 102.4 KiB/帧
后路平均：1,310,720 ÷ 25 = 52,428.8 Byte/帧  = 51.2 KiB/帧
```

这只是平均预算。H.265 的 I 帧通常比 P 帧大，复杂画面也会产生峰值。因此，RingBuffer 不能只按“平均一帧大小×帧数”算出容量后填满使用，还要容纳峰值和读写进度差。

### 15.8 recbuffer_time 如何换算成数据容量

先估算对应时长的压缩视频数据，不把它当成底层实际申请大小：

```text
名义视频容量（MiB）≈ B ÷ 8192 × Tms ÷ 1000
```

当前前路 3600 ms：

```text
20480 ÷ 8192 × 3600 ÷ 1000 = 9 MiB
```

当前后路 3200 ms：

```text
10240 ÷ 8192 × 3200 ÷ 1000 = 4 MiB
```

两路名义视频数据容量合计为 13 MiB。这里只计算两路主视频的时长预算；录像库实际申请还可能包含音频、帧描述信息、内存对齐、额外余量或不同的分配规则，必须以实际申请日志和 MMZ 占用核实，不能直接宣布“ringbuf_mmz 设为 13 MiB 就够”。

还要区分以下三类内存：

| 名称 | 存储对象 | 本节码率×时长能否直接推导 |
|---|---|---|
| 录像 RingBuffer | 已压缩的视频/音频及管理信息 | 能估算数据部分，不能直接确定最终申请总量 |
| VENC 输出码流缓冲 | 编码器输出码流 | 有独立配置和底层要求，不能等同于录像预缓存 |
| VCAP/VPSS 的 VB 图像池 | 原始/压缩图像帧 | 主要取决于尺寸、像素格式、压缩和块数，不能按录像码率计算 |

由此可算出提高缓存时间的增量预算：

| 调整 | 增加的名义视频容量 |
|---|---:|
| 前路增加 100 ms | 0.25 MiB |
| 后路增加 100 ms | 0.125 MiB |
| 后路从 3200 ms 增加到 3600 ms | 0.5 MiB |
| 两路各增加 100 ms | 0.375 MiB |

反推可增加时长：`增加时长（ms）≈ 可用于该视频数据的容量（MiB）× 8192 ÷ B × 1000`。例如真正有 1 MiB 可用于后路视频数据，名义上对应 800 ms；该公式尚未扣除管理、对齐和峰值余量，不能直接作为可安全增加的结论。

### 15.9 降低码率会怎样影响缓存

保持后路 3200 ms，将码率从 10240 调到 8192 时，名义容量从：

```text
10240 ÷ 8192 × 3.2 = 4 MiB
变为
8192 ÷ 8192 × 3.2 = 3.2 MiB
差值 = 0.8 MiB
```

同理，前路由 26624 降为 20480、缓存保持 3600 ms 时：

```text
26624 ÷ 8192 × 3.6 = 11.7 MiB
20480 ÷ 8192 × 3.6 = 9 MiB
差值 = 2.7 MiB
```

降低目标码率通常能降低数据吞吐压力，但也可能损失复杂画面的细节。名义预算降低不代表已经分配的 MMZ 会立即归还；是否重新申请缓冲、何时释放，要看录像任务和媒体重建流程。

### 15.10 缩时录像不能直接套用普通录像文件大小

普通录像中，真实采集时长和正常播放时长通常接近。缩时录像的两种时长不同：假设真实每秒编码 1 帧、按 30 fps 播放，则采集 60 秒得到约 60 帧，播放约 2 秒。相同文件分别除以 60 秒和 2 秒，计算出的码率相差 30 倍。

当前 `product_param_videoin.c` 中的 `PDT_PARAM_RefreshRcByLapseRec()` 还包含以下动态调整：

```c
#define PDT_PARAM_VENC_INPUT_DEF_FPS 30

*bitRate = (*bitRate) * 1000 / (30 * intervalMsec);
```

当该分支执行且 `intervalMsec=1000` 时，传入码率会被整数除以 30。例如传入 20480，计算结果为 682。这里的 30 是代码定义的换算基准，不能理解成当前 ISP 一定输入 30 fps。

缩时模式可能使用专用媒体 INI，传入的码率也可能已经不同。因此应先确认实际选中的模式和日志中的 `before/after Refresh`，再计算真实每秒写入量；不要直接拿普通 4K25 的 20480 和缩时文件的播放时长判断码率异常。

### 15.11 实际检查时按什么顺序计算

1. 确认普通录像还是缩时录像，以及当前 cam0/cam1 媒体模式。
2. 读取对应具体 INI 的码率，再检查公共 INI 的 H.264/H.265 和 CBR/VBR/QVBR 选择。
3. 核对运行时最终参数，排除 Flash 旧值或动态调整覆盖默认值。
4. 用 `B÷8192` 计算工程口径的名义 MiB/s，再乘时长估算文件或视频缓存数据量。
5. 测量真实文件字节数、有效时长、帧数和视频包大小，与估算比较。
6. 若排查 RingBuffer 溢出，再结合实际缓冲申请量、读写位置、SD 写入停顿及 I 帧峰值；不能只看目标码率或平均文件大小。
