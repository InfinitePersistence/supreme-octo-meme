# 如何移植一个新摄像头

——以 IMX675 适配 HC112／Hi3516CV610 为例

更新日期：2026-09-18。面向有嵌入式开发经验、但不熟悉本工程的同事。

这份文档可以单独阅读，不要求访问作者的电脑、网络盘或历史对话。正文解释模块职责、配置关系、关键代码思路、验证方法和排错依据；附录提供本案例的相对文件路径，只有准备落代码时才需要查阅。

案例硬件：HC112 单摄设备，SoC 为 Hi3516CV610，128MiB DDR，IMX675-AAQR-G 模组，两条 MIPI 数据 lane。目标是接入双曝光 WDR，并支持不同输出尺寸和 PQ 调试。这里的“2K”专指2560×1440，“4K”专指3840×2160。

**读完应能回答五个问题：** 要先向硬件和供应商确认什么？驱动和接收端分别改什么？菜单与INI怎样变成板端行为？怎样证明移植成功？怎样搭建PQ并判断RAW抓取失败发生在哪一层？

> 出现 `init success` 只说明某个初始化流程返回成功。移植完成还要证明数据格式、实际帧率、曝光控制、产品输出和资源使用正确，并且结果能够重复。

阅读顺序：第1～4节建立整体认识；第5～9节用于实施；第10节验收；第11节可作为PQ操作流程；第12节查典型故障；第13～14节用于安排工作和记录结果。无需先阅读附录。

### 先认识本文的几个术语

| 术语 | 在本文里负责什么 | 不要混淆什么 |
| --- | --- | --- |
| Sensor／CMOS | 将光转换为像素，经MIPI发送原始数据；I2C用于控制它 | Sensor寄存器驱动与录像应用是不同层。 |
| SDK | 芯片厂商提供的媒体接口、驱动、库和工具 | 不同SoC／版本的结构体和二进制不一定兼容。 |
| NDK／媒体适配层 | 本工程封装SDK的一层，将产品的sensor选择和媒体配置转换成底层调用 | 新增sensor需要让该层认识它，不能只加入寄存器表。 |
| MIPI／lane／VC | MIPI是图像接口；lane是物理数据通道；VC是数据流中的虚拟通道标识 | 两个曝光VC不等于两颗摄像头；lane数量也不等于曝光数量。 |
| VI／pipe | 视频输入模块及其处理管线 | WDR可以使用两个曝光pipe，但仍是一颗sensor。 |
| ISP／AE／AWB | ISP处理原始图像；AE控制曝光和增益；AWB控制白平衡 | 曝光更新可能在初始化之后持续改变sensor寄存器。 |
| WDR／DOL2 | 宽动态；本例DOL2由长、短两次曝光提供输入，再经ISP融合 | 画面能显示，不足以证明两个曝光都正确。 |
| VPSS／VENC | VPSS进行缩放等后处理；VENC将图像编码成视频或JPEG | 输出4K不代表sensor采集的是原生4K。 |
| Scene／IQ／PQTools | Scene按场景自动更新图像参数；IQ是图像质量与参数；PQTools是调参工具 | 暂停Scene不等于停止ISP，也不自动锁定AE／AWB。 |
| VB／MMZ | VB是按块管理的媒体缓冲池；MMZ是供媒体使用的内存区域 | Linux空闲内存与媒体区可用内存不是同一个数。 |
| proc | Linux下用于读取驱动运行状态的伪文件，例如`/proc/umap/vi` | 它能提供实际运行证据，和配置文件里的期望值不同。 |

## 1. 先确定要交付的模式，而不是先复制驱动

### 1.1 用三行规格消除歧义

以“4K25 WDR”为例，实施前必须将需求拆成：

```text
Sensor采集：2560×1440，25fps，两曝光WDR，RAW10
ISP处理：将两曝光融合成一幅有效图像
最终输出：VPSS放大到3840×2160，VENC编码25fps，提供预览和录像
```

这样才能判断：sensor是否支持该采集模式、两lane能否承载、SoC能否处理、内存是否够用。如果只写“4K25”，开发人员可能误以为要求sensor原生4K，或错误地按4K尺寸抓RAW。

还要确认是否同时需要抓拍、子码流、SD录像、APP预览，以及切换模式时是否允许短暂断流。不同并发组合需要不同内存预算。

### 1.2 本案例中的四个选项

下表描述保留PQ功能的调试版本。原产品版本与调试版本应分别管理；不要用关闭了部分业务的调试版本代替正式产品验收。这里的“在线/离线”指芯片内部模块之间的数据是否经过 DDR 帧缓存。

| 产品选项 | Sensor有效采集 | 最终视频输出 | 驱动模式编号 | 主VI／VPSS工作方式 | 目的与验证边界 |
| --- | --- | --- | --- | --- | --- |
| `1080P30FPS WDR` | 2560×1440 WDR30 | 缩小至1920×1080@30 | 1 | 离线／离线 | 已有双曝光RAW抓取与恢复正常的测试反馈。 |
| `1440P25FPS WDR` | 2560×1440 WDR25 | 同尺寸2560×1440@25 | 2 | 离线／离线 | 当前调试源码默认的2K档；最新版本仍需独立记录上板验收。 |
| `4K25FPS WDR` | 2560×1440 WDR25 | 放大至3840×2160@25 | 2 | 在线／离线 | 已有此前4K编码运行证据；正常4K档双曝光RAW未完成验收。 |
| `PQ RAW25 WDR` | 2560×1440 WDR25 | 缩小至1920×1080@25 | 2 | 离线／离线 | 减少输出占用，检查25fps模式RAW；选对10bit后有成功反馈。 |

“离线”在这里表示模块间通过内存缓冲传递数据，不是设备没有网络；“在线”指相应模块间的在线连接方式。能否抓RAW与平台接口、缓冲和具体连接方式有关，不能把离线或在线作为跨平台的单一结论。

模式编号1、2只是本案例代码中的索引，没有行业通用含义。三个25fps选项共用sensor mode2，仅输出和资源配置不同。

当前调试版本的2K／4K精简档保留SD录像和RTSP主流，关闭抓拍、缩略图、子码流等资源。产品若要求这些功能，最终必须恢复并重新验收，不能把精简后的内存结果直接用于完整产品。

案例最终采用1440P采集后缩小到1080P。曾试过sensor中央裁1080P，但会改变视场；两种方式都可能得到1920×1080文件，实际采集方式却不同。

## 2. 移植前必须确认的事情

先把下表填写完整。没有资料或没有测量依据的项目写“待确认”，不要用供体注释代替确认。

| 要确认什么 | 从哪里确认 | 怎样判断、为什么重要 |
| --- | --- | --- |
| Sensor 完整料号、版本、模组料号 | 模组标签、供应商 BOM、对应 datasheet／勘误 | 同系列的 AAQR、AAQR1、AAQR-G 等后缀不能直接视为完全相同。本次实物为 AAQR-G，已有资料的后缀适用性仍需供应商核实。 |
| SoC、SDK／NDK 版本、CPU 架构 | 工程配置、SDK 版本文件、启动日志、工具链 | 本次目标为 Hi3516CV610／A7；Hi3519 供体不能只改目录名就使用其头文件、结构体和二进制库。 |
| 供电、IO 电压、上电时序、复位极性 | 板级原理图、模组接口图、datasheet；示波器测量 | 排线能插上、I2C 偶尔响应都不能证明电气条件正确。直接替换 GC8613 模组也要逐项核对。 |
| MCLK／INCK | Sensor 模式表、SoC 时钟配置、实际引脚波形 | 软件选择值、寄存器编码和实际频率要一致；不能把 MIPI 速率当成外部 MCLK。 |
| I2C 总线、地址、地址／数据字节数 | 原理图、模组说明、驱动、实际寄存器读取 | 本次驱动用 `0x34` 的 8-bit 表示，Linux 7-bit 地址为 `0x1A`；寄存器地址 2 字节、数据 1 字节。不能混用两种地址口径。 |
| MIPI lane 数、物理 lane 映射、速率和极性 | 原理图、模组初始化表、SoC MIPI 手册、NDK lane 表 | 本次为两 lane，物理映射沿用 GC8613 的 lane0／lane2；两 lane 并不一定是数组 `{0,1}`。 |
| RAW 位深、Bayer 顺序、镜像翻转 | 原厂模式说明、寄存器、NDK 配置、色彩图样 | RAW10／RAW12、RGGB 等必须一致；偏色不一定是 AWB 参数问题，也可能是 Bayer 或裁剪起点错误。 |
| Linear／DOL WDR、曝光数、VC／数据类型 | DOL 应用说明、寄存器表、MIPI 接收配置 | “两曝光”不是“两摄像头”；发送端 VC 格式、接收配置和 VI 融合方式必须成套匹配。 |
| 有效尺寸、传输尺寸、OB／EBD／边界行 | Datasheet、软件手册、DOL 数据格式图、MIPI proc | 有效 1440 行不表示链路只传 1440 行；接收裁剪坐标必须在正确的数据类型坐标中计算。 |
| 采集帧率与输出帧率 | Sensor 时序计算、VI／ISP／VENC proc、录像文件 PTS | 写成 30fps 不代表实际达到 30fps；补帧、慢快门或错误 MCLK 都可能造成误判。 |
| 视场是否允许改变 | 产品需求、镜头和画面实拍对比 | Sensor 中央裁剪通常改变视场，VPSS 缩小与中央裁剪不是同一件事。 |
| 内存和业务并发 | DDR／Flash 配置、启动参数、VB／MMZ／VENC proc、业务需求 | 是否同时录像、预览、抓拍、抓 RAW，会直接改变所需资源。先确定需求，才能计算内存。 |

### 本次应优先准备的资料

- IMX675 对应版本的 datasheet、Software Reference Manual、DOL 应用说明和勘误。
- SUNNIC 寄存器设置 No1～No4 的原始文件及版本。本次 No3 是两 lane Linear 参考，No4 是两 lane DOL 参考；不是拿到一份表就适用于所有窗口和帧率。
- 同平台已运行工程的源码、实际配置、固件版本、启动日志和实测结果。供体当前 `config.conf` 不一定就是曾经成功的那一套。
- HC112 原理图、GC8613 接口连线、IMX675 模组接口表。
- Hi3516CV610 对应版本的 Windows PQTools、板端工具、API／结构体头文件。

**判断方法：** 优先用“实物／原理图 + 原厂资料 + 当前代码 + 实机结果”互相校验。四者不一致时，先定位差异，不能选择一个看起来方便的数值继续移植。

## 3. 先做基线与备份，再选择参考工程

### 3.1 保存的不只是 Git 提交

Linux 开发服务器执行以下只读检查：

```sh
# 将下一行替换为自己的工程根目录
PROJECT=/path/to/your/project
cd "$PROJECT"
pwd -P
git symbolic-ref --short HEAD
git rev-parse HEAD
git status --short
git diff --stat
find . -type l -printf '%p -> %l\n'
```

需要保留：当前分支与提交、未提交修改、未跟踪文件、被忽略的 SDK／库／构建产物、`config.conf`、参数文件及完整启动日志。工程有大量未提交修改时，仅打一个 Git tag 不能形成完整回退点。

本次采用工程外的完整归档，包含 `.git` 和被忽略文件，记录 SHA-256，并做归档内容比对。回退时先解压到空目录验证，保存现有工程，再交换目录；直接覆盖解压会残留锚点之后新增的文件。

### 3.2 复制工程后检查符号链接

完整复制工程不一定意味着工程已经独立。`cp -a`会原样保留符号链接；如果链接里写的是另一个工程的绝对地址，新副本仍可能读取旧工程的文件。

例如，调试工程内有一个名为`sdk`的链接，实际指向原工程SDK。后来原工程被回退，即使调试工程的源文件没变，经过这条链接读取的库也已经变了。已烧入板端的固件不会因此自动改变，风险发生在后续编译、链接或打包时。

检查方法：

```sh
# 在工程根目录执行，查看链接本身保存的目标文字
find . -type l -printf '%p -> %l\n'

# 找到可疑链接后，用它的实际路径替换占位符，查看最终目标
readlink -f /path/to/suspected/link
```

如果目标在工程外，确认它是刻意共享的固定工具链，还是复制工程时留下的错误引用。对于需要独立的SDK依赖，应先核对副本自身文件，再修改链接；不要直接删除所有符号链接，也不要将不同SDK版本混合使用。

本例曾发现一处媒体示例SDK链接和两处文件系统工具链接。前者可能影响部分头文件／库搜索路径；两个工具的文件哈希一致，暂未出现工具版本差异。主构建仍默认使用本工程自己的SDK，因此不能把三条链接理解成“整个固件都依赖旧工程”。

### 3.3 供体选择原则

同平台、同 SDK、同 sensor 且有实际证据的供体优先。本次优先 ET1XX 的 Hi3516CV610 驱动与 WDR 链；Hi3519 提交用于对照寄存器和接入思路。

可以借鉴的是 sensor 驱动框架、初始化序列、AE／AWB 回调和接收配置；需要重新判断的是 lane、MCLK、窗口、帧率、内存、库接口、产品业务及网络收流方式。不能因为供体做以太网后拉，就把网络后拉应用一起搬进单录工程。

## 4. 先画清楚两条链，再开始修改

### 4.1 图像运行链

```text
模组供电、复位、MCLK
        ↓
I2C 写入 sensor 寄存器 → Sensor 按设定时序发送 MIPI RAW
        ↓
MIPI 接收与 VC 分离 → VI 曝光 pipe → ISP／WDR 融合
        ↓
VPSS 缩放、降噪等处理 → VENC 编码 → SD 录像／RTSP
```

RAW 抓取针对融合前的采集数据。4K 编码由 VPSS 放大得到，不会让 IMX675 产生原生 3840×2160 RAW。

### 4.2 配置生效链

```text
make menuconfig → config.conf
        ↓
构建变量与宏 → SDK 驱动库 + NDK sensor 配置／注册
        ↓
选择产品 INI 和 Scene INI
        ↓
参数转换、链接、镜像打包、启动参数生成
        ↓
烧录到板端 → 实际 bootargs／持久化参数 → 运行配置
```

两条链都要通：菜单能选到 IMX675，只说明配置入口存在；没有驱动注册、正确参数镜像或正确启动时钟，仍然不能出图。

## 5. 需要修改哪些代码：按职责理解，不必先记路径

本工程分成五类修改：**驱动控制sensor、接收配置告诉SoC怎样收、注册让系统找到驱动、产品参数定义输出业务、构建与启动把这些内容带到板端。** 各模块的相对路径集中在附录A，本节不要求打开源码才能阅读。

### 5.1 Sensor驱动：把“目标模式”变成实际寄存器行为

驱动不是只有一张初始化表。典型组成如下：

| 职责 | 输入 → 输出 | 本次要改什么 | 漏改时的典型表现 |
| --- | --- | --- | --- |
| I2C读写 | 总线号、寄存器地址／数值 → 实际总线操作与返回值 | 地址位宽、数据位宽、总线选择、错误处理 | 初始化假成功；读取总返回0；写入一半失败后仍继续。 |
| 初始化 | 选定模式 → PLL、lane、RAW格式、窗口、帧周期等寄存器 | 用匹配本模组、两lane及目标时钟的表 | I2C正常但MIPI无帧，或帧格式／帧率错误。 |
| 模式匹配 | 尺寸、FPS、WDR要求 → 驱动内部模式索引 | 增加并严格匹配1440P WDR30／25 | 请求25fps却仍用30fps时序；选中不存在的模式。 |
| AE回调 | ISP给出的FPS、曝光、增益要求 → 运行寄存器更新 | 同步行时间、曝光范围、增益表、WDR长短曝光控制 | 开始出图，随后被AE写成错误帧率或曝光。 |
| ISP／AWB默认参数 | 模式与模组信息 → 初始黑电平、白平衡等参数 | 以目标SDK结构填充，后续用本模组标定 | 能出图但偏色、暗角、噪声或宽动态效果异常。 |

以FPS回调为例，下面是**逻辑示意**，函数名和完整边界检查以目标SDK为准：

```c
/* 用当前模式自己的基准计算行数，不能沿用供体另一模式的最大帧率。 */
vmax = mode_base_vmax * mode_base_fps / requested_fps;

/* 本例DOL2中FSC为两倍VMAX；其他sensor须依据对应手册。 */
fsc = is_dol2 ? 2 * vmax : vmax;
```

关键不在于复制这两行，而是确保初始化、AE默认值、FPS回调和WDR曝光计算使用同一套时序。第6节给出本例的具体数值与错误案例。

### 5.2 接收配置：发送端和接收端必须描述同一帧

Sensor决定“发什么”，SoC接收配置决定“按什么规则收”。本例需要接收：两条物理lane、RAW10、两个曝光VC，以及2560×1440有效图像。

| 接收字段 | 对应的硬件／图像事实 | 为什么要核对 |
| --- | --- | --- |
| lane映射 | PCB实际接到SoC的lane编号 | 两lane并不必然是lane0／lane1，本板使用lane0／lane2。 |
| RAW位宽 | MIPI实际数据类型 | Sensor发RAW10，接收端按RAW12解释会出错。 |
| WDR接收格式 | 双曝光在MIPI中的组织方式 | VC、行交织等方式不能凭“都是WDR”混用。 |
| 有效窗口和起点 | 去掉相应边界后要交给ISP的像素区域 | Sensor有效像素、传输边界和OB／EBD不是同一个尺寸。 |
| Bayer顺序 | 有效图像左上角的颜色排列 | 窗口起点或镜像翻转变化可能影响颜色排列。 |
| 驱动对象与模式索引 | 应该调用哪个驱动、哪套时序 | 尺寸正确但绑定错对象，仍然会写错寄存器。 |

本例WDR25的NDK模式表项节选：

```c
/* 这是采集模式，不是最终编码分辨率；4K由后续VPSS放大。 */
{
    .width = 2560, .height = 1440, .snsMode = 2,
    .wdrMode = OT_WDR_MODE_2To1_LINE, .snsMaxFrameRate = 25.0f
},
```

这里的`.snsMode=2`必须能在sensor驱动中找到对应实现，不能只在接收层声明一个模式。WDR还要将两个曝光pipe正确配置到融合组，详见第6.3节。

### 5.3 注册与链接：让应用真正找到新驱动

嵌入式工程经常有“源文件已经放进去，却没有运行到”的问题。新sensor通常需要三个动作：

1. **提供驱动对象。** 对象中保存初始化、退出和ISP／AE／AWB回调等函数入口；本例名为`g_sns_imx675_obj`。
2. **建立注册关系。** 将产品侧的IMX675类型、NDK接收配置、模式表和驱动对象关联起来；本例有`SensorImx675Init`注册入口。
3. **纳入最终构建。** 编译驱动库、配置库及注册代码，并确认最终应用链接了它们。只生成一个`.a`库不等于应用已经使用它。

关系可理解为：

```text
产品选择“IMX675”
       ↓ 通过sensor类型找到注册项
NDK接收配置 + 可用模式表 + sensor驱动对象
       ↓ 根据请求的尺寸／FPS／WDR选择模式
调用驱动初始化及后续AE／AWB等回调
```

这是配置和对象关系图，不是完整函数调用栈。实际执行顺序以目标SDK为准。

**编号陷阱：** 本例IMX675在目标工程的sensor枚举为31，而某供体使用30，目标的30已属于其他sensor。因此要在目标枚举中追加并同步INI，不能复制供体数字，也不能重排旧枚举导致已保存参数含义变化。

### 5.4 菜单和构建：把“选中了”变成“编进去了”

本例菜单项的核心条件：

```kconfig
config SNS0_IMX675
    bool "sony_imx675"
    depends on HI3516CV610 && DRONECAM && HI3516CV610_LANE_DIVIDE_MODE_1
```

菜单选中后，构建层将它映射为sensor名称和编译宏：

```makefile
# 位于原有sensor选择条件链中，将菜单配置传给构建规则
else ifeq ($(CONFIG_SNS0_IMX675), y)
CFG_SENSOR_TYPE0 := imx675
KCONFIG_CFLAGS   += -DCONFIG_SNS0_IMX675
```

还需要把IMX675加入NDK的sensor编译列表，使注册条件成立；选择正确的产品参数目录和Scene参数目录；核对驱动库、配置库进入最终链接。

**判断方法：** 从菜单符号逐层向下搜索定义和使用位置，直到驱动注册与最终链接，不要停在菜单截图。已有按sensor名称自动选择库的规则就沿用，不必重复添加专用分支。

### 5.5 产品参数：同一个采集模式可以产生不同输出

驱动mode2采集1440P WDR25，产品层可以选择2K直出、4K放大或1080P调试预览。因此不能用最终VENC尺寸反推sensor应该配置成同样尺寸。

对应产品INI的采集部分节选：

```ini
[vcap.dev]
; 31是本工程的IMX675枚举值，2是已实现的WDR25模式
sensor_type = "31"
sensor_mode = "2"
sensor_width = "2560"
sensor_height = "1440"
; 本SDK此字段中1表示RAW10
data_type = "1"
```

在此基础上，产品层还要配置：

- VI／ISP输入与WDR曝光pipe；
- VPSS输出尺寸和帧率；
- VENC格式、分辨率、码率和缓冲；
- 录像、抓拍、子码流、缩略图等通道绑定；
- 每条处理链所需的公共VB及运行时私有缓冲；
- 可选档位、默认档、持久化参数与Scene索引。

第7节解释参数文件如何落到板端，第8节解释内存计算。修改INI后还要确认应用代码没有再次覆盖这些值。

### 5.6 板级与启动：确保上电后选择正确的时钟和设备

新sensor名称必须被板级代码识别，并选择正确的MCLK、复位及I2C／MIPI资源。本例启动参数包含：

```text
sensors=sns0=imx675,sns1=none
```

同一份设置可能来自升级配置、保存的U-Boot环境或U-Boot默认环境。如果只改升级配置，遇到环境CRC无效时仍可能回退到旧sensor名称，进而使用错误的时钟分支。

**为什么要检查默认回退路径：** 此前出现过sensor初始化成功，但实际帧率不对；最终通过真实启动参数和ISP周期发现运行条件并非预期。烧录文件内容正确，不代表板端正在使用它。以`cat /proc/cmdline`和实际硬件状态为准。

### 5.7 运行中切档：保证“保存的模式”和“运行的模式”一致

切档通常包括停止相关业务、停止或重建媒体、应用新参数、恢复Scene及流服务。以4K切换为例：

```text
收到4K请求 → 检查支持范围 → 停止相关业务 → 应用4K媒体配置
                                               ├─成功：确认运行状态并恢复服务
                                               └─失败：报告错误，按设计恢复旧配置和服务
```

如果提前保存“当前是4K”，但实际创建4K通道因内存失败，下次请求4K可能被误判成“不需要切换”。修正目标是保持参数与实际状态一致，并保留失败现场；不是不断重试同一个失败配置。

判断切档成功要同时看接口返回、实际sensor模式、VENC尺寸与帧率、重新连接后的预览／录像。不能只凭CGI返回`Success`。

## 6. 驱动移植最容易错的三个问题

### 6.1 改成两 lane，不等于只改 lane 数组

本次 NDK 物理映射示意：

```c
/* 本板复用原 GC8613 接口，只连接物理 lane0 和 lane2。 */
{ 0, 2, -1, -1, -1, -1, -1, -1 }
```

同时需要核对 sensor 的 LANEMODE、PLL、lane 速率、RAW 位宽、窗口、HMAX／VMAX 和 SoC 接收模式。供体四 lane 的完整表不能仅在接收端改成两 lane。

**怎么判断：** 先看供体表的配套条件，再看 SoC 接收限制；上板观察 MIPI 有效尺寸、VC、CRC／ECC 等计数是否持续增长，最后看稳定接收帧率。能读 I2C 只证明控制链部分工作，不证明 MIPI 链正确。

### 6.2 帧率要把初始化与 AE 回调一起算

本次驱动使用时序时钟 74.25MHz；外部 INCK 为37.125MHz。以下公式针对本次实现，不是所有 Sony sensor 的通用公式。

```text
行周期 = HMAX / 74,250,000 秒
Linear 帧率 = 74,250,000 / HMAX / VMAX
DOL2 帧率 = 74,250,000 / HMAX / FSC，本实现 FSC = 2 × VMAX

Linear30：HMAX=1100，VMAX=2250 → 30fps
WDR30：HMAX=750，VMAX=1650，FSC=3300 → 30fps
WDR25：HMAX=750，VMAX=1980，FSC=3960 → 25fps
```

本次供体 Linear 的基准为60fps。如果只替换成30fps初始化表，却保留旧 `cmos_fps_set()` 的 `2250×60/fps` 计算，请求30fps会把 VMAX 写成4500，新 HMAX 下就变成约15fps。

**为什么改回调：** 初始化只是第一次写寄存器，AE 会继续调用 FPS／曝光／增益更新；所有运行时默认值、行数和寄存器缓存必须与新模式同步。

**怎么验收：** 初始化日志核对计算值；运行后看 ISP 周期、VI／VENC 计数变化，再用录像文件时间戳验证。固定帧率需求还要验证暗处是否触发慢快门降帧。本次 WDR 固定25／30fps，暂不让慢快门回调改变 FSC。

### 6.3 WDR 不只是设置一个开关

本次 sensor 采用 DOL2 VC，接收侧使用 `OT_MIPI_WDR_MODE_VC`，ISP／VI侧采用 `OT_WDR_MODE_2To1_LINE`。两个名字来自不同层，不能看到“LINE”就擅自将 sensor 发送方式改成另一种格式。

必须同时检查：

1. 初始化表确实输出两个曝光，VC／数据类型与接收一致。
2. 主、副曝光 pipe 正确绑定到同一个融合组；SNS1 仍为 NONE，不另加第二颗摄像头。
3. CMOS 回调正确接收长短曝光请求，计算 SHR0、SHR1、RHS1，遵守有效范围、对齐、BRL 和跨帧约束。
4. 运行寄存器用正确的组保持与更新时机写入；切档时清空旧模式的曝光配对状态和缓存。
5. AE／AWB／Scene 作用于正确的 ISP，避免错误地为曝光辅助 pipe 再起一套不需要的 Scene。

本实现中，曝光行数可按 `长曝光=FSC−SHR0`、`短曝光=RHS1−SHR1` 理解，但合法边界和相邻帧约束必须查 IMX675 DOL 手册及当前实现，不能只代公式后截断到任意范围。

本次还修正过 RAW 裁剪起点：OB 使用独立数据类型 `DT 0x37`，不能直接计入 `RAW10 DT 0x2B` 的行坐标。当前 WDR 接收裁剪起点为 `(8,12)`，有效尺寸2560×1440。这个坐标是本模式的数据格式推导结果，不是换任何 sensor 都能复制的常量。

## 7. 产品 INI、Scene 和板端参数如何真正生效

### 7.1 产品参数：四类文件必须互相对得上

| 文件 | 作用 | 检查方法 |
| --- | --- | --- |
| `config_cfgaccess_entry.ini` | 登记参数模块和各模式文件 | 每个模块名对应的文件必须存在；模块数量与登记项一致。 |
| `config_product_valueset.ini` | APP／CGI可选项文字与模式枚举映射 | UI文字对应枚举，枚举必须能在媒体配置中找到；文件名不是唯一依据。 |
| `config_product_workmode_record.ini` | 默认录像模式、录像缓存等 | 默认档必须存在；区分默认值与板端持久化的用户选择。 |
| `config_product_mediamode_cam0_record_*.ini` 及公共配置 | sensor、VI、ISP、VPSS、VENC、VB | 分清公共项、模式覆盖项和运行时代码的再次修改，核对最终有效值。 |

当前 IQ 参数目录有5个媒体配置，包含4个录像选项和1个照片档。参数数组长度由构建中的 `media_cnt.sh` 计算。增加模式后，不仅要放一个 INI，还要检查参数核心与转换工具是否按新数量重新生成。

### 7.2 这是两套不同的参数来源

```text
产品 INI → 参数转换工具 → rawparam／rawparambak 等产品参数镜像
         → 板端参数加载 → 媒体配置和业务配置

Scene INI → scene_ini2bin → sceneparam.bin
          → 固件 /app/sceneauto/sceneparam.bin → Scene 初始化／切模式

Sensor 驱动默认 IQ → ISP／AWB 等初始化
PQTools 临时修改 → 当前运行时 ISP 参数
```

因此，板端正常运行时**不是直接读取 Windows 的 `sensor_imx675` 目录中的 INI**。改源 INI 不重新转换、打包和升级，板端不会自动变化；只更换 SD 上的 PQ 程序也不会更新产品媒体参数。

**Scene 报错实例：** `Load [static_nr:coring_ratio] failed` 出现在 PC 端 `scene_ini2bin` 转换阶段，说明配置格式／字段不匹配，不是 MIPI 不出图。应沿报错查 `scene_loadparam.c` 的必读键、数组长度和对应 SDK 头文件宏；只关闭某模块不一定能绕过加载器对字段的读取。

供体 Scene 可以提供起始参数，但必须按目标 SDK 结构补齐。复用其他 sensor 参数使转换通过，不代表 IMX675 的颜色、降噪、黑电平和镜头校正已经调好。

### 7.3 切档时不要假定临时 IQ 自动保留

本工程切档会停止相关服务、重置或重建媒体；Scene 启用时会重新初始化并设置模式。即使两个档位都使用 Scene idx2，也不能承诺 PQTools 临时下发的全部参数跨切档保留。

正确操作是先导出调参结果，断开 PQ 后切档，再连接并确认参数；需要时按对应模式重新下发。最终固化应将结果按工具格式整理进相应 Scene／驱动配置，重新转换并验证重启后仍生效。

## 8. 内存要算整条链，不能只数 VB

### 8.1 区分四种资源

| 资源 | 主要用途 | 常见误判 |
| --- | --- | --- |
| Linux RAM | 应用、协议栈、普通堆、文件缓存等 | 看到 `free` 有余量，就认为媒体能继续分配。 |
| anonymous MMZ | VI／ISP／VPSS／VENC 的媒体缓冲和工作区 | 只合计公共 VB，遗漏 WDR、编码参考帧、JPEG、OSD 等私有分配。 |
| ringbuf_mmz | 本工程独立录像缓存 | 将剩余 ringbuf 算到匿名媒体区，错误地认为可以供 JPEG／RAW 使用。 |
| Flash／SD | 固件及工具存储 | PQ 程序放SD解决Flash容量，不会消除运行时抓RAW的内存占用。 |

本次内存优化参考 HC112_B 的机制：确认纯 Linux 产品不再使用 PARAM／RES 的两块 DDR 预留后，回收2MiB给 anonymous，保持 Linux44MiB 和录像 ringbuf7740KiB。当前布局示例：

```text
mem=44M
mmz_zones=anonymous,0,0x42C00000,78276K:ringbuf_mmz,1,0x47871000,7740K
```

这不是删除Flash的`rawparam/rawparambak/resImage`分区，也不是其他平台可以直接照抄的节省办法。实现时必须同步处理四件事：重新生成无重叠的启动内存布局；避免时间戳继续使用已取消的预留区；让纯Linux参数加载不再错误要求该物理地址；将正常启动与U-Boot默认回退参数保持一致。只把预留大小改成0，可能导致启动或参数加载失败。

### 8.2 先估算，再用 SDK 公式与 proc 确认

```text
公共 VB 占用 = 各池 blk_size × blk_count 的总和
2560×1440、紧凑 RAW10 的有效字节数 = 2560×1440×10/8 = 4,608,000
一组长短曝光有效数据 = 9,216,000 字节，约8.79MiB
六块上述 RAW10 缓冲 = 27,648,000 字节，约26.37MiB
2560×1440、8-bit YUV420 有效数据 = 5,529,600 字节
```

这些是特定布局下的估算。实际缓冲还受 stride、对齐、压缩头、附加信息和队列深度影响。RAW若展开到16-bit容器，一组长短帧约14.06MiB；不能把 packed RAW10 文件大小直接当成任何 API 缓冲大小。

当前2K精简档运行时保留三组公共池：`5529600×2 + 4608000×6 + 3743744×3`，合计47.625MiB。其中3743744来自目标SDK的 SEG_COMPACT 计算，不是简单 `宽×高×1.5`。仍需另外统计ISP／编码器等私有内存。

### 8.3 两种“停止”必须分清

关闭 PotPlayer、停止 SD 录像，只代表业务暂时不消费码流，**不一定销毁 VENC／JPEG／VPSS 通道或释放对应内存**。要证明节省，必须比较停止前后的 `/proc/umap/media-mem`、`vb`、`venc` 等实际占用。

精简调试档关闭抓拍和子码流，要同时处理：VENC启用、VPSS输出、照片任务、缩略图绑定、OSD绑定、RTSP别名及无用VB池。只把一个INI的enable改0，业务层可能仍去创建或使用被关闭的句柄。

### 8.4 码率与录像缓存的关系

本次主H.265配置保留QVBR，参数为22528kbps，项目中按 `22×1024` 称为22Mbps档；不等于实际码流始终固定在这个数值。静态场景实际更低，不能仅凭播放器瞬时码率判定配置没生效。

缓存粗算应先统一单位，再用代码实际换算规则核对：

```text
视频数据量约等于 配置码率 × 缓存时间 / 8
```

还需计入音频、索引和分段管理余量，并核实分配来自哪个区。增加 `recbuffer_time0=2300ms` 不能解决 MIPI 帧率或 RTSP 延时问题，也不能在没有预算的情况下无限增加。

## 9. 编译、升级与首次出图的验证顺序

### 9.1 构建前的静态核对

- sensor 枚举、驱动模式、NDK模式、INI的sensor_type／sensor_mode逐项对应。
- sensor发送尺寸、接收裁剪、ISP输入和VPSS输入一致；输出尺寸另列。
- driver FPS基准、AE默认值、VMAX／FSC一致。
- Scene登记、必读字段、数组长度、模式索引完整。
- 菜单宏、驱动库、NDK配置库、参数目录和bootargs都选到同一sensor。
- 保留现有文件换行符；新增或修改的代码注释写中文。使用 `git diff --check` 和文件差异复查，避免整文件换行转换掩盖真正修改。

### 9.2 构建与升级

本项目常用构建入口为 `make reference`。新增模式造成参数数量变化时，需先按工程流程清理并重建参数核心和转换工具；修改NDK、驱动或内核时，也必须重建对应层，而不是只打包rootfs。

以下由开发人员在Linux服务器执行，不是本文已经执行的操作：

```sh
# 将下一行替换为自己的PQ调试工程根目录
PROJECT=/path/to/your/pq_project
cd "$PROJECT"
# 修改参数档数量后，先清理参数模块，避免沿用旧结构大小
make -C source/camera/demo/dronecam/modules/param clean
make reference
```

这两行不是所有修改的完整清理方案。若还改动驱动、NDK或内核，按依赖补齐对应重建。核对构建输出、时间／哈希、参数档数量与最终镜像，升级时保证内核、应用、参数和启动配置匹配；不能仅凭“整包”二字假设所有分区必然更新，应查升级日志和板端结果。

本次发现过U-Boot环境CRC无效、SD无配置后落到默认环境，使用了旧sensor启动参数。处理方法是同时修正常规生成链和默认回退链，最终以 `/proc/cmdline` 为准。

### 9.3 每次上板保存一套证据

板端串口命令，只读取状态：

```sh
cat /proc/cmdline
cat /proc/meminfo
for node in mipi_rx vi isp vpss venc vb media-mem; do
    # 节点名称以当前 SDK 为准，只读取实际存在的节点
    if [ -r "/proc/umap/$node" ]; then
        echo "===== $node ====="
        cat "/proc/umap/$node"
    fi
done
dmesg
```

记录完整开机日志、固件来源、档位、操作时间，并保存几秒间隔的两组proc快照。累计错误数要看是否继续增长，不能看到一个历史非零值就判定当前持续故障。

## 10. 怎样判断移植成功

按层验收，未通过哪层就停在哪层定位。后一级成功不能代替前一级的全部正确性。

| 层级 | 要证明什么 | 有效证据 | 不能当作通过的证据 |
| --- | --- | --- | --- |
| 供电／I2C | Sensor真正可控 | 电压／时钟测量；按手册读取允许读取的标识或状态寄存器；读写返回值正确 | 无条件返回固定值的read函数；仅打印init success |
| MIPI接收 | 数据格式和接收窗口正确 | lane／VC／DT、检测尺寸正确，错误计数不持续增长 | I2C有响应；菜单已选择 |
| VI／ISP | 实际持续收帧并处理 | 计数持续增长，周期接近30fps的33.33ms或25fps的40ms，两曝光路径与融合组正确 | 把主在线pipe某个统计字段为0直接当成无帧；只看初始化日志 |
| WDR | 两曝光确实参与且控制正确 | 两路RAW、合法曝光参数、亮暗区域及运动场景验证 | 文件名带WDR；看到一幅正常画面；只开一个枚举 |
| VPSS／VENC | 尺寸、帧率和资源正确 | 输入／输出尺寸对应，编码帧计数、丢帧统计、实际流参数正常 | 把YUV存储格式LINEAR当成sensor线性模式；把SDR8当作未做WDR |
| 录像／预览／抓拍 | 产品功能完整 | 可解码录像、正确PTS和音画同步；跨分段点；主JPEG计数与照片尺寸；反复切档 | CGI只返回Success；只创建了JPEG通道而未实际拍照 |
| 稳定性与IQ | 可持续交付 | 冷启动、亮暗切换、长时间录像、按需求并发、抓RAW后恢复、内存不持续减少；IQ场景验收 | 一次短时间出图；使用供体IQ就宣布画质完成 |

本次已经有Linear30与WDR30的运行帧率证据，也有MMZ优化后4K放大编码25fps和短录像的证据。它们说明相应阶段运行成功，不覆盖所有后续PQ改动、长期稳定性或4K双曝光RAW。

用户已反馈1080P档双曝光RAW成功、抓后恢复正常；PQ RAW25在选对10 bits后反馈能抓取。当前默认2K的最新构建／上板结果仍应另存记录，正常4K双曝光RAW不能据此自动判定通过。

## 11. 如何搭建本项目的 PQ 环境

### 11.1 分清 Windows端、板端和媒体应用

| 部分 | 职责 | 本次位置 |
| --- | --- | --- |
| Windows PQTools | 参数读写、Dump Tool、相关调试界面 | 在PC上解压匹配版本的工具包，运行其中的`PQTools.exe` |
| 板端 `ittb_control` | 接收PQ命令，调用目标SDK接口 | `/app/sd/pqtool/ittb_control` |

向项目负责人获取Hi3516CV610R001C01SPC020对应的软件包，其中`01.software/common pc/PQTools`提供本例使用的PC工具。不同项目以自己的SDK版本为准。选择与SoC、SDK版本匹配的PC模板和板端工具，不根据“能打开界面”判断二进制兼容性。

本次采用**工具和依赖库放SD，固件放启动脚本**的方式，原因是appfs剩余空间不足以容纳整套工具。与此同时，Scene CGI、水印和自动录像规则还涉及应用源码修改；“只接入启动脚本”描述的是工具部署方式，不表示调试固件只有一处代码改动。

不要另起一套 sample 或 `ittb_stream` 抢占 sensor／VI／ISP。本方案使用已有main_app的媒体链，启动控制服务。

### 11.2 IQ工程中的准备与打包

当前配置：

### 11.3 板端先确认服务，再连Windows

在设备串口执行：

```sh
ifconfig
mount | grep /app/sd
ls -l /app/sd/pqtool
/app/bin/PQTools.sh status
# 服务没有运行时再启动
/app/bin/PQTools.sh -c
netstat -lnt | grep ':4321'
```

本次设备Wi-Fi地址为 `192.168.0.1`，电脑可能是 `192.168.0.20`。两者不能反过来填写。Windows连接摄像头Wi-Fi后可执行：

```powershell
Test-NetConnection 192.168.0.1 -Port 4321
```

如果板端不监听4321，先查进程退出、动态库、挂载权限和媒体是否已启动；如果监听正常而PC连不上，再查IP、路由和网络。不要看到“socket错误”就先改sensor。

SD默认可能以 `noexec` 挂载：文件有执行权限仍会报 `Permission denied`。当前脚本会在PQ启动时执行 `mount -o remount,exec /app/sd`。判断依据是 `/proc/mounts`，不是只看 `ls -l`；单独 `chmod` 不能解决noexec。

### 11.4 暂停Scene，防止自动参数覆盖

Windows PowerShell直接复制以下命令。不要把Markdown的`[文字](链接)`整段放进curl参数：

```powershell
# 暂停 Scene 自动更新，之后再进行手动调参
curl.exe "http://192.168.0.1/cgi-bin/hisnet/setsceneauto.cgi?-sceneauto=0"

# 调试结束后恢复 Scene
curl.exe "http://192.168.0.1/cgi-bin/hisnet/setsceneauto.cgi?-sceneauto=1"
```

核对返回正文为 `Success`，而不是只看HTTP连接成功。当前实现直接调用Scene暂停／恢复，并返回调用结果。

**Scene暂停不等于ISP停止，也不等于锁定AE／AWB。** 如果需要固定曝光、增益或白平衡，要另外设置、记录并在测试后恢复。避免在抓RAW或PQ调参过程中同时通过APP切档。

### 11.5 用CGI选择档位，用RTSP观察主画质

切档前停止录像、关闭播放器，导出未保存的IQ；退出Windows PQ连接并在板端停止控制服务。媒体稳定后再启动控制服务、重新连接。

```sh
# 在板端串口执行
/app/bin/PQTools.sh stop
/app/bin/PQTools.sh status
```

Windows PowerShell按目标执行其中一条设置命令，再查询：

```powershell
$cgi = 'http://192.168.0.1/cgi-bin/hisnet'

# 2K 直出，当前源码默认档
curl.exe "$cgi/setcamparam.cgi?-workmode=NORM_REC&-type=MEDIAMODE&-value=1440P25FPS%20WDR"

# 1080P30，采集仍是 1440P WDR30
curl.exe "$cgi/setcamparam.cgi?-workmode=NORM_REC&-type=MEDIAMODE&-value=1080P30FPS%20WDR"

# 专用 RAW25 对照档
curl.exe "$cgi/setcamparam.cgi?-workmode=NORM_REC&-type=MEDIAMODE&-value=PQ%20RAW25%20WDR"

# 4K25 放大编码档
curl.exe "$cgi/setcamparam.cgi?-workmode=NORM_REC&-type=MEDIAMODE&-value=4K25FPS%20WDR"

# 查询实际选择
curl.exe "$cgi/getcamparam.cgi?-workmode=NORM_REC&-type=MEDIAMODE"
```

不要将四条设置命令一次全部执行。CGI选项文字来自当前valueset；如果别的版本改名，以该版本的值集为准。

主流预览地址：

```text
rtsp://192.168.0.1:554/livestream/11
```

切档会重建流，播放器可能需要重新打开连接。`Success`只表示接口返回成功，仍应核对当前档位、VENC尺寸、实际帧率和新RTSP会话。

### 11.6 抓取WDR长短曝光RAW

第一次测试选择已经验证过的离线档，停止录像和外部预览，保留完整板端日志与PC日志。当前配置RAW10，Dump Tool选择：

| 设置 | 本次值 |
| --- | --- |
| Pipe | PIPE0 |
| Bits | 10 bits；不能选12 bits |
| Mode | 先按故障定位需要分别测试VCNUM0／VCNUM1，最终用WDR(2in1)获取同次请求的双曝光数据 |
| Captimes | 1 |
| Multiple／连续抓取 | 初次验证关闭 |
| Raw Info | 本次故障对照先取消；需要完整元数据时，基础抓取通过后另行验证附加信息路径 |

两次单独抓到VCNUM0和VCNUM1，不等于它们是同一WDR周期。最终要核对2in1输出格式、两曝光顺序、帧标识／PTS及可获得的曝光元数据。不同曝光可能有正常的时序偏移，不能只要求任意两帧PTS完全相等。

当前抓取的有效RAW来自2560×1440采集，不按3840×2160解释。packed RAW10单曝光有效数据约4,608,000字节；本次PC日志中收到4,608,152字节包，包含额外协议信息，不能直接将网络包长当成最终文件大小或固定头长度。

完整成功需要同时满足：

1. PC期望的两曝光数据均接收完成，校验通过，无第二包长度失败。
2. 输出文件符合工具规定的容器／打包格式，正确解码出图。
3. 确认长短曝光关系及帧配对，不能只看文件数量或板端 `out frame count:2`。
4. 抓取完成后能恢复预览、录像，反复抓取不持续减少可用内存。

### 11.7 RAW失败怎样判断

| 现象 | 先判断什么 | 本次经验 |
| --- | --- | --- |
| VCNUM0能抓，VCNUM1失败 | 第二曝光的帧描述、物理地址、在线／离线链和映射方式 | 已出现 `invalid mmap addr:0x0` 及 `cacheable conflit`，不能直接认定是Wi-Fi慢。 |
| 2in1第一包成功，第二包长度获取失败 | 对应时刻板端第二曝光获取／映射／发送是否失败 | 第一包校验通过说明至少第一路数据传输成立，不代表第二路采集成立。 |
| `cacheable conflit` | 同一物理内存是否存在不一致的缓存属性映射 | 这是具体映射冲突证据，优先查MMZ映射和采集方式，不是笼统增加录像缓存。 |
| 10bit固件选12bits | 工具请求与真实格式是否一致 | 本次选错位宽导致测试无效，必须先统一格式再评估内存。 |
| PC弹窗提示“可能内存不足” | 板端到底是NO_MEM、超时、零地址还是映射冲突 | PC通用提示不是根因；不能据它直接修改MMZ。 |
| 已停录像／播放器仍失败 | 对应通道和缓冲是否真正释放 | 停止业务不等于销毁编码资源；查proc确认。 |

本次将1080P链改为主副pipe均离线并配置六块RAW缓冲后，用户反馈双曝光抓取成功。这个结果只证明该配置和对应工具组合有效，不能推出所有在线WDR都不能抓RAW，也不能推出4K输出档照搬相同池表一定有内存。

### 11.8 ISP Simulator的Send RAW另行验收

本次Simulator出现过 `Failed to send raw data. Communication interrupted.`，当时只导入了一个单曝光文件，而板端为双曝光WDR链。

应首先核对输入数据是否满足所选WDR模式：完整双曝光数据、尺寸、位深、打包／stride、Bayer、曝光顺序、工具版本和必要元信息。单曝光缺少另一曝光，是输入条件不完整的依据；但仅凭该弹窗仍不能认定唯一根因就是文件数量。

此外，RAW抓取是“从板端读数据”，Simulator Send RAW是“把数据送入指定处理链”，方向和运行条件不同。需要确认本版工具要求的回放／输入源模式及板端接收日志，不能把抓取成功直接视作Send RAW已可用。当前尚未将Simulator回灌闭环作为已验证结果。

### 11.9 水印和业务行为：方便调试，但不能误当量产行为

本次将时间水印的文字生成逻辑改为：向主ISP查询曝光和白平衡信息，检查查询结果，然后生成`L / S / Ag / IspDg / CT`文本，继续使用原来的OSD显示通道。查询失败显示横线，不使用未初始化的数据。

| 字段 | 表示什么 | 查看时注意 |
| --- | --- | --- |
| L／S | 长／短曝光时间 | 本例显示单位为微秒；字段映射需按SDK确认。 |
| Ag | 模拟增益 | 当前显示SDK原始值，不直接当作倍数或dB。 |
| IspDg | ISP数字增益 | 同样要查SDK比例定义。 |
| CT | 色温 | 本例单位为K，观察AWB变化。 |

本工程当前API映射下，2-to-1 WDR的L取 `shortExpTime`、S取 `expTime`；`longExpTime`不能因名字带long就直接当作这两曝光中的长曝光字段。该映射需结合目标SDK定义、适配层与实测确认，不推广为所有平台的规则。水印也不是RAW逐帧元数据。

当前显示格式使用 `%u`，没有保留早期 `%10u` 的固定宽度。若修改显示字段，检查OSD最大宽度和边缘裁切，不能只看打印字符串是否正确。

本次调试版还跳过语音识别引擎初始化、部分开机自动录像触发；录音和提示音不是同一功能。其他自动录像路径仍可能存在，不能据“开机没录像”就断言抓RAW期间永远不会启动录像。停止PQ服务也不会自动撤销这些源码级调试改动。

## 12. 排错时使用“证据 → 假设 → 最小修改 → 复测”

每次只改变能验证当前假设的因素，保留修改前后同场景日志。下面是本次可复用的实例：

| 问题 | 怎么判断 | 为什么这样修改 | 修改后应看到什么 |
| --- | --- | --- | --- |
| Linear声明30fps，实际约22fps | 对比`/proc/cmdline`、时钟分支与ISP周期；发现默认启动参数仍是旧sensor | 补齐U-Boot默认回退路径，使板级时钟选择与IMX675一致 | 启动参数正确，VI／VPSS／VENC实际30fps；不能只看MIPI频率打印 |
| Scene转换中断 | 报错发生在PC转换器且指向明确INI键 | 按目标加载器补字段、数组和格式，不先改I2C | 转换成功、板端加载对应Scene；随后单独验收IQ |
| WDR初始化成功但收帧异常 | 核对VC、DT和有效尺寸，发现RAW裁剪坐标包含了另一DT的OB行 | 修正接收坐标，并对照同平台融合链 | 两曝光有效尺寸正确，计数增长，融合正常 |
| APP切4K后又回1080P | 查到VENC／JPEG创建NO_MEM及恢复流程 | 先按实际YUV格式纠正VB，再基于明确依据回收DDR预留 | 4K创建成功；若失败，已保存档位和实际媒体状态保持一致 |
| 已改INI却仍运行旧档 | 检查entry、valueset、持久化参数、参数镜像和实际启动日志 | 打通参数生成／升级／模式归一路径 | 运行档位、sensor mode和VENC尺寸一致 |
| PQ无法连接 | 板端ifconfig显示`.1`，PC曾填`.20`；再查4321监听 | 先用正确设备IP，再解决服务启动条件 | TCP可达，PQ能读取主ISP参数 |
| 长曝光水印L一直0 | 其他字段正常，核对SDK曝光结构及2-to-1字段映射 | 修改字段来源，避免使用不适用于本模式的longExpTime | L／S均有合理数值并随场景变化 |
| 复制工程后仍依赖原工程 | `find`与`readlink -f`显示跨目录SDK链接 | 将需要独立的引用调整到副本自身，验证实际库搜索路径 | 原工程回退或移动不再影响副本对应构建 |

排查运行时代码时，先按职责寻找入口，而不是从报错行盲目向外跳：

| 想确认的问题 | 应找的模块 | 读代码时追踪什么 |
| --- | --- | --- |
| INI有没有被运行代码覆盖？ | 产品参数组装模块 | 读到的原值、条件分支、写回的最终媒体配置。 |
| 为什么保存的档位没生效？ | 工作模式／参数归一模块 | 旧值是否被判为不支持、默认回退是什么、持久化在何时更新。 |
| 为什么切档后RTSP断流？ | 状态机与媒体服务模块 | 旧流删除、新通道创建、Scene重启、新流注册及失败返回。 |
| 关闭抓拍后为什么仍占内存？ | 照片任务及通道绑定模块 | 是否仍创建JPEG或缩略图，是否仍有OSD／VPSS消费者。 |
| PQ命令是否真的执行？ | CGI入口和对应API调用 | 参数解析、忙状态、实际调用返回值及响应正文。 |

附录A将这些职责映射到本工程文件，正文的判断方法不依赖具体函数名。

还遇到过编译报错：`OT_MEDIA_VencAttr has no member named payloadTypeAttr`。应查**目标SDK实际类型定义**，本工程正确访问层级为 `vencChnAttr.payloadTypeAttr`。这类报错是接口结构不匹配，不能通过修改码率或关闭编译告警解决。

## 13. 建议按六个阶段交付，而不是一次改完再猜

| 阶段 | 主要工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：确认与基线 | 模组／SoC／接口／模式资料，保存完整基线，检查链接 | 需求表明确，回退点可验证，关键资料缺口列明 |
| B：最小点亮 | 允许时先用已知Linear模式打通I2C、MIPI、VI／ISP | 有效图像、实际帧率、曝光增益变化正常 |
| C：目标WDR | DOL寄存器、双曝光控制、接收与融合、对应Scene | 两曝光、融合和实际帧率有证据，切档可恢复 |
| D：产品化 | 菜单、参数镜像、录像、预览、抓拍、内存 | 正常业务与并发通过，异常路径不假报成功 |
| E：PQ与RAW | 对应版本工具、SD部署、离线抓取条件、调试流程 | 配对RAW及参数读取成功，退出后业务恢复 |
| F：IQ固化与回归 | 模组／镜头标定，固化Scene／驱动参数，去除调试限制 | 冷启动和重启可复现，画质、稳定性、正式功能全部验收 |

本次最初允许Linear点亮，随后产品菜单中的Linear调试入口已移除，底层参考模式仍保留。通用流程中的“先Linear”不是要求重新打开当前产品的Linear菜单。

## 15. 转发与交接时应同时给同事什么

本文中的原理和流程无需外部链接即可阅读。实际开始移植或上板时，还需要以下交接材料；这是工程输入，不能由一份说明文档替代。

| 材料 | 应包含的内容 | 对方拿到后怎样核对 |
| --- | --- | --- |
| 工程基线 | 完整工程或可复现提交、必要补丁、config、分支与版本说明 | 能确定当前选中的sensor、SDK版本和编译入口；工程副本无意外跨目录依赖。 |
| Sensor资料 | 对应完整料号的datasheet、软件手册、DOL说明、寄存器表及版本 | 时钟、lane、RAW格式、窗口和帧率与需求一致；区分同系列不同后缀。 |
| 板级资料 | 原理图、模组接口、供电／复位／MCLK／lane映射 | 能按第2节核对实际连线；不是只有旧sensor名称。 |
| 平台文档 | 匹配SDK的Sensor适配、Sensor调试、MIPI和ISP接口文档 | 结构体、枚举、缓冲算法和错误码与正在使用的SDK一致。 |
| PQ工具 | PC工具、板端程序、匹配库、项目启动脚本、配置和版本记录 | 端口／pipe正确；能说明每个文件来自哪个SDK或工具包。 |
| 测试证据 | 固件哈希、从开机开始的日志、档位、操作顺序、proc、RAW和视频样本 | 知道结果对应哪一版，哪些项目成功、哪些尚未验收。 |
| IQ结果 | 参数导出、对应模式和模组／镜头信息、固化方法 | 重新上电后仍可复现，区分临时PQ下发与固化参数。 |

本例原始资料中曾混有IMX335文档，也存在与实物AAQR-G后缀不同的IMX675手册。交接时要明确标注适用性，不能把同文件夹内的资料都当成同一颗sensor的依据。

移植时始终保留“代码状态、板端状态、测试结论”三者的对应关系。排错时先问证据能证明到哪一层，再选择最小修改；调试配置通过后，还要回到正式产品需求逐项验收。

## 附录B：修改前先写下这四句话

```text
观察到的事实：在哪个版本、哪个档位、做了什么操作，出现什么日志或现象？
当前假设：最可能是哪一层不一致，有哪条证据支持，什么尚未证实？
最小修改：只改哪项设置或哪段代码，预期改变哪个可观察结果？
验证结果：是否出现预期变化，是否引入新问题，能否重复和回退？
```

例如：观察到VCNUM0接收完成、VCNUM1映射报错；假设问题在第二曝光的取帧／映射条件；先核对RAW位宽和在线／离线链，不同时调整码率、时钟与Wi-Fi。这样复测结果才能支持或否定当前假设，而不是只得到“一次碰巧成功”。
