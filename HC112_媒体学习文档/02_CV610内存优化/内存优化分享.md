### 2.1 物理地址划分（config.conf）

本项目 64M DDR 自 `0x40000000` 起，按地址**顺序切分**为两段（参数区/资源区不占 DDR 空间）：

```
0x40000000                                                      0x44000000
├──────────────────────────┬────────────────────────────────────┤
│   Linux OS 分区           │   MMZ 媒体内存                      │
│   34 MB                   │   30 MB                            │
│   0x40000000~0x42200000   │   0x42200000~0x44000000            │
└──────────────────────────┴────────────────────────────────────┘
         ↑ bootargs mem=34M              ↑ mmz_anonymous
         free 统计范围                    /proc/media-mem
```

**根目录** `config.conf` **当前值**：


| 区域            | 配置项                                   | 当前值                  | 大小                               |
| ------------- | ------------------------------------- | -------------------- | -------------------------------- |
| 总 DDR         | `CONFIG_MEM_TOTAL_SIZE`               | `"64"`               | 64 MB                            |
| Linux OS 起始   | `CONFIG_MEM_LINUX_SYS_BASE`           | `0x40000000`         | —                                |
| Linux OS 大小   | `CONFIG_MEM_LINUX_SYS_SIZE`           | `0x2200000`          | **34 MB**                        |
| 参数区 PARAM     | `CONFIG_MEM_PARAM_BASE` / `SIZE`      | `0x42200000` / `0x0` | **0**（不占空间）                      |
| 资源区 RES       | `CONFIG_MEM_RES_BASE` / `SIZE`        | `0x42200000` / `0x0` | **0**（不占空间）                      |
| MMZ 起始        | `CONFIG_MEM_LINUX_MMZ_BASE`           | `0x42200000`         | —                                |
| MMZ 大小        | `CONFIG_MEM_LINUX_MMZ_SIZE`           | `0x1E00000`          | **30 MB**                        |
| MMZ anonymous | `CONFIG_MEM_LINUX_MMZ_ANONYMOUS_SIZE` | `0x1E00000`          | 30 MB（`SSGO_SIZE=0`，无 ringbuf 段） |


**容量验算**：34 + 30 = **64 MB**。

### 2.2 启动参数与编译替换



#### 2.2.1 boot 模板 vs 编译替换

**boot 模板**（`[config_squashfs_jffs2_spinor_linux_smp](../source/camera/demo/dronecam/rootfs/configs/hi3516cv610/config_squashfs_jffs2_spinor_linux_smp)`，`mem=44M` 为占位）：


**Makefile 编译时仅自动替换**（`[rootfs/Makefile](../source/camera/demo/dronecam/rootfs/Makefile)`）：


| 项目          | 是否 sed 替换   | 计算方式                             | 编译后值                                |
| ----------- | ----------- | -------------------------------- | ----------------------------------- |
| `mem=`      | **是**       | `CONFIG_MEM_LINUX_SYS_SIZE / 1M` | `**mem=34M`**                       |
| `mmz_zones` | **否**（模板遗留） | —                                | 仍为模板里的 `0x42200000,23552K:...7168K` |
| `sensors=`  | 按 sensor 配置 | CONFIG_SNS0_*                    | 如 `sns0=sc431hai`                   |


```makefile
# rootfs/Makefile — 仅替换 mem=，不替换 mmz_zones
sed -i 's/mem=.*M /mem=$(CFG_LINUX_SYS_LEN)M /g' $(PDT_OUT_BURN)/config
```

> **注意**：`mmz_zones` 写在 u-boot boot 模板里，Makefile **仅替换** `mem=`，不会自动同步 MMZ。板端实际布局以 bootargs 为准，与 `load_module` 注入值相互独立。



### 2.3 OS 与 MMZ 的分工


| 内存           | 管理者    | 用途                    | 查看方式                                   |
| ------------ | ------ | --------------------- | -------------------------------------- |
| Linux OS 34M | 内核伙伴系统 | 应用、WiFi、文件 cache、ZRAM | `free` / `/proc/meminfo`               |
| PARAM / RES  | —      | 不占 DDR 空间（`SIZE=0`）   | —                                      |
| MMZ 30M      | MPP 驱动 | VI / VPSS / VENC 的 VB | `/proc/umap/media-mem`、`/proc/umap/vb` |


**优化思路**：OS 34M 侧应**先量化 WiFi 占用**（§3.1），再考虑 Kernel 裁剪 + ZRAM + VM 调优；MMZ 30M 通过 VB 精算、卷绕控制业务峰值。

### 2.4 为什么 `free` 的 total 是 26552（约 26M），不是 34M？

`free` 的 **total** = `/proc/meminfo` 的 **MemTotal**，只反映 Linux 伙伴系统在 Kernel 初始化**之后**还能管理的内存。

#### 理论说明

**第一步：34M 是 OS 分区配置，不是 MemTotal**

- `CONFIG_MEM_LINUX_SYS_SIZE = 0x2200000` → 物理 DDR 划给 Linux **34M**。
- 编译后 bootargs `**mem=34M`** 告知内核可用物理 RAM 范围。

**第二步：Kernel 启动自留约 8M，不计入 MemTotal**


| 占用项                   | 说明                  |
| --------------------- | ------------------- |
| uImage 解压后的 Kernel 本体 | mini 方案约 **8.1 MB** |
| 页表、内核栈、per-CPU        | 架构固定开销              |
| `min_free_kbytes`     | `bootapp` 设 1024 KB |


```
MemTotal ≈ mem=34M − Kernel自留 ≈ 34816 KB − 8264 KB ≈ 26552 KB
```

**第三步：本项目实测**

```bash
~ # free
              total    used    free  shared  buff/cache  available
Mem:         26552   14728    1904       4        9920       8112
Swap:         8188    5632    2556
```


| 概念                         | 大小                   | free 能否看到            |
| -------------------------- | -------------------- | -------------------- |
| 整颗 DDR                     | 64 MB                | 否                    |
| Linux OS 分区（config / mem=） | 34 MB                | 否                    |
| Kernel 自留                  | ~8 MB                | 否                    |
| **MemTotal（free total）**   | **26552 KB ≈ 26 MB** | **是**                |
| PARAM + RES                | 0（不占 DDR）            | 否                    |
| MMZ                        | 30 MB                | 否（`/proc/media-mem`） |




#### 通俗理解

1. **64M 切成两块**：Linux 34M + 摄像头仓库 MMZ 30M（参数区/资源区不占 DDR 空间）。
2. **free 只统计 Linux 34M 那块**，内核先占约 8M，剩约 26M 才是 total。
3. **34M 是划地尺寸，26552 是净可用量**，不矛盾。
4. MMZ 30M 去 `**/proc/media-mem`** 看；**available 8112** 比 free 1904 更能反映实际余量。

## 3. OS 内存优化详解

> **问题单 HSCP2025082045311**：64M DDR 方案 MMZ 不足（`no free mmz` / VB 分配失败），需同步优化 OS 与 MMZ。  
> **OS 验证指标**：`free` **available > 6M**；MMZ 峰值 **< 27M**（见 **§4**）。  
> **关联提交**：`doc/OS内存.patch`  
> **涉及文件**：`linux-5.10.221.patch`、`bootapp`、`ss_hal_wifi.c`、`config.conf`

问题单 HSCP2025082045311

**推荐顺序**：64M 方案 OS 余量有限，**优先评估 WiFi 占用**（§3.1）——若单模块超 3M，换模块或找 WiFi 厂裁剪往往比 Kernel 裁剪收益更大；确认 WiFi 可接受后再做 §3.3 起的内核与运行时调优。

### 3.1 WiFi 内存评估与优化思路

64M 方案 OS 侧余量有限，**WiFi 是主要 OS 内存消耗者之一**。新项目选型或内存紧张时，**应先量化 WiFi 占用**，再决定是否换模块或找 WiFi 厂裁剪；不要一上来就裁剪 Kernel。

#### 3.1.1 测量方法：开/关 WiFi 对比 free

在系统稳定、无其他大业务干扰时：

```bash
# 1. 确保 WiFi 未加载，先 drop cache 使基线干净
echo 3 > /proc/sys/vm/drop_caches
free

# 2. 打开 WiFi（AP 或 STA 按产品实际模式）
#    通过应用或 SS_HAL_WIFI_Init / SS_HAL_WIFI_Start 拉起
echo 3 > /proc/sys/vm/drop_caches   # 可选，与驱动内 drop 二选一即可
free

# 3. 关闭 WiFi
#    SS_HAL_WIFI_Stop / SS_HAL_WIFI_Deinit
echo 3 > /proc/sys/vm/drop_caches
free
```

**关注** `available` **或** `used` **的差值**（建议多看 `available`，比 `free` 更能反映实际余量）：

```
WiFi 占用 ≈ (WiFi 关闭时 available) − (WiFi 开启时 available)
         或 ≈ (WiFi 开启时 used) − (WiFi 关闭时 used)
```


| 结果       | 建议                                                |
| -------- | ------------------------------------------------- |
| **≤ 3M** | 一般可接受，继续 §3.2 措施表及 §3.3 起的 Kernel / ZRAM / VM 等优化 |
| **> 3M** | 咨询 WiFi 芯片厂，看能否减占用；优先于 Kernel 裁剪                  |




#### 3.1.2 超 3M 时的优化方向

与 WiFi 厂沟通时可从以下方向入手（由厂方评估可行性）：

1. **关闭不用的驱动配置**：如 P2P、monitor、多余扫描缓存、5G/双频未用通道等（`wifi.cfg` / 驱动编译选项）。
2. **减小预分配 buffer**：扫描队列、TX/RX ring、skb 池等（需厂方可给出安全下限）。
3. **更换 WiFi 模块**：同方案下换更低内存占用的芯片或精简 firmware 版本。

> 本项目已在 `SS_HAL_WIFI_Init()` 内 drop cache（§3.5.1），对比测试时建议在**两次** `free` **前都执行 drop cache**，避免 page cache 干扰差值。

#### 3.3.2 按需关闭的内核配置项（HSCP2025092852334）

根据产品实际功能需求，在 defconfig 或 `menuconfig` 中关闭未使用模块，减少内核运行时内存占用：


| 配置项                  | 操作                                | 说明                                                 |
| -------------------- | --------------------------------- | -------------------------------------------------- |
| `CONFIG_HZ_PERIODIC` | `# CONFIG_HZ_PERIODIC is not set` | 关闭周期性 HZ tick；配合 `NO_HZ` 减少空闲 tick 开销（无高精度定时需求时可关） |
| `CONFIG_RELAY`       | `# CONFIG_RELAY is not set`       | 关闭内核 relay 文件系统，用于 ftrace/debug 中继，正式产品不需要         |
| `CONFIG_COMPAT_BRK`  | `# CONFIG_COMPAT_BRK is not set`  | 关闭旧版堆 `brk()` 兼容逻辑，嵌入式固定 glibc 版本可关                |

### 3.4 ZRAM 压缩内存

Linux 内核默认**未启用 ZRAM**，需在内核配置中打开后再于启动脚本激活。

#### 3.4.1 压缩原理：怎么省内存

ZRAM 不是「把内存变多」，而是在 **OS 内存紧张** 时，把暂时不用的页 **压缩后仍放在 RAM 里**，用 CPU 换空间，避免过早 OOM。

**正常情况（无 swap）**：

```
应用 / WiFi / cache 持续占用
    → OS 34M（MemTotal ≈ 26M）被吃满
    → 内核回收 page cache 仍不够
    → OOM Killer 杀进程
```

**ZRAM 介入后**：

```
内存低于水位线
    → 内核选出「近期不太会用」的匿名页（进程堆栈、堆等）
    → 不写到 Flash，而是 LZO 压缩后存入 zram0 设备（仍在 DDR 内）
    → 原物理页释放回伙伴系统，供其他模块继续分配
    → 需要时再解压读回
```

**为什么能省**：压缩后同样 1MB 原始数据可能只占 300~500KB 物理 RAM（视内容而定，文本/零页压缩比高）。本项目 `disksize=8M` 表示 **逻辑 swap 容量 8M**；`mem_limit=8M` 限制压缩数据 **最多占 8M 物理 RAM**。实际 `free` 里 Swap 行 total ≈ 8188，即「最多还能再扛 8M 逻辑换出」。

```
示例（典型压缩比约 2:1~3:1）：

  换出 6M 原始页  →  zram 内压缩存 2~3M  →  释放约 3~4M 物理页给业务
  ─────────────────────────────────────────────────────────────
  逻辑收益：多 6M「可换出空间」    物理代价：zram 占 2~3M + 少量 CPU
```

**与 Kernel 裁剪的区别**：


| 手段               | 作用               | 何时生效             |
| ---------------- | ---------------- | ---------------- |
| Kernel 裁剪（§3.3）  | 内核自身少占 RAM       | 启动后 MemTotal 就变大 |
| ZRAM（本节）         | 内存紧张时压缩换出，延缓 OOM | 负载高、触发 swap 时    |
| drop cache（§3.5） | 释放文件 cache       | 执行命令瞬间           |


**局限**（讲解/验收时需说明）：

1. **不减少业务常驻 RSS**：正在用的 buffer 不会被压缩换出。
2. **消耗 CPU**：压缩/解压有开销，高负载下可能略增延时。
3. **不是 MMZ 优化**：MMZ 在 `mem=` 之外，ZRAM 管不了 VB / 媒体内存。

查看实际压缩效果：

```bash
cat /sys/block/zram0/mm_stat
# orig_data_size  ：已换出原始数据量
# compr_data_size ：压缩后实际占用 RAM
# 压缩比 ≈ orig_data_size / compr_data_size
```



#### 3.4.2 内核编译配置

在 `linux-5.10.221.patch` / defconfig 中开启：

```
CONFIG_SWAP=y
CONFIG_ZRAM=y
CONFIG_ZSMALLOC=y
CONFIG_CRYPTO_LZO=y
```


| 选项                  | 作用                   |
| ------------------- | -------------------- |
| `CONFIG_SWAP`       | 启用 swap 子系统（ZRAM 依赖） |
| `CONFIG_ZRAM`       | 编译 zram 块设备驱动        |
| `CONFIG_ZSMALLOC`   | ZRAM 后端压缩分配器         |
| `CONFIG_CRYPTO_LZO` | LZO 压缩算法支持           |




#### 3.4.3 运行时配置（bootapp）

本项目在 `source/camera/demo/dronecam/rootfs/appfs_priv/bootapp` 中于**业务启动前**执行：

```bash
echo 8M > /sys/block/zram0/disksize

```

**参数说明**：


| 步骤       | 命令                         | 说明                                                      |
| -------- | -------------------------- | ------------------------------------------------------- |
| 设置虚拟磁盘大小 | `echo 8M > .../disksize`   | swap 分区逻辑容量；**不宜过大**，约占 DDR 的 disksize×0.1% 元数据开销，不够再扩大 |
| 设置最大使用内存 | `echo 8M > .../mem_limit`  | 压缩数据实际占用 RAM 上限                                         |
| 格式化 swap | `mkswap /dev/zram0`        | 创建 swap 签名                                              |
| 激活 swap  | `swapon /dev/zram0 -p 100` | 优先级 100，内存紧张时换出到此压缩区                                    |


**可选调参**（默认值通常够用）：

```bash
# 压缩流数量，默认与 CPU 核数相同
cat /sys/block/zram0/max_comp_streams

# 压缩算法，默认 lzo-rle
cat /sys/block/zram0/comp_algorithm
# 如需修改：echo lzo > /sys/block/zram0/comp_algorithm
```

**运维命令**：

```bash
# 查看压缩状态（orig_data_size / compr_data_size 等）
cat /sys/block/zram0/mm_stat

# 取消 swap
swapoff /dev/zram0

# 复位：释放 zram 全部内存并将 disksize 清 0
echo 1 > /sys/block/zram0/reset
```

> **注意**：上述 `/sys/block/zram0/`* 操作通过 proc/sysfs 节点设置，**重启后失效**。本项目通过 `bootapp` 每次启动自动配置；若需持久化，可借助 `zramctl` 工具和配置文件。

**效果验证**：

```bash
free          # Swap 行应显示 total ≈ 8188（8M）
cat /proc/swaps
```

### 3.5 drop cache 与 VM 参数调优



#### 3.5.1 大内存业务前先 drop cache

在 WiFi 驱动加载、媒体管线初始化等**大内存消耗操作之前**，主动释放 page cache，避免与业务争抢 OS 内存：

```bash
echo 3 > /proc/sys/vm/drop_caches
```


| 值   | 释放内容                 |
| --- | -------------------- |
| 1   | page cache           |
| 2   | dentry / inode cache |
| 3   | 以上全部                 |


**WiFi 加载前 drop cache**

WiFi 驱动 + 协议栈加载时会一次性占用较多 OS 内存。加载前先 drop cache，可避免 page cache 与驱动争抢，使 `free` 读数更能反映 WiFi **真实增量**（也便于 §3.1 对比测试）。


| 时机       | 文件                                                                                           | 实现                                            |
| -------- | -------------------------------------------------------------------------------------------- | --------------------------------------------- |
| WiFi 初始化 | `[ss_hal_wifi.c](../source/camera/hal/wifi/src/common/ss_hal_wifi.c)` → `SS_HAL_WIFI_Init()` | `system("echo 3 > /proc/sys/vm/drop_caches")` |
| 系统启动     | `bootapp`                                                                                    | 在 ZRAM / VM 调优之前可酌情执行                         |


```
SS_HAL_WIFI_Init()
    ├── echo 3 > /proc/sys/vm/drop_caches   // 释放 page cache
    ├── HAL_WIFI_HAL_LoadAPDriver / LoadSTADriver
    └── WiFi 协议栈初始化完成
```



#### 3.5.2 减小 min_free_kbytes

`min_free_kbytes` 是 Linux 内核参数，表示系统运行时**保留的最小空闲物理内存（KB）**。当可用内存低于此值时，内核会积极回收内存，以避免 OOM。

在 `bootapp` 中设置（本项目当前值）：

```bash
echo 0 > /proc/sys/vm/watermark_boost_factor
echo 1024 > /proc/sys/vm/min_free_kbytes
echo 1024 > /proc/sys/vm/user_reserve_kbytes

# 验证
cat /proc/sys/vm/min_free_kbytes
```


| 参数                       | 本项目值 | 作用                                      |
| ------------------------ | ---- | --------------------------------------- |
| `watermark_boost_factor` | 0    | 关闭水位加成，避免内核过度预留                         |
| `min_free_kbytes`        | 1024 | 最低保留 1MB 空闲页（64M 方案下从默认 4M+ 降低，释放更多给业务） |
| `user_reserve_kbytes`    | 1024 | 限制用户态最低保留，与 min_free 配合                 |


**逻辑**：64M 方案 OS 仅 34M（MemTotal ≈ 26M），默认 `min_free_kbytes` 过大时会长期占用不可分配内存；降至 1024KB 后配合 ZRAM，在 OOM 前优先压缩换出。

**风险**：压测时若频繁 OOM，可适当调高 `min_free_kbytes`（如 2048）。

#### 3.5.3 bootapp 完整 VM + ZRAM 片段（本项目）

```bash
# VM 调优
echo 3 > /proc/sys/vm/dirty_background_ratio
echo 30 > /proc/sys/vm/dirty_ratio
echo 100 > /proc/sys/vm/dirty_writeback_centisecs
echo 0 > /proc/sys/vm/watermark_boost_factor
echo 1024 > /proc/sys/vm/min_free_kbytes
echo 1024 > /proc/sys/vm/user_reserve_kbytes

# ZRAM 8M
echo 8M > /sys/block/zram0/disksize
echo 8M > /sys/block/zram0/mem_limit
mkswap /dev/zram0
swapon /dev/zram0 -p 100
```

## 5. 场景化方案



### 5.1 场景 A：真 4K（3840×2160，宽width > 3200）— 低延时

#### 5.1.1 措施清单


| 序号  | 措施                        | 配置/代码                                                |
| --- | ------------------------- | ---------------------------------------------------- |
| 1   | 开启 VI Pipe 低延时            | ini: `lowdelayenable = "1"`, `lowdelayline = "1000"` |
| 2   | 4K 自动开启 one_buf           | `ispWidth > 3200` 时 `one_buf_en = lowDelayEnable`    |
| 3   | 低延时必须在 StartPipe **之前**配置 | 调整 `MEDIA_StartVcapDev()` 调用顺序                       |

| 6   | 关闭帧中断 Early-End           | `frameinterrupt_type = "0"`（与 one_buf 配合）            |




#### 5.1.2 代码流程

```
参数加载（ini）
    config_product_mediamode_cam0_comm_record.ini
        └── [vcap.pipe.0] lowdelayenable=1, lowdelayline=1000

                    ├── SS_MAPI_VCAP_StartPipe() 之前：

                    │               ├── lowDelayInfo.enable = TRUE
                    │               ├── lowDelayInfo.line_cnt = 1000
                    │               └── if (ispWidth > 3200)
                    │                       lowDelayInfo.one_buf_en = TRUE  // 4K 关键

                    ├── SS_MAPI_VCAP_StartPipe()
```

**关键约束**（`MEDIA_SetVcapPipeLowDelay`）：

- AIBNR 开启时不启用低延时

**VB 调整逻辑**（2160p30 ini）：

```

    pool.0 (10M 级) blk_count: 2 → 0
```

| 5   | VI 帧中断支持 online 模式    | `mapi_vcap.c` 增加 `VI_ONLINE_VPSS_ONLINE` 分支                       |
| 6   | 关闭 vport.2            | 减少一路 VPSS 输出                                                      |
| 7   | VB 池 4→3              | 按 wrap 后实际大小重算                                                    |
| 8   | bootargs VGS 限制       | `g_max_vgs_job=20` 等，限制 VGS 内存                                    |

#### 5.2.3 卷绕参数验证与 buf_line 调优

卷绕开启后，可通过 MPP Proc 接口确认实际生效参数：

```bash
cat /proc/umap/vpss
```

在输出中找到 `**vpss chn wrap attr**` 段，典型值如下（1440P WDR + 卷绕方案）：

VPSS chn wrap attr 调试信息


| 字段            | 示例值        | 含义                                |
| ------------- | ---------- | --------------------------------- |
| `grp` / `chn` | 0 / 0      | VPSS 组号 / 通道号（主码流 chn0）           |
| `enable`      | Y          | 卷绕已开启                             |
| `buf_line`    | 448        | 卷绕 buffer 行数（代码中设置，可微调）           |
| `buf_size`    | 1258976    | 卷绕 buffer 实际数据大小（字节）              |
| `vb_size`     | 1259008    | 向 VB 池申请的块大小（含对齐余量）               |
| `pool_id`     | 0          | 使用的公共 VB 池编号，对应 ini `[vb.pool.0]` |
| `phy_addr`    | 0x42227000 | VB 块物理地址                          |


**关键关系：卷绕的 VB 大小与行数正相关**

```
buf_line ↑  →  buf_size ↑  →  vb_size ↑  →  MMZ 占用 ↑
buf_line ↓  →  buf_size ↓  →  vb_size ↓  →  MMZ 占用 ↓
```

- `buf_line` 由 `ss_mpi_sys_get_vpss_venc_wrap_buf_line()` 计算后，代码中可手动覆盖（如 320、448）。
- `buf_size = ot_comm_get_vpss_venc_wrap_buf_size(&buf_attr, buf_line)`，随 `buf_line` 线性增大。
- `vb_size` 为对齐后的 VB 块大小，略大于 `buf_size`（示例：1258976 → 1259008，差 32 字节）。

**调优步骤**：

1. 开启卷绕跑业务，执行 `cat /proc/umap/vpss`，确认 `enable = Y`。
2. 记录 `buf_line`、`vb_size`，与 ini 中 `[vb.pool.0] blk_size` 对比：
  - ini 的 `blk_size` 应 **≥ vb_size**（或等于 `buf_size` 向上对齐值）；
  - 若 ini `blk_size` 远大于 `vb_size`，按 **§8.3** 调小 `free_bytes`。
3. 若 MMZ 仍紧张，可在画质/稳定性允许范围内 **逐步减小** `buf_line`（如 448 → 400 → 320），每次改后：
  - 重新查看 `/proc/umap/vpss` 中 `vb_size` 是否下降；
  - 同步更新 ini `[vb.pool.0] blk_size`；
  - 压测确认无花屏、丢帧、`logmpp` VB 报错。
4. `buf_line` 过小会导致卷绕 buffer 深度不足，可能出现编码异常，需实机验证。

**与 ini VB 配置的对应关系**（1440P WDR 示例）：

```ini
[vb.pool.0]
blk_size  = "1258976"   ; 对应 proc 中 buf_size
blk_count = "2"         ; 卷绕 public VB，按 min_free 调优（见 **§8.4**）
```

```
media_vproc.c 设置 wrap
    buf_line = 448
        → buf_size = 1258976
        → vb_size  = 1259008（VB 对齐）
        → 从 pool_id=0 分配
            → ini [vb.pool.0] blk_size 应匹配此 vb_size
```

**数据通路（1620P30 全在线 + 卷绕）**：

```
Sensor → VI(online) → VPSS(online, chn0 wrap) → VENC0(主码流 2880×1620)
                              └→ VPSS chn1 → VENC1(子码流 1024×576)
```

**与 4K 低延时的选择逻辑**：


| 条件                                 | 方案                 | 原因                  |
| ---------------------------------- | ------------------ | ------------------- |
| ispWidth > 3200 或 ispHeight > 3200 | VI 低延时 + one_buf   | 4K 不支持 VPSS 卷绕      |
| ispWidth ≤ 3200 且 ispHeight ≤ 3200 | VPSS-VENC 卷绕 + 全在线 | wrap 可节省 1.5~1.8 VB |
| 1080P                              | 常规在线模式             | 高度=1080 跳过 wrap 逻辑  |

## 8. 补充：VB 配置与调优方法

> 参考文档：《MPP 媒体处理软件 V6.0 开发参考》**第 12 章 Proc 调试信息说明** — VB 章节（`/proc/umap/vb`）。

VB（Video Buffer）是 MMZ 内存的主要占用者。调优分两步：**先改 ini 配置**，再用 `**cat /proc/umap/vb`** 验证是否"刚刚好"。

### 8.1 ini 中如何配置 VB

VB 公共池在对应 **mediamode 的 record/photo ini** 中配置，由 param 模块加载后传入 `SS_MAPI_SYS_Init()`。

**配置路径示例**：

```
source/camera/demo/dronecam/modules/param/inicfg/hi3516cv610/nonescreen/
    sc431hai_wdr_64M/config_product_mediamode_cam0_record_1440p25_wdr.ini
```

**配置格式**（`PDT_INIPARAM_LoadCamVBSpecCfg` 解析 `[vb]` / `[vb.pool.N]` 段）：

```ini
; ============= VB Configure =============
[vb]
max_poolcnt        = "3"
[vb.pool.0]
blk_size           = "1258976"    ; 卷绕主路 VB
blk_count          = "2"
[vb.pool.1]
blk_size           = "884736"     ; 1024*576*3/2，预览/子码流
blk_count          = "3"
[vb.pool.2]
blk_size           = "28928"      ; 缩略图
blk_count          = "2"
```

VB ini 配置示例


| 字段            | 含义          | 调优方向                  |
| ------------- | ----------- | --------------------- |
| `max_poolcnt` | 公共 VB 池数量   | 能合并则减少 pool 数         |
| `blk_size`    | 每个 VB 块字节数  | 按实际帧大小精确计算，避免过大       |
| `blk_count`   | 每个 pool 的块数 | 按流水线深度需求设置，见 **§8.3** |


**各 pool 典型用途（1440P WDR + 卷绕方案）**：


| Pool   | 用途     | blk_size 计算参考                                                                                        |
| ------ | ------ | ---------------------------------------------------------------------------------------------------- |
| pool.0 | 卷绕主路   | `ss_mpi_sys_get_vpss_venc_wrap_buf_size()` 或 wrap 后实际帧大小；见 **7.2.3 节** `/proc/umap/vpss` 中 `vb_size` |
| pool.1 | 子码流/预览 | 目标分辨率 YUV420：`W×H×3/2`，如 1024×576 → 884736                                                           |
| pool.2 | 缩略图    | JPEG 缩略图分辨率对应大小，如 160×120 级别 → 28928                                                                 |


**代码加载流程**：

```
config_product_mediamode_cam0_record_*.ini
    └── PDT_INIPARAM_LoadCamVBSpecCfg()        // product_iniparam_cammedia.c
            ├── 读取 vb:max_poolcnt
            └── 循环读取 vb.pool.N:blk_size / blk_count
                    └── OT_MEDIA_VbCfg → SS_MAPI_SYS_Init() → ss_mpi_vb_set_cfg()
```

修改 ini 后需 **重新编译 param（ini2bin）并烧录**，重启生效。

### 8.2 如何查看 VB 运行信息

```bash
cat /proc/umap/vb
```

输出结构（MPP 手册第 12 章）：


| 区域                  | 内容                       |
| ------------------- | ------------------------ |
| 头部                  | MPP 版本、Build Time        |
| vb pub config       | `max_pool_cnt` 等全局配置     |
| common pool config  | 各 pool 的 size / count 汇总 |
| pool 详情（每个 pool_id） | 见下表                      |


**pool 详情关键字段**：


| 字段           | 含义                                                     |
| ------------ | ------------------------------------------------------ |
| `pool_type`  | `common`（公共池）或 `private`（模块私有池，owner 为 vi/vpss/venc 等） |
| `blk_sz`     | 块大小（与 ini 中 blk_size 对应）                               |
| `blk_cnt`    | 块总数（与 ini 中 blk_count 对应）                              |
| `free`       | 当前空闲块数                                                 |
| `min_free`   | 运行期间最小剩余空闲块数（**调 blk_count 的核心依据**）                    |
| `free_bytes` | 每块内剩余未用字节（**调 blk_size 的核心依据**）                        |
| 模块占用表        | 各模块（vi/vpss/venc/vdec 等）当前占用的块数                        |

### 8.3 调 blk_size：看 free_bytes

**原则**：`free_bytes` 越接近 0，说明 `blk_size` 设得越准，没有浪费。

VB blk_size 调优 — free_bytes

上图为调优**合格**示例：


| Pool | blk_sz  | free_bytes | 结论               |
| ---- | ------- | ---------- | ---------------- |
| 0    | 1259008 | 32         | 几乎无浪费（32 字节对齐余量） |
| 1    | 884736  | 0          | 完全匹配             |
| 2    | 28928   | 0          | 完全匹配             |


**调整方法**：

1. 先用当前配置跑业务，执行 `cat /proc/umap/vb`。
2. 若某 pool 的 `free_bytes` **很大**（如 > 1KB），说明 `blk_size` 过大：
  - 将 ini 中 `blk_size` 减小到 `blk_sz - free_bytes`（向上对齐到 64 字节）。
3. 若出现 **VB 分配失败** / `logmpp` 报 VB 不足，说明 `blk_size` 过小，需增大。
4. 卷绕场景下 `blk_size` 应使用 wrap 后的实际 buffer 大小，而非整帧 `W×H×3/2`。

---



### 8.4 调 blk_count：看 min_free

**原则**：在**最大负载场景**下测试（录像 + 子码流 + WiFi + 缩略图等全部开启）。

VB blk_count 调优 — min_free


| min_free 值 | 含义              | 建议                      |
| ---------- | --------------- | ----------------------- |
| **> 1**    | 该 pool 块数偏多，有浪费 | 可将 `blk_count` 减 1，重新测试 |
| **= 1**    | 内存充足时的理想状态      | 保留，留 1 块余量              |
| **= 0**    | 内存紧张时的极限状态      | 可接受，但需确认 `logmpp` 无报错   |


**判定标准**（见上图标注）：

> 在最大场景下测试：内存充足时 **min_free 最好剩 1 个**；内存不够时 **剩 0 个** 也可，但 `cat logmpp` 不能报错，或偶尔报 1 次可接受。

**调整步骤**：

```
1. 最大负载运行 5~10 分钟
2. cat /proc/umap/vb → 记录各 pool 的 min_free
3. 若 min_free > 1：
       ini 中 blk_count -= (min_free - 1)
4. 重新编译烧录 → 重复步骤 1~3
5. 同时检查：cat logmpp | grep -i vb
       无 "vb fail" / "no blk" 等错误即通过
```

### 8.5 完整调优流程

```
┌─────────────────────────────────────────────────────────┐
│  1. 确定 mediamode 对应 ini 文件                          │
│  2. 根据分辨率/卷绕/低延时方案，估算各 pool blk_size       │
│  3. 写入 ini [vb] 段，编译烧录                            │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│  4. 最大负载运行 → cat /proc/umap/vb                      │
│  5. 检查 free_bytes → 调 blk_size（目标：0 或接近 0）     │
│  6. 检查 min_free   → 调 blk_count（目标：0 或 1）        │
│  7. 检查 cat logmpp → 确认无 VB 报错                      │
└──────────────────────┬──────────────────────────────────┘
                       ▼
              重复 4~7 直到满足目标
                       ▼
         cat /proc/media-mem → MMZ 总量 < 目标值（如 27M）
```



### 8.6 常见问题


| 现象                                     | 可能原因                                                  | 处理                          |
| -------------------------------------- | ----------------------------------------------------- | --------------------------- |
| `no free mmz` / VB 分配失败                | blk_count 过小或 blk_size 不足                             | 增大对应 pool 的 count 或 size    |
| MMZ 占用偏高但业务正常                          | blk_size 过大（free_bytes 大）或 blk_count 过多（min_free > 1） | 按 **§8.3 / §8.4** 缩小        |
| common pool 够用但 proc 显示 private pool 多 | VI/VPSS 模块创建了私有 VB                                    | 检查是否可改用公共池或开启 wrap/低延时减少私有池 |
| 改 ini 不生效                              | 未重新 ini2bin 或未烧录 param 分区                             | 确认编译链完整执行                   |
