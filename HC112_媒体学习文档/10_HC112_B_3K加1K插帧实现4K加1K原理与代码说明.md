# HC112_B 前路 3K＋后路 1K 插帧实现 4K＋1K：原理、代码与流程

> 文档日期：2026-08-03  
> 分析工程：`Z:\HC112_B_SPC020`  
> 对照工程：`Z:\HC101_A_SPC020`  
> 参考补丁：`C:\Users\Admin\Desktop\1.patch`  
> 当前有效配置目录：`source/camera/demo/dronecam/modules/param/inicfg/hi3516cv610/nonescreen/gc4653_ahd_128M`

## 1. 结论

HC112_B 当前实现的“前路 3K 插帧成为 4K＋后路 AHD 1K”并不是单独一种插帧，而是两个动作共同完成：

1. **空间分辨率转换**：GC4653 实际采集 `2560×1440`，由 VPSS 放大为 `3840×2160`，再送入 VENC。因此录像文件的宽高为标准 4K UHD。
2. **时间帧率转换**：前路实际帧率为 `19fps`，VENC 使用 `COPY` 重复帧策略，把编码输出补到 `25fps`。

后路 AHD 不参与前路插帧，保持独立的 `1920×1080@25fps` 编码链路。

因此最终录像参数是：

| 路别 | 实际输入 | VPSS 输出 | VENC 输出 | 处理方式 |
|---|---|---|---|---|
| 前路 GC4653 | 2560×1440@19fps | 3840×2160@19fps | 3840×2160@25fps | VPSS 空间放大＋VENC 复制帧 |
| 后路 AHD | 1920×1080@25fps | 1920×1080@25fps | 1920×1080@25fps | 正常编码，不插帧 |

需要明确：录像文件确实会显示 `3840×2160@25fps`，但它不是传感器原生 4K，也不是运动估计生成的新画面。空间细节来自 2560×1440 放大，新增的约 6 帧/秒是已有帧的复制。

## 2. 总体媒体流程

```text
前路 GC4653
  │  RAW 2560×1440@19
  ▼
VI / ISP
  │  YUV 2560×1440@19
  ▼
VPSS.0
  ├─ vport.0：放大为 3840×2160@19 ─► VENC0（H.265/QVBR）
  │                                      │
  │                                      ├─ 创建前：设置 duplicate=COPY
  │                                      ├─ 创建时：临时使用 25→25
  │                                      ├─ 创建后：恢复 19→25
  │                                      ▼
  │                                 4K H.265@25fps
  │                                      │
  │                                      ▼
  │                              ringbuf_mmz ─► MP4
  │
  └─ vport.1：1024×576@19 ─► 预览/辅码流

后路 AHD
  │  1920×1080@25
  ▼
VI / ISP / VPSS ─► VENC3（H.265/QVBR）
                         │
                         ▼
                  1080P H.265@25fps
                         │
                         ▼
                 ringbuf_mmz ─► MP4
```

## 3. 配置层：从 3K 档位构造 4K 输出

核心文件：

```text
source/camera/demo/dronecam/modules/param/inicfg/hi3516cv610/nonescreen/
gc4653_ahd_128M/config_product_mediamode_cam0_record_1440p30.ini
```

### 3.1 传感器和 ISP 仍按 2560×1440@19 工作

当前代码：

```ini
[vcap.dev]
sensor_type        = "30"; 30:gc4653
sensor_mode        = "0"
sensor_width       = "2560"
sensor_height      = "1440"

[vcap.pipe.0]
enable             = "1"
src_framerate      = "19"
dst_framerate      = "19"
isp_framerate      = "19"
isp_width          = "2560"
isp_height         = "1440"
```

含义：

- `sensor_type = 30`：选择已经完成真实注册的 GC4653。
- `sensor_width/height`：传感器输出仍是 2560×1440。
- `src_framerate/dst_framerate = 19`：输入链路按 19fps 运行，降低前路处理吞吐量，为双路编码和 4K 输出留出性能、VB 与 MMZ 空间。
- `isp_width/height`：ISP 不伪装成 4K，仍按真实输入尺寸处理。

配置段名称仍叫 `1440p30`，但当前实际帧率已经改为 19fps。这只是历史文件名/枚举名，不代表运行时仍是 30fps。

### 3.2 VPSS 完成 2560×1440 到 3840×2160 的空间放大

参考补丁修改前：

```ini
[vpss.0.vport.0]
res_width          = "2880"
res_height         = "1620"
src_framerate      = "30"
dst_framerate      = "30"
```

当前修改后：

```ini
[vpss.0]
max_width          = "2560"
max_height         = "1440"
src_framerate      = "19"
dst_framerate      = "19"

[vpss.0.vport.0]
res_width          = "3840"
res_height         = "2160"
src_framerate      = "19"
dst_framerate      = "19"
```

含义：

- `vpss.0` 接收 2560×1440@19。
- `vport.0` 输出 3840×2160@19，空间缩放在 VPSS 阶段完成。
- VPSS 只改变宽高，不负责把 19fps 补到 25fps。

### 3.3 VENC 声明最终文件分辨率和插帧目标

参考补丁修改前：

```ini
[venc.0]
res_width          = "2880"
res_height         = "1620"
src_framerate      = "30"
dst_framerate      = "30"
```

当前修改后：

```ini
[venc.0]
res_width          = "3840"
res_height         = "2160"
bufsize            = "3110400"
gop                = "19"
src_framerate      = "19"
dst_framerate      = "25"
h265bitrate        = "18432"; kbps
stat_time          = "2"; second
```

含义：

- `res_width/res_height`：编码码流和最终录像文件标记为 3840×2160。
- `src_framerate = 19`：VENC 每秒实际接收约 19 张不同输入帧。
- `dst_framerate = 25`：要求编码码流时间轴输出 25fps。
- `gop = 19`：当前 GOP 周期依据实际输入帧率设置。
- `h265bitrate = 18432`：前路 H.265 目标码率约 18Mbps。
- `bufsize` 是 VENC 通道缓冲参数，不等同于录像预缓存，也不等同于 `ringbuf_mmz` 总大小。

只修改这份 INI 还不够。原中间件默认不支持 `src_framerate < dst_framerate` 的创建流程，所以还必须增加后面介绍的 VENC 复制帧控制接口。

## 4. MAPI 接口层：增加“复制帧策略”控制命令

### 4.1 定义策略枚举和扩展命令

文件：

```text
platform/middleware/ndk/code/include/ot_mapi_venc_define.h
```

新增代码：

```c
typedef enum {
    OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_RECODE = 0,
    OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_COPY,
    OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_BUTT
} OT_MAPI_VENC_DuplicateFrameStrategy;

typedef enum {
    /* 原有命令省略 */
    OT_MAPI_VENC_CMD_FRAMEINC_STRATEGY,
    OT_MAPI_VENC_CMD_BUTT
} OT_MAPI_VENC_Cmd;
```

逐项说明：

- `RECODE`：驱动采用重新编码方式处理补帧。
- `COPY`：直接复制已有帧来补齐目标帧率；当前 HC112_B 使用这一项。
- `BUTT`：枚举边界，只用于参数合法性检查。
- `FRAMEINC_STRATEGY`：给 `SS_MAPI_VENC_SetAttrEx()` 增加一个设置插帧策略的命令号。

当前实现选择 `COPY`，所以 19→25 时每秒大约补 6 个重复帧，计算量小于运动插值，也不会产生真正的新运动细节。

### 4.2 声明适配层函数

文件：

```text
platform/middleware/ndk/code/mediaserver/adapt/include/mapi_venc_adapt.h
```

代码：

```c
TD_S32 MAPI_ADAPT_VENC_SetFrameIncStrategy(
    TD_HANDLE vencHdl,
    OT_MAPI_VENC_DuplicateFrameStrategy strategy);
```

作用：把上层 MAPI 命令传给海思底层 VENC 通道配置接口。

### 4.3 把 MAPI 策略写入底层 VENC 通道

文件：

```text
platform/middleware/ndk/code/mediaserver/adapt/h9/mapi_venc_adapt.c
```

当前代码：

```c
TD_S32 MAPI_ADAPT_VENC_SetFrameIncStrategy(
    TD_HANDLE vencHdl,
    OT_MAPI_VENC_DuplicateFrameStrategy strategy)
{
    ot_venc_chn_config chnCfg;
    TD_S32 ret = ss_mpi_venc_get_chn_config(vencHdl, &chnCfg);
    if (ret == TD_SUCCESS) {
        if (chnCfg.duplicate_frame_strategy ==
            (ot_venc_duplicate_frame_strategy)strategy) {
            return TD_SUCCESS;
        }

        chnCfg.composite_enc_en = TD_FALSE;
        chnCfg.mosaic_en = TD_FALSE;
        chnCfg.quality_level = 0;
        chnCfg.duplicate_frame_strategy =
            (ot_venc_duplicate_frame_strategy)strategy;

        ret = ss_mpi_venc_set_chn_config(vencHdl, &chnCfg);
    }
    return ret;
}
```

逐段说明：

1. `ss_mpi_venc_get_chn_config()`：先读取底层通道当前配置，避免覆盖其他字段。
2. 策略已经一致时直接返回，避免重复设置。
3. 关闭 `composite_enc_en` 和 `mosaic_en`：避免复合编码/马赛克功能与复制帧策略同时占用不兼容路径。
4. `quality_level = 0`：保持该通道配置的基础质量级别。
5. 写入 `duplicate_frame_strategy`：选择底层复制帧策略。
6. `ss_mpi_venc_set_chn_config()`：把策略真正设置到 VENC 驱动。

### 4.4 允许插帧策略在通道正式初始化前设置

文件：

```text
platform/middleware/ndk/code/mediaserver/venc/mapi_venc.c
```

关键代码：

```c
CHECK_MAPI_VENC_CHECK_PREINIT_UNLOCK_RET(g_vencContext.vencInited);
if (cmd != OT_MAPI_VENC_CMD_FRAMEINC_STRATEGY) {
    CHECK_MAPI_VENC_CHECK_INIT_UNLOCK_RET(
        g_vencContext.vencChnCfg[vencHdl].inited);
}
```

含义：

- VENC 模块本身必须已经预初始化。
- 普通扩展属性要求具体通道已经初始化。
- `FRAMEINC_STRATEGY` 是特例，必须在 `SS_MAPI_VENC_Init()` 创建通道前设置，因此跳过“通道已初始化”检查。

命令处理代码：

```c
case OT_MAPI_VENC_CMD_FRAMEINC_STRATEGY:
    if (attrLen < sizeof(OT_MAPI_VENC_DuplicateFrameStrategy)) {
        return OT_MAPI_VENC_EILLEGAL_PARAM;
    }

    OT_MAPI_VENC_DuplicateFrameStrategy *strategy =
        (OT_MAPI_VENC_DuplicateFrameStrategy *)attr;

    if ((*strategy) != OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_RECODE &&
        (*strategy) != OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_COPY) {
        return OT_MAPI_VENC_EILLEGAL_PARAM;
    }

    ret = MAPI_ADAPT_VENC_SetFrameIncStrategy(vencHdl, *strategy);
    if (ret != TD_SUCCESS) {
        return ret;
    }
    break;
```

含义：

- 检查参数长度，防止错误指针或越界读取。
- 只接受 `RECODE` 和 `COPY` 两种有效策略。
- 调用适配层写底层 VENC 配置。
- 当前 HC112_B 会把底层失败码继续返回给上层，不会把设置失败误判为成功。

相比 `1.patch`/HC101_A 的原始写法，当前 HC112_B 使用 `sizeof(OT_MAPI_VENC_DuplicateFrameStrategy)` 检查长度，并检查适配层返回值，语义更明确、错误更容易暴露。

## 5. MEDIA 层：识别 19→25 场景并正确创建通道

核心文件：

```text
source/camera/component/media/src/component/media_venc.c
```

### 5.1 全局状态仅标记当前正在初始化的通道是否插帧

```c
static td_bool g_vencFrameInsertion = TD_FALSE;
```

这个变量不是录像状态，也不是永久开关。它只用于当前 VENC 通道初始化阶段，在“设置复制策略”和“调整创建参数”之间传递判断结果。

### 5.2 严格识别需要插帧的通道

```c
static td_bool MEDIA_IsVencFrameInsertionAttr(
    const OT_MEDIA_VencAttr *attr)
{
    if (attr->vencChnAttr.payloadTypeAttr.type !=
        OT_MAPI_PAYLOAD_TYPE_H265) {
        return TD_FALSE;
    }

    if (attr->vencChnAttr.rcAttr.rcMode !=
        OT_MAPI_VENC_RC_MODE_QVBR) {
        return TD_FALSE;
    }

    const OT_MAPI_VENC_QvbrAttr *qvbrAttr =
        &attr->vencChnAttr.rcAttr.vencAttr.h265QvbrAttr.qvbrAttr;

    if ((qvbrAttr->dstFrameRate == 25 &&
         qvbrAttr->srcFrameRate == 19) ||
        (qvbrAttr->dstFrameRate == 30 &&
         qvbrAttr->srcFrameRate == 25)) {
        return TD_TRUE;
    }

    return TD_FALSE;
}
```

当前前路满足：

```text
编码类型 = H.265
码控模式 = QVBR
输入帧率 = 19
输出帧率 = 25
```

后路是 25→25，不满足判断条件，所以不会误开插帧。

代码还保留 25→30 的兼容分支，但当前 4K＋1K 主路径使用的是 19→25。

### 5.3 在创建 VENC 通道之前设置 COPY 策略

```c
static td_s32 MEDIA_SetVencFrameInsertion(
    const OT_MEDIA_VencAttr *attr)
{
    g_vencFrameInsertion = TD_FALSE;
    if (!MEDIA_IsVencFrameInsertionAttr(attr)) {
        return TD_SUCCESS;
    }

    g_vencFrameInsertion = TD_TRUE;
    OT_MAPI_VENC_DuplicateFrameStrategy strategy =
        OT_MAPI_VENC_DUPLICATE_FRAME_STRATEGE_COPY;

    td_s32 ret = SS_MAPI_VENC_SetAttrEx(
        attr->vencHdl,
        OT_MAPI_VENC_CMD_FRAMEINC_STRATEGY,
        &strategy,
        sizeof(OT_MAPI_VENC_DuplicateFrameStrategy));

    MLOGI("Set frame insertion strategy venc[%u] "
          "strategy[%d] ret[0x%x]\n",
          attr->vencHdl, strategy, ret);
    return ret;
}
```

执行顺序非常重要：必须先让底层通道知道将使用复制帧，然后再创建 VENC 通道。

### 5.4 为什么创建时先把 19→25 临时改成 25→25

```c
static td_bool MEDIA_CheckUpdateChnFrameRate(
    OT_MAPI_PayloadType type,
    OT_MAPI_VENC_RcAttr *attr,
    td_u32 *srcFrameRate,
    td_u32 *dstFrameRate)
{
    if (type != OT_MAPI_PAYLOAD_TYPE_H265 &&
        type != OT_MAPI_PAYLOAD_TYPE_H264) {
        return TD_FALSE;
    }

    if (g_vencFrameInsertion == TD_FALSE) {
        return TD_FALSE;
    }

    td_bool needSetChnParam = TD_FALSE;

    if (attr->rcMode == OT_MAPI_VENC_RC_MODE_QVBR) {
        if (attr->qvbrAttr.srcFrameRate <=
            attr->qvbrAttr.dstFrameRate) {
            *srcFrameRate = attr->qvbrAttr.srcFrameRate;
            *dstFrameRate = attr->qvbrAttr.dstFrameRate;

            attr->qvbrAttr.srcFrameRate =
                attr->qvbrAttr.dstFrameRate;
            needSetChnParam = TD_TRUE;
        }
    }

    return needSetChnParam;
}
```

对于前路：

```text
原始配置：src=19，dst=25
保存下来：srcFps=19，dstFps=25
创建参数：src=25，dst=25
```

原因是底层 VENC 创建通道时通常要求码控参数能够直接成立。先用 25→25 创建通道，可以绕开创建阶段对“输入低于输出”的限制；通道创建完成后，再通过帧率扩展属性恢复真实的 19→25。

当前 HC112_B 已修正参考补丁中的一个潜在错误：不同码控分支分别读取自己的 `cbrAttr/vbrAttr/cvbrAttr/qvbrAttr/avbrAttr`。原参考补丁在多个非 CBR 分支中误读了 `cbrAttr`，可能造成错误帧率。

### 5.5 VENC 初始化的完整顺序

当前代码的核心顺序：

```c
ret = MEDIA_SetVencFrameInsertion(mediaVencAttr);
OT_APPCOMM_RETURN_IF_FAIL(ret, ret);

ret = MEDIA_InitVencChn(mediaVencAttr);
OT_APPCOMM_RETURN_IF_FAIL(ret, ret);
```

`MEDIA_InitVencChn()` 内部：

```c
td_u32 srcFps = 30;
td_u32 dstFps = 30;

td_bool needSetChnParam = MEDIA_CheckUpdateChnFrameRate(
    attr->vencChnAttr.payloadTypeAttr.type,
    &mapiVencAttr.rcAttr,
    &srcFps,
    &dstFps);

ret = SS_MAPI_VENC_Init(attr->vencHdl, &mapiVencAttr);
OT_APPCOMM_RETURN_IF_FAIL(ret, ret);

ret = MEDIA_SetVencAttrEx(attr, &hierarchicalQp);
OT_APPCOMM_RETURN_IF_FAIL(ret, ret);

ret = MEDIA_BindVencChn(attr->vencHdl, &attr->bindSrc);
OT_APPCOMM_RETURN_IF_FAIL(ret, ret);

if (needSetChnParam == TD_TRUE) {
    OT_MAPI_FrameRateCtrl vencFrameRate;
    vencFrameRate.srcFrameRate = srcFps;
    vencFrameRate.dstFrameRate = dstFps;

    ret = SS_MAPI_VENC_SetAttrEx(
        attr->vencHdl,
        OT_MAPI_VENC_CMD_FRAME_RATE,
        &vencFrameRate,
        sizeof(OT_MAPI_FrameRateCtrl));

    OT_APPCOMM_RETURN_IF_FAIL(ret, ret);
}
```

流程解释：

1. 判断并设置底层 `COPY` 策略。
2. 保存真实帧率 19→25，同时把创建属性临时改为 25→25。
3. 创建 VENC 通道。
4. 设置其他扩展属性。
5. 把 VPSS 输出绑定到 VENC。
6. 通道创建完成后，设置真实帧率 19→25。
7. 底层收到 19 张输入帧，复制其中部分帧，输出 25fps 码流。

### 5.6 分辨率/录像模式切换时也重新应用

`MEDIA_PartiallyInitVenc()` 中同样调用：

```c
ret = MEDIA_SetVencFrameInsertion(newVencAttr);
ret = MEDIA_InitVencChn(newVencAttr);
```

这样在录像模式切换、缩时录像切换或只重建 VENC 时，不会因为没有重新设置复制策略而退回 19fps 或创建失败。

## 6. 后路 AHD 为什么不受插帧影响

后路配置文件：

```text
.../gc4653_ahd_128M/config_product_mediamode_cam1_record_1080p30.ini
```

关键配置：

```ini
[vcap.dev]
sensor_width       = "1920"
sensor_height      = "1080"

[venc.0]
res_width          = "1920"
res_height         = "1080"
src_framerate      = "25"
dst_framerate      = "25"
h265bitrate        = "10240"; kbps
```

后路主编码句柄来自 `config_product_mediamode_cam1_comm_record.ini`：

```ini
[venc.0]
venchdl            = "3"
payload            = "1"; H.265
rcmode             = "2"; QVBR
```

虽然同样是 H.265/QVBR，但它是 25→25，不满足 `MEDIA_IsVencFrameInsertionAttr()` 的 19→25 或 25→30 条件，所以：

- 不设置 `FRAMEINC_STRATEGY`；
- 不临时修改创建帧率；
- 不复制帧；
- 保持正常 1080P25 编码。

这就是前后路可以同时运行而又互不误触发的关键。

## 7. MMZ 与录像缓存配套调整

### 7.1 当前启动内存划分

以下三处已经保持一致：

```text
platform/sdk/open_source/u-boot/u-boot-2022.07.patch
source/camera/demo/dronecam/rootfs/configs/hi3516cv610/config_squashfs_jffs2_spinor_linux_smp
build/image/hi3516cv610_dronecam_nonescreen_demb_gc4653_ahd/spinor/config
```

当前参数：

```text
mem=43M
mmz_zones=anonymous,0,0x42C00000,77824K:
          ringbuf_mmz,1,0x47800000,8192K
```

含义：

- Linux 普通内存：43MiB。
- `anonymous` MMZ：77824KiB，供 VI、VPSS、VENC、AENC 等媒体模块申请。
- `ringbuf_mmz`：8192KiB，专门给录像环形缓冲使用。

`anonymous` 结束地址与 `ringbuf_mmz` 起始地址连续，两个区域总和仍在 128MiB 物理内存范围内。

### 7.2 录像明确从 ringbuf_mmz 申请

文件：

```text
source/camera/demo/dronecam/modules/statemng/src/component/product_statemng_record.c
```

代码：

```c
recTaskAttr->fileAttr[i].bufCfg[j].bufType =
    OT_RECMNG_BUF_TYPE_MMZ;

snprintf_s(
    recTaskAttr->fileAttr[i].bufCfg[j].bufCfg.mmzBufCfg.zoneName,
    OT_APPCOMM_COMM_STR_LEN,
    OT_APPCOMM_COMM_STR_LEN - 1,
    "ringbuf_mmz");
```

含义：录像缓存不从 Linux 堆或普通 anonymous MMZ 随机申请，而是从命名区域 `ringbuf_mmz` 申请，便于隔离和计算。

实际申请在：

```text
source/camera/component/recordmng/src/ss_recordmng.c
```

```c
ret = ss_mpi_sys_mmz_alloc_cached(
    &bufAttr->bufInfo.mmzBufInfo.bufPhyAddr,
    virAddr,
    bufAttr->bufInfo.mmzBufInfo.bufName,
    bufAttr->bufInfo.mmzBufInfo.zoneName,
    bufSize);
```

### 7.3 当前录像预缓存时间

```ini
[normal.0.filenum.0.fileattr]
venc_hdl0          = "0"; 前路
recbuffer_time0    = "2000"; ms

[normal.1.filenum.0.fileattr]
venc_hdl0          = "3"; 后路
recbuffer_time0    = "2000"; ms
```

这两个 `2000ms` 分别作用于前路和后路录像轨道，并不是只修改后路，也不是整个录像共用一个 2000ms 参数。

已验证日志曾显示前路约申请 `4,795,328` 字节、后路约申请 `2,698,176` 字节，合计约 `7,493,504` 字节，可以放入 8MiB 的 `ringbuf_mmz`，但余量不算大。提高码率或预缓存时间前必须重新计算。

## 8. 参考补丁、HC101_A 与当前 HC112_B 的关系

### 8.1 从参考方案继承的核心思想

HC101_A 和 `1.patch` 提供了以下关键思路：

1. 定义 VENC 重复帧策略枚举。
2. 增加 `FRAMEINC_STRATEGY` 扩展命令。
3. 在通道创建前设置底层 `duplicate_frame_strategy`。
4. 创建通道时临时使用相同输入/输出帧率。
5. 创建后恢复真实的低输入、高输出帧率。
6. 前路通过 VPSS 输出 3840×2160，后路继续 1080P。

### 8.2 当前 HC112_B 做的整理和修正

当前 HC112_B 没有原样复制 `1.patch`，而是做了以下整理：

- 把插帧条件提取为 `MEDIA_IsVencFrameInsertionAttr()`，避免完整初始化和局部初始化各写一套判断。
- 把策略设置提取为 `MEDIA_SetVencFrameInsertion()`，统一日志和错误返回。
- 修正 VBR/CVBR/QVBR/AVBR 分支误读 `cbrAttr` 的问题。
- 参数长度使用策略枚举自身的 `sizeof`。
- 检查并向上传递 `MAPI_ADAPT_VENC_SetFrameIncStrategy()` 的失败码。
- 同时覆盖完整初始化和局部 VENC 重建路径。
- 保留 HC112_B 原有 GPS、时间、Logo 水印，没有采用参考补丁中删除大量 OSD 的改动。
- 保留 AENC 通道缓冲设置，避免为节省内存导致音频编码初始化失败。

### 8.3 没有直接照搬的参考补丁内容

`1.patch` 一共涉及 26 个文件，其中包含文件系统清理、空间监控、AENC、OSD、录像管理等修改。它们不全是实现 4K 插帧的必要条件。

真正的插帧核心是：

```text
ot_mapi_venc_define.h
mapi_venc_adapt.h
mapi_venc_adapt.c
mapi_venc.c
component/media_venc.c
前路媒体模式 INI
双录模式选择 INI
MMZ/录像缓存配套配置
```

文件系统删除策略、恢复出厂、GPS/Logo 删除等不应与插帧功能捆绑迁移，否则很难定位故障，并可能破坏已有产品功能。

## 11. 风险与限制

1. **不是真原生 4K**：GC4653 当前链路输入为 2560×1440，4K由 VPSS放大，无法增加传感器没有采集到的空间细节。
2. **不是真实 25 张不同画面**：19→25使用 COPY，每秒约有6张重复帧，快速运动时可能看到轻微节奏不均。
3. **触发条件较窄**：当前只识别 H.265/QVBR 的19→25和25→30。以后改成 CBR、H.264或其他帧率时不会自动启用。
4. **全局布尔量依赖串行初始化**：`g_vencFrameInsertion` 假定 VENC 通道依次初始化；若未来并行创建多个通道，应改为按 `vencHdl` 保存状态。
5. **ringbuf_mmz 余量有限**：8MiB需要同时容纳前后路录像环形缓存，增加码率或预缓存时间可能再次导致 MMZ 申请失败。
6. **配置名称与实际值不一致**：`1440p30`/`OT_PARAM_MEDIAMODE_1440P_30` 当前实际输入为19fps，维护时必须看INI内容，不能只看名字。
7. **配置注释可能过时**：部分 `bufsize` 后面的尺寸注释与当前4K参数不完全一致，审核时应以实际字段值和SDK计算方式为准。

## 13. 一句话总结

HC112_B 的 4K＋1K 是“**GC4653 2560×1440@19 → VPSS 放大到 3840×2160@19 → VENC COPY 插帧到 25fps**”与“**后路 AHD 1920×1080@25 正常编码**”两条独立链路共同运行的结果；实现关键不只是改分辨率，还包括 VENC 创建前的复制帧策略、创建时的临时帧率、创建后的真实帧率恢复，以及配套的 MMZ/录像缓存划分。
