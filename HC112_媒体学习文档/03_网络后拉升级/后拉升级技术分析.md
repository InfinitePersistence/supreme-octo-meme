## 1. 为什么要做后拉升级（动机）

要讲“为什么要做后拉升级”，得先回答上一层的问题：**我们为什么要在后路上加“网络摄像头”这一套？** 想清楚这个，升级的必要性就是水到渠成的结果。

### 1.1 为什么要加“网络后拉”——两个产品动机

传统记录仪的后路，往往是一路**模拟/本地并接**的低规格摄像头，跟前路挤在同一颗 SoC 上。我们改成**独立的网络后拉**（后路自成一颗芯片、走以太网连主机），是出于两个很实在的产品考量：

**动机一：提高整机规格——做到「前 4K60 + 后 2K30」双路高清。**
前路一颗 SoC 的编码/带宽/内存是有上限的，如果前后两路都压在它身上，规格必然互相让步。把后路独立成一颗自带 ISP + 编码的网络摄像头后，**前路可以专心做 4K60，后路独立做 2K30**，两路各自吃满自己的算力，整机对外规格直接拉到「4K60 + 2K30」这个档位——这是单芯片方案很难同时做到的。

**动机二：后路用自家芯片/模组——完善生态、多赚一份钱。**
后路模组如果外购，利润和话语权都在别人手里；改用**我们自己公司的芯片和模组**，好处是双重的：
- **生态更完整、配套更可控**：前后路协议、画质调校、OSD 叠加、升级机制都能端到端自研优化，不受第三方模组接口/迭代节奏牵制；
- **多一份营收**：原本要付给外部模组厂的那份钱，现在留在公司内部——整机之外，**后路模组本身也成了一块可对外销售、可复用到其他机型的生意**。

一句话：**加网络后拉，对上是把整机规格顶上去（4K60+2K30），对内是把后路这块价值和生态握在自己手里。**

#### 顺带一提：这条路线的平台代表——22AP70

这套“主机 + 网络摄像头”的打法，并不是我们独创，而是行业方向。以海思 **22AP70 超高清智能网络录像机（NVR）SoC** 为例，它的定位就天然是“一台主机用以太网聚合多路网络摄像头”（引自《22AP70 超高清智能网络录像机 SoC 用户指南》00B01, 2022-11-30，§1.1/§1.3）：

| 维度 | 22AP70 规格 |
|------|------------|
| 定位 | 超高清智能**网络录像机** SoC |
| 视频 | 多路 sensor 接入、**4K60 ISP**(补丁4K67.5)、3F WDR、H.264/H.265/JPEG 编解码 |
| CPU | ARM **Cortex-A55 MP4 @1.4GHz**（512KB L3，Neon FPU） |
| AI | **2.5 Tops@INT8**，Vision Q6 DSP、NNIE |
| 网络 | **双路 GMAC（GEPHY）**、PCIe RC/EP、USB3.0 |
| 存储 | 64bit DDR4/LPDDR4(x)、SPI Flash/eMMC、SDXC |

关键就是**双千兆 GMAC + 多路视频**——正说明这类平台的自然形态就是“主机挂多路网络摄像头”，跟我们“前拉 + 网络后拉”的思路完全一致。

> **准确说明**：本 build 的**前路主控实际是 SS927V100**（`config.conf: CONFIG_SS927V100=y`），后路是 **CV610**。22AP70 只是作为**同类网络化平台的代表**用来佐证路线方向，**不是**本 build 的芯片。理解这条演进线即可，不必纠结具体型号。

### 1.2 网络后拉带来一个新问题：车尾那颗摄像头怎么升级？

好，后路独立成网络摄像头，规格和生态都拿到了。但**天下没有免费的午餐**——后路一旦变成一颗**跑着自己独立固件**的芯片（本 build 为 **CV610**），就冒出四个单芯片时代不存在的问题：

1. **主机碰不到后路的 Flash**。本地升级只能读写**前路自己**的 MTD/eMMC 分区，物理上访问不到后路 CV610 的 Flash。
2. **前后固件必须配套**。前路每版固件都依赖后路的协议（心跳字段、OSD 叠加、倒车信号、拍照接口），后路落后会不兼容，必须能同步升。
3. **不能拆机刷后路**。后路装在车尾、无屏无键，量产/售后不可能拆下来接烧录器，也无法本地交互。
4. **应复用已有链路**。前后路之间**本来就有**一条以太网 + 私有心跳链路在跑，升级应复用它，而不是新拉硬件通道。

**后拉升级就是这四条的答案。** 一句话定义目标：

> **在“主机 + 网络子摄像头”架构下，为没有独立升级入口的后路，提供一条复用以太网心跳链路、由前路主机驱动的整机 OTA 升级通道。**

带着这个目标往下看，所有设计选择都能自洽。

## 2. 先建立整体认知（一张图看懂）

在钻代码之前，先在脑子里装一张图。整个系统是**两颗芯片、两条 TCP 通道**：

```
   ┌─────────────────── 前路主机 SS927（本仓库固件） ──────────────────┐
   │                                                                    │
   │   ss_media_netclient.c              upgrade_netCamera.c            │
   │  ┌──────────────────┐  ①控制/心跳   ┌────────────────────────┐    │
   │  │  TCP 客户端       │  通道         │  TCP 服务器 :4400        │    │
   │  │  连 192.168.1.69  │◀────────────▶│  等后路反连，逐分区推送   │    │
   │  │  发心跳 / 收状态   │              │  升级镜像                │    │
   │  └───────┬──────────┘              └───────────┬────────────┘    │
   │          │ 版本比对/找包                        │ ②升级数据通道     │
   │          ▼  (ss_eventhub 事件)                  │                  │
   │   UI：cam2_upgrade_page.c / ui_lvgl_home.c       │                  │
   └───────────────────────────────────────────────┼──────────────────┘
                                                    │
                        以太网（后路 IP 192.168.1.69）│
                                                    ▼
   ┌─────────────────── 后路 CV610（独立固件） ────────────────────────┐
   │  平时：回心跳、上报版本/倒车状态                                     │
   │  升级：反连主机 :4400，逐分区收镜像 → 写自身 Flash → 回 "xxx OK"     │
   └────────────────────────────────────────────────────────────────────┘
```

**两条通道分工**（这是全系统最重要的设计，先记住）：

| 通道 | 谁是服务器 | 端口 | 跑什么 | 什么时候用 |
|------|-----------|------|--------|-----------|
| ① 控制/心跳 | 后路 | `NET_CHECK_CONNECT_PORT` | 心跳、版本、状态、**升级握手** | 一直在跑 |
| ② 升级数据 | **前路** | `4400` | 后路固件镜像大文件 | 握手成功后才起 |

> **为什么要拆两条通道？** 因为心跳是“小而频繁、必须实时”，升级数据是“大而慢、会长时间占满带宽”。混在一条通道里，大文件传输会把心跳饿死、连接判死。拆开后，握手用心跳链路轻量完成，真正的大数据走独立 socket，互不干扰——甚至升级期间主动把心跳链路断掉（见 5.4.3）。

记住这张图，后面每一节都是在给这张图“填细节”。

## 3. 核心难点：为什么不能照搬本地升级

本地升级（第 7 章详述）已经很成熟了，为什么后拉不能直接复用？把差异摆出来，就知道后拉升级到底难在哪、要额外解决什么：

| 问题 | 本地升级 | 后拉升级面对的现实 |
|------|---------|-------------------|
| 升级对象在哪 | 前路自己的 Flash，**直接 open/write** | 后路的 Flash，**够不着**，只能把数据送过去让后路自己写 |
| 数据怎么过去 | 文件系统里读文件 | **要走网络**，涉及连接、握手、分包、应答、重传 |
| 怎么知道该升 | 插卡扫描 `.pkt` | 后路在不在线？版本多少？——**得先建立通信拿到对端状态** |
| 何时开始 | 用户点确认 | 后路要先**重启进入升级态**，主机得等它准备好 |
| 出错怎么办 | 本地重试即可 | 网络会断、会丢包、对端会没响应——**要有超时和失败判定** |
| 校验谁做 | 本地 magic + CRC + MD5 | 数据在后路落地，**端到端校验依赖后路**，前路只能靠应答确认 |

结论：后拉升级的本质是把“**本地的一次文件写 Flash**”变成“**一套跨设备的网络升级协议**”。于是它必须自己解决：**联网 → 找包 → 比版本 → 握手 → 传输 → 应答 → 反馈 → 收尾**这一整条链路。这正好就是第 4 章的技术点清单。

## 5. 逐层深入

### 5.1 通信基础：两颗芯片怎么联网

**是什么**：前后路通过以太网互联，后路固定 IP `192.168.1.69`。平时跑一条**心跳链路**保活并同步状态。

**为什么这么做**：升级前必须先知道“后路在不在、什么版本、准备好了没”。这些信息只能通过通信拿到。与其为升级单开一条链路，不如复用平时就在跑的心跳链路——省资源、也天然复用了“对端在线检测”。

**怎么实现**：前路作 **TCP 客户端**主动连后路，一个线程里循环“发心跳 + 收状态”：

```c
// ss_media_netclient.c:212
void* tcp_client_fun(void* arg) {
    while (task_t.running) {
        while (task_t.fd == -1) { init_tcp_client_socket(); }   // 断了就重连
        while (task_t.running) {
            if (send_heart_msg() < 0) break;                    // 发心跳
            if (recv_heart_msg() < 0) break;                    // 收后路状态
            usleep(500*1000);                                   // 0.5s 一拍
        }
    }
    return NULL;
}
```

心跳上行（`send_heart_msg`）携带的不只是“我还活着”，还有**前路要下发给后路的业务数据**：OSD 时间串、GPS 叠加、后路镜像/翻转配置——因为后路画面上的时间/GPS 水印其实是前路算好、告诉后路怎么叠的：

```c
// ss_media_netclient.c:337  下发后路镜像/翻转设置
SS_PDT_PARAM_GetCamParam(..., OT_PDT_CAMID_REAR, OT_PARAM_TYPE_MIRROR, &msg_t.backCamMirror, ...);
SS_PDT_PARAM_GetCamParam(..., OT_PDT_CAMID_REAR, OT_PARAM_TYPE_FLIP,   &msg_t.backCamFlip,   ...);
msg_t.msg_type = MSG_OSD;   // 默认心跳类型
```

心跳下行（`recv_heart_msg`）读回一个结构体，拿到后路的在线/倒车状态和**版本号字符串**——后面握手全靠这个字符串：

```c
// ss_media_netclient.c:92
struct msg_backcam_status {
    td_bool backcam_status;    // 后路在线
    td_bool reverse_status;    // 倒车信号
    td_char backcam_version[64];  // ★ 后路版本 / 握手关键字都塞在这里
};
```

**连接细节里的两个工程技巧**（值得学）：
- **非阻塞 connect + select 超时**：`connect_server` 先把 socket 设 `O_NONBLOCK`，`connect` 后用 `select` 等 1 秒可写，再用 `getsockopt(SO_ERROR)` 确认，避免默认阻塞 connect 卡死几十秒（`ss_media_netclient.c:153-207`）。连上后再改回阻塞模式收发。
- **升级期间拒绝重连**（见 5.4.3），把带宽让给数据通道。

#### 5.1.1 顺带理解：后路视频是怎么传上来的

前面讲的心跳链路只传“状态和小数据”。那**后路的画面**是怎么显示到前路屏幕上的？这是另一条**独立的视频通道**，虽然不属于升级，但理解它有助于看清前后路的整体协作——而且它和升级数据通道用的是**同一套“私有帧头 + TCP”套路**。

**是什么**：后路 CV610 把自己的画面**编码成 H.265 码流**，通过以太网推给前路；前路**解码后显示**。

**为什么这么做**：后路画面是 sensor 采集的，要显示在前路屏上，跨芯片只能走网络。传原始 YUV 太大（一帧 1080p 就好几 MB），所以后路先**硬件编码成 H.265**再传，前路再**硬件解码（VDEC）**——用编解码把带宽压下来，这是网络摄像头的标准做法。

**怎么实现**（和升级数据通道对称，但这次**前路当服务器**）：

1. **前路监听 8080，等后路反连**（`sample_public_vdec.c:239 prepare_recv_vdec_init`）：

```c
address.sin_port = htons(8080);
bind(...); listen(...);
// accept 带超时轮询：后摄拔出或超时(3s)即放弃，绝不无限阻塞状态机线程导致永久黑屏
select(listen_fd+1, &readFds, ...);
data_fd = accept(...);
```

2. **私有帧头协议**：每帧前面带一个定长头 `stream_header`，描述这一帧（`ss_media_netclient.h:43`）：

```c
struct stream_header {
    td_u64  magic;         // 魔数，帧同步校验
    td_u32  venc_chn;      // 编码通道
    td_u32  length;        // ★ 这一帧码流的字节数
    td_u64  pts;           // 时间戳
    td_bool bKeyFrameFlag; // ★ 是否关键帧(I 帧)
    td_u64  reserved;
};
```

3. **收流线程 `VDEC_SendStream`（`sample_public_vdec.c:316`）**：**先收固定长度的帧头，再按 `header.length` 收一整帧码流**，然后送硬件解码：

```c
// 先收帧头
while (total < sizeof(header)) { recv(data_fd, &header + total, ...); ... }
// 再按帧头里的 length 收一帧数据
while (total < header.length) { recv(data_fd, stream.streamAddr + total, ...); ... }
// 送 VDEC 解码
SS_MAPI_VDEC_SendStream(SAMPLE_VDEC_HANDLE_0, &stream, 2);
```

4. **首帧必须等关键帧**：新连接建立后，若首帧不是 I 帧（`bKeyFrameFlag` 为假）就丢弃，直到收到关键帧——否则 P 帧先于 I 帧送解码会花屏（`sample_public_vdec.c:398`）：

```c
if (!vdecContext.firstFrame && !header.bKeyFrameFlag) {
    continue;   // 还没来关键帧，P 帧先丢掉
}
```

5. 解码出的图像再经 **VPROC/VPSS** 缩放送预览端口显示（`NET_LIVE_VPORT`）。

**串起来看，前后路之间其实有三条 TCP 链路**：

| 链路 | 服务器端 | 端口 | 传什么 | 帧格式 |
|------|---------|------|--------|--------|
| 心跳/控制 | 后路 | `NET_CHECK_CONNECT_PORT` | 状态、版本、握手 | 定长结构体 |
| **视频流** | **前路** | `8080` | 后路 H.265 画面 | `stream_header` + 码流 |
| 升级数据 | 前路 | `4400` | 后路固件镜像 | 裸文件流 + `OK` 应答 |

> 可以看到：**“私有定长帧头 + TCP 流”是这套系统跨芯片传数据的统一范式**——视频用它带 `length`/关键帧标志，升级用它带分区应答。理解了视频通道，再回头看升级的数据通道（5.5）就毫无障碍了。

### 5.2 升级包怎么组织

**是什么**：后路升级包不是一个文件，而是 SD 卡上的一个**目录**，里面是后路各分区的**裸镜像文件** + 一个版本文件。

**为什么这么做**：后路 CV610 是一整套 Linux 系统（uboot / 内核 / rootfs / appfs / 参数区）。与其打成一个私有格式的包再解析，不如直接把每个分区镜像单独放好——**传输时一个分区一个文件地送，天然对应后路一个分区一个分区地烧**，逻辑最简单，也方便产测替换单个分区。

**怎么实现**：路径和分区清单都是硬约定：

```c
// ot_upgrade_netCamera.h
#define CAM2_PKG_FULL_DIR        "/app/sd/et104_pkg"            // 升级包目录
#define CAM2_PKG_VERSION_FILE    "/app/sd/et104_pkg/version.txt" // 版本文件
#define CAM2_PKG_VERSION_FACTORY "/app/sd/et104_factory.txt"     // 产测触发标志
#define PARTITION_COUNT 8
```

8 个分区（`upgrade_netCamera.c:584`）：

```c
char* file_array[PARTITION_COUNT] =
    {"u-boot.bin","uImage","rootfs.jffs2","appfs_01","appfs_02",
     "rawparam","rawparambak","resImage"};
```

一个小设计点：`appfs_01` 和 `appfs_02`（下标 3、4）是后路的两个逻辑 appfs 分区，但物理上**共用同一个 `appfs.jffs2` 文件**——传输时都读这一个文件，只是应答关键字分别是 `appfs_01 OK` / `appfs_02 OK`：

```c
// upgrade_netCamera.c:208  传输时把 3/4 号都指到 appfs.jffs2
if (i == 3 || i == 4) {
    snprintf(name_path, 32, "%s/appfs.jffs2", CAM2_PKG_FULL_DIR);
}
```

### 5.3 版本比对：要不要升、能不能升

**是什么**：拿后路当前版本和包里的版本比，决定是否升级；并对“太旧、非法、已最新”做防呆拦截。

**为什么这么做**：OTA 最怕**乱升**——升成更旧的、升入不兼容的、明明最新还反复升。所以比对逻辑不能只写一句 `if (new > old)`，要把各种异常挡在外面。

**怎么实现**：版本号用 **`yyMMdd` 日期串**（如 `250316`），`atoi` 转整数比大小。核心防呆在 `Compare_cam2_NewPkg_Version`：

```c
// upgrade_netCamera.c:532（节选逻辑）
int now = atoi(fw_str);    // 后路当前版本 yyMMdd
int pkg = atoi(pkg_str);   // 包版本 yyMMdd

if (now == 0)   { ... return TD_FALSE; }   // 后路还没上报有效版本 → 不升
if (now == pkg) {                          // 已是最新
    event.EventID = OT_EVENT_NETCAMERA_VERSION;   // → UI 提示“已是最新版本”
    SS_EVTHUB_Publish(&event);
    return TD_FALSE;
}
if (pkg <= 250316) {                       // ★ 低于基线的包一律拒绝（防刷入过老固件）
    event.EventID = OT_EVENT_NETCAMERA_VERSION;
    SS_EVTHUB_Publish(&event);
    return TD_FALSE;
}
return TD_TRUE;                             // 通过，可升
```

比对通过后，`Find_Check_NetCamera_all_NewPkg`（`:580`）逐个 `stat()` 分区文件，把大小填进全局表 `upgrade_info[8]`，并把整张大小表打包进事件 payload 发给 UI：

```c
upgrade_info[i].pkg_size = st.st_size;              // 记录每个分区大小
...
memcpy(pkg_info, &upgrade_info[0].pkg_size, size);  // 打包给 UI 展示
```

> **学习点**：版本用日期串是嵌入式常见做法——单调递增、人能读、`atoi` 就能比。代价是无法表达“分支版本”，且强依赖构建时正确打日期。

### 5.4 握手协议：三段式字符串状态机

这是整个后拉升级**最精妙也最脆弱**的一环，重点讲。

**是什么**：主机和后路要就“现在开始升级”达成一致。主机通过心跳里的 `msg_type` 下行意图，后路通过 `backcam_version` 字符串里的**关键字**上报自己的状态，双方靠状态机推进。

**为什么用字符串握手**：因为**复用了心跳链路**（5.1）。心跳本来就在传 `msg_type` 和 `backcam_version`，握手不新增协议字段，直接往这两个已有字段里塞“暗号”，改动最小。代价是——协议脆弱、靠 `strstr` 匹配关键字（见第 8 章风险）。

**怎么实现**：

前路的状态用一个枚举表示：

```c
// ss_media_netclient.c:71
typedef enum {
    PKG_PREPARE_FIND = 0x00,   // 准备找包
    PKG_NOT_EXIST,             // 无包
    PKG_MSG_PUBLISH,           // 已通知后路“有新包”，等它应答
    PKG_MSG_UPGRADE_START,     // 已进入传输，心跳不再重连
} PKG_STATUS;
```

**三段式时序**（把它当成一个握手协议来记）：

| 阶段 | 前路做什么 | 下行 `msg_type` | 后路回什么（`backcam_version` 含） | 前路状态迁移 |
|------|-----------|-----------------|-----------------------------------|-------------|
| ① 找包 | 找到新包 | `MSG_UPGRADE_ALL_P` | — | `FIND → PKG_MSG_PUBLISH` |
| ② 后路重启 | 收到 `"reboot"` | — | `...reboot...` | 关 gsensor + **主机自己也重启** |
| ③ 后路请求发包 | 收到 `"upgrade send"` | `MSG_UPGRADE_ALL_S` | `...upgrade send...` | `→ PKG_MSG_UPGRADE_START`，发 `ALL_START` 事件 |

对应代码（`ss_media_netclient.c:362-386`）：

```c
} else if (PKG_MSG_PUBLISH == package_status) {
    if (strstr(g_backCamStatus.backcam_version, "reboot") != NULL) {
        SS_GSENSORMNG_Deinit();     // ② 关 gsensor，防重启期间 i2c 报错
        SS_SYSTEM_Reboot();         //    主机自己重启
    } else if (strstr(g_backCamStatus.backcam_version, "upgrade send") != NULL) {
        msg_t.msg_type = MSG_UPGRADE_ALL_S;
        package_status = PKG_MSG_UPGRADE_START;
        SS_UPGRADE_SetUpgradeStatus();               // 打全局“升级中”标志
        event.EventID = OT_EVENT_NETCAMERA_UPGRADE_ALL_START;
        SS_EVTHUB_Publish(&event);                   // ③ 通知 UI 切进度页 + 起传输线程
        sleep(2);
    }
}
```

#### 5.4.1 为什么第②步主机自己也要重启？

初学者最容易困惑这里。原因是：后路收到“有新包”后要**重启进入升级态**；主机重启，是为了在重启后建立一条**只跑升级、不跑双路推流的干净链路**——避免推流线程和升级 socket 抢网络/内存资源。头文件注释点破了这一点：

```c
// ot_upgrade_netCamera.h:26
OT_EVENT_NETCAMERA_UPGRADE_ALL_PREPARE, //后路创建/home/upgrade.txt 重启设备，不启动两个推流的通信线程
```

所以测试时“主机会重启一次”是**正常现象**，不是异常。

#### 5.4.2 触发时机：寄生在心跳里的轮询

握手第①步的“找包”不是独立线程，而是**寄生在 `send_heart_msg` 里**，每 13 个心跳周期查一次：

```c
// ss_media_netclient.c:344

    if (++new_heart_counts % 13 == 0 || isFactoryBurn) {

                    CAM2_PKG_FULL_DIR, netcam_version, msg_t.msg_data);
                if (check_result) {
                    msg_t.msg_type = MSG_UPGRADE_ALL_P;         // ① 通知后路有新包
                    package_status = PKG_MSG_PUBLISH;
                }
            }
        }
        ...
    }
}
```

两个前置条件值得注意：`et104_factory.txt` 存在（**产测/工厂模式**才触发）、`/app/sd/Video_Front` 存在（**只有前路机**才推送升级，区分前后路）。

> **学习点**：把“定时任务”挂在一个已有的周期性函数里（心跳），是资源受限嵌入式的常见做法——不用额外线程、天然限频（每 13 拍一次）。缺点是耦合，找包逻辑和发心跳搅在一起。

#### 5.4.3 升级期间“主动放手”心跳链路

一旦进入 `PKG_MSG_UPGRADE_START`，心跳客户端不再重连，把网络让给数据通道：

```c

    return -1;

```

这正是 5.1 里“两条通道分工”的落地——控制通道功成身退，数据通道接管。

### 5.5 数据传输：逐分区推送 + 应答

**是什么**：握手成功后，前路翻身当 **TCP 服务器**监听 `4400`，等后路反连，然后把 8 个分区镜像**一个一个**送过去，每送完一个等后路回 `"<分区名> OK"` 才发下一个。

**为什么这么设计**：
- **前路当服务器**：后路刚重启完，由它主动来连主机、主机被动 accept，时序更好控（主机先把 server 架好等着）。
- **逐分区 + 应答（停等协议）**：后路收一个分区要**擦写一大片 Flash**，很慢。如果主机不管不顾地把 8 个分区连着灌过去，后路缓冲会溢出。用“发一个 → 等一个 OK → 再发下一个”的**停等**方式，用应答做**流控**，天然把主机节奏压到后路能消化的速度。

**怎么实现**：由 UI 收到 `ALL_START` 后调 `SS_NETCAMERA_UPGRADE_ALL_PARTITION_PREPARE()` 起线程：

```c
// upgrade_netCamera.c:138
td_s32 SS_NETCAMERA_UPGRADE_ALL_PARTITION_PREPARE(void) {
    SS_UPGRADE_SetUpgradeStatus();
    pthread_create(&upgradeId, NULL, SS_NETCAMERA_UPGRADE_TASK_ALL_PARTITION, NULL);
    pthread_detach(upgradeId);
    return TD_SUCCESS;
}
```

传输线程主体（`upgrade_netCamera.c:146`）流程：

```
malloc 10KB 缓冲
socket → bind(:4400) → listen → accept   // 等后路反连
for (i = 0; i < 8; i++) {
    if (分区大小 == 0) continue;           // 包里没这个分区 → 跳过
    打开分区文件（3/4 号读 appfs.jffs2）
    while (还有数据) {
        read 10KB → 循环 write 到 socket   // 处理短写
        大分区(>1MB) 每块 SS_Usleep(1000)  // 限速，见 5.6
    }
    发 OT_EVENT_UPGRADE_PROGRESS，arg1 = (i+1)*10   // 进度粗粒度：每分区 +10%
    大分区发完 sleep(18)                   // 等后路擦写 Flash
    while (1) 阻塞读 socket，等 "<分区> OK" // 停等应答
}
发 OT_EVENT_UPGRADE_PROGRESS(100) → OT_EVENT_NETCAMERA_UPGRADE_ALL_SUCCESS
```

发送核心（注意**内层 while 处理“短写”**——一次 `write` 不保证写完，要循环）：

```c
// upgrade_netCamera.c:219

    read_size = read(pkg_fd, send_buff, UPGRADE_MEM_SIZE);   // 10KB

```

停等应答与失败判定：


### 5.6 可靠性设计：限速、超时、失败与复位

网络升级必须假设“**什么都可能出错**”。这一节把 T6 的容错手段单独拎出来讲，它们散落在传输线程各处：

1. **限速让后路跟得上**：大分区每 10KB `SS_Usleep(1000)`；单分区发完 `sleep(18)`。目的都是**给后路擦写 NAND 留时间**。这些是**硬编码经验值**——后路 Flash 变了、数据量变了都要重新标定，否则会 5 次超时误判失败。

2. **停等应答做流控 + 超时**：`count_upgrade == 5` 判失败（≈ 5 秒没收到 OK），发 `ALL_FAIL` 让 UI 提示重试。

3. **短写/短读循环**：`read`/`write` 都不保证一次完成，代码用内层 while 补齐，避免丢字节。

4. **统一错误出口**：`error / error_malloc / error_write` 三个标号，都做 `close(socket)` + `free(buff)`，延时后发 `ALL_FAIL`，保证资源不泄漏、UI 有反馈：

```c
// upgrade_netCamera.c:342
error:
    close(socket_upgrade); close(socket_srv); free(send_buff);
    SS_Usleep(1000*5000);
    event.EventID = OT_EVENT_NETCAMERA_UPGRADE_ALL_FAIL;
    SS_EVTHUB_Publish(&event);
    return NULL;
```

5. **后路硬复位**（旧的单分区路径 `SS_NETCAMERA_UPGRADE_TASK` 结尾）：写寄存器拉低再拉高，等价给后路一个 reset 脉冲，让它带新固件重启：

```c
// upgrade_netCamera.c:454
sleep(2);
OT_WriteReg(0x1109a004, 0x0);
usleep(300 * 1000);
OT_WriteReg(0x1109a004, 0xff);
```

> **一个已知瑕疵**（第 8 章还会提）：`count_upgrade==5` 命中后只 `Publish(FAIL)`，**循环没 break**，线程还会继续 `sleep(1)` 空转等应答。功能上 UI 已提示失败，但线程没干净退出，属可改进点。

### 5.7 进度与 UI：事件驱动的状态机

**是什么**：升级全程用户要能看到“检查中 / 升级中 X% / 成功 / 失败”。这套反馈完全由 `ss_eventhub` 事件驱动，UI 只是事件的消费者。

**为什么用事件**：符合本项目的**模块解耦**约定（见 CLAUDE.md）——升级组件不直接调用 UI，而是发事件；UI 订阅事件更新画面。升级逻辑和界面彻底分离，谁都能独立改。

**怎么实现**：事件在 `ot_upgrade_netCamera.h:18` 定义，由 `SS_NETCAMERA_UPGRADE_RegisterEvent`（在 `ss_product_main.c:283` 的 `g_registerEventOps[]` 注册）注册到总线；UI 侧订阅见 `hi_product_ui.c:164`。

事件 → UI 行为对照：

| 事件 | 何时发 | UI 响应（`ui_lvgl_cam2_upgrade_page.c`） |
|------|--------|------------------------------------------|
| `OT_EVENT_NETCAMERA_VERSION` | 已最新/过老 | 提示“已是最新版本” |
| `OT_EVENT_NETCAMERA_UPGRADE_ALL_START` | 握手成功 | 切进度页 + 调 `..._ALL_PARTITION_PREPARE()` 起传输线程 |
| `OT_EVENT_UPGRADE_PROGRESS` | 每分区完成 | `SetProgress(arg1)` 推进进度条 |
| `OT_EVENT_NETCAMERA_UPGRADE_ALL_SUCCESS` | 全部完成 | 进度置 100%，显示成功，起 3s 定时器后重启 |
| `OT_EVENT_NETCAMERA_UPGRADE_ALL_FAIL` | 传输/应答失败 | 显示失败 / 请重试 |

进度页自身也是个**小状态机** `Cam2UpgradeSubState`：`CHECKING`（检查中，2s 自动消失）→ `PROGRESS`（升级中，**禁止误关**）→ `LATEST`（已最新，可手动关）。收到 `ALL_START` 会从 CHECKING 主动切 PROGRESS，并清掉自动消失定时器，防止升级中弹窗被关掉（`ui_lvgl_cam2_upgrade_page.c:345-352`）——这对齐了功能文档 12.4.3“升级过程中所有按键失效”。

## 7. 对比本地升级，加深理解

把后拉升级和**本地升级**（`ss_upgrade.c` / `upgrade_partition.c`）并排看，能更深理解“网络升级为什么这么设计”：

| 维度 | 本地升级（前路自己） | 后拉升级（后路 CV610） |
|------|---------------------|------------------------|
| 升级对象 | 前路 SS927 自身 Flash | 后路 CV610 Flash |
| 包格式 | 单一 `.pkt`（头+分区数据+尾） | 目录 + 8 裸分区文件 + `version.txt` |
| 完整性校验 | **头尾 magic + 全包 CRC32 + 文件名 MD5 + 分区/Flash 尺寸检查** | 仅版本比对 + 逐分区 `OK` 应答，**无 CRC/MD5** |
| 写 Flash | 本地 `SS_Flash_*`，分 bin/ext4-sparse/yaffs | 后路自己写，前路只送 socket 数据 |
| 断点/状态 | 寄存器 `PWR_USER_REG0`/`SOFTINT_REG` 记升级态，重启后判成功/失败 | 全局标志 + 字符串握手 |
| 进度 | 按写入字节数**精确**上报 | 每分区固定 **+10%** 粗粒度 |
| 触发 | 插卡扫描 `.pkt` / APP OTA | 心跳内 13 周期轮询 |

本地包结构（对照理解“正规升级包长什么样”）：

```c
// ot_upgrade_define.h
#define OT_UPGRADE_PACKET_HEAD_MAGIC  0x08122515   // 头 magic
#define OT_UPGRADE_PACKET_TAIL_MAGIC  0x0812251d   // 尾 magic
typedef struct UPGRADE_PKT_HEAD_S {
    td_u32 u32Magic;
    td_u32 u32Crc;        // 从 HeadVer 到 image-data 的 CRC32
    td_u32 u32PktLen;
    td_u8  pktType;       // 0:uboot写MTD 1:linux写MTD 2:linux写全MTD
    td_char szPktSoftVersion[...];
    td_u32 au32PartitionOffSet[OT_UPGRADE_MAX_PART_CNT];
    ...
} OT_UPGRADE_PKT_HEAD_S;
```

本地升级的 CRC 从 `u32HeadVer` 起算（跳过前 8 字节 magic+crc 自身），逐 64KB 累加（`UPGRADE_CheckPktCrc`，`ss_upgrade.c:324`）。**这正是后拉升级欠缺的端到端校验**——见下章风险。

## 8. 技术点小结与风险清单

**技术点回顾**（学完应该能复述）：

1. **两条 TCP 通道分工**：心跳（后路当 server）跑控制/握手，`:4400`（前路当 server）跑数据。
2. **握手是字符串状态机**：`MSG_UPGRADE_ALL_P` → `"reboot"`（双方重启）→ `"upgrade send"` → `ALL_START`。
3. **传输是停等协议**：逐分区发、等 `OK`、应答做流控。
4. **反馈是事件驱动**：eventhub 解耦升级逻辑与 UI。
5. **版本用日期串**，多重防呆拦截。

**风险 / 可改进点**（分享时重点提示）：

| 风险 | 说明 | 影响 |
|------|------|------|
| 握手靠 `strstr` 关键字 | 后路改 `"reboot"`/`"upgrade send"`/`"OK"` 字样即握手失败 | 跨版本必须锁死关键字约定 |
| **数据通道无 CRC/MD5** | 只靠“逐分区 OK”，网络抖动致个别字节错但后路仍回 OK，可能刷入损坏镜像 | 安全性弱于本地升级，强依赖后路自校验 |
| 限速/`sleep(18)` 是经验值 | 后路 Flash/数据量变化未重标定，易 `count_upgrade==5` 误判失败 | 移植/改版需重新标定 |
| 失败判定后未 `break` | `:321` 命中 5 次仅发 FAIL，循环仍空转 | 线程未干净退出，可改进 |
| 触发依赖 `et104_factory.txt` | 当前主要面向产测/工厂 | 量产普通卡触发需确认门槛是否放开 |
| 主机会自重启 | 握手第②步 `SS_SYSTEM_Reboot()` | 测试时须视为正常，非异常 |
| appfs 双分区映射同一文件 | `appfs_01/02` 共用 `appfs.jffs2`，应答名不同 | 收发两端命名须严格一致 |
