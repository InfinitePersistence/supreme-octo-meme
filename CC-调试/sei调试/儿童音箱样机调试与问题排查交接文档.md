## 二、 核心问题汇总表（按严重度排序）

| 编号 | 所属模块 | 严重度 | 问题概述 | 核心根因 |
| :---: | :--- | :---: | :--- | :--- |
| **#1** | **语音助手 / 云端** | **P0（阻塞）** | 能正常语音唤醒（播报 `greet.wav`），但**无法回答任何问题** | 端侧唤醒走本地模型，而问答走云端 LiveKit；因板端未烧录 `usid`（Token 中 `sn` 为全 `0`），云端返回 `HTTP 503 / 404 NOT_FOUND`，无法获取 LiveKit 房间凭证 |
| **#2** | **Wi-Fi / 按键服务** | **P0（阻塞）** | 配网连上 Wi-Fi 后，**按一下板载音量键会导致 Wi-Fi 彻底断网** | `wifi_tool.sh` 由 `input_eventd` 拉起，`wpa_supplicant` 归属在 `input-eventd.service` 的 CGroup 下；按音量键时 `input_eventd` 因 MQTT 未连接抛未捕获异常 `SIGABRT` 崩溃，Systemd 清理 CGroup 时连带杀死了 `wpa_supplicant` 和 `udhcpc` |
| **#3** | **底层驱动 / I2C** | **P1（严重）** | 物理 I2C 按键失灵，且 `i2c_key` 每 200ms 报错引发系统日志风暴 | I2C-2 总线（`fe06a000.i2c`）上的 `aw9523_led (2-005b)` 和 `aml_ledring (2-001f)` probe 失败（`-6 ENXIO` 无 ACK），导致 `/usr/bin/i2c_key` 死循环报错，冲刷掉 `journald` 日志 |
| **#4** | **蓝牙功能** | **P1（重要）** | 手机搜索连接音箱蓝牙时，被手机系统**识别为“车载设备”** | `/usr/bin/bluez_tool.sh` 将蓝牙 CoD 硬编码为 `0x240408`（Minor Class `0x08` = `Hands-free Device` 免提设备），配合 `hfp-hf` 被手机判定为车载免提 |
| **#5** | **蓝牙 / 内核配置** | **P1（重要）** | `bluealsa` 开启了 HFP 免提（`-p hfp-hf`），但 `bluetoothd` 报错 RFCOMM 不支持 | 内核未开启 `CONFIG_BT_RFCOMM`，导致 `socket(STREAM, RFCOMM): Protocol not supported (93)`，HFP 实际不可用 |
| **#6** | **蓝牙功能** | **P2（一般）** | 每次整机重启后，蓝牙 MAC 地址（BD Address）随机变化 | UnifyKey 未烧写 `mac_bt`，`aml_hciattach` 每次生成 `22:22:xx:xx:xx:xx` 随机地址，导致手机配对记录失效 |
| **#7** | **Wi-Fi / 网络配置** | **P2（一般）** | 软 AP 接口 `wlan1` 未关闭且抢占默认路由；DNS 默认配置在局域网内解析超时 | `dhcpcd` 为 `wlan1` 分配 `169.254.x.x` 并生成默认路由；`/etc/resolv.conf` 指向 `systemd-resolved` 的 `1.1.1.1`/`8.8.8.8`；内核缺 `regulatory.db` |
| **#8** | **系统服务** | **P3（体验）** | 未同步 NTP 时间前 `alarmService` 每秒刷屏数十条日志；3 个 systemd 服务处于 `failed` | `alarmService` 缺少日志限频；`aml_key_inject` 缺 `/factory` 分区；`swupdate` 在非 recovery 模式下直接 `exit 1` |

## 三、 各板块详细排查过程、错误证据与解决方案

### 3.1 语音助手板块（`/usr/bin/speaker`）

#### 1. 进程与线程运行状态验证（已确认正常）
- **验证结论**：主进程 `/usr/bin/speaker` 及其 **61 个子线程**均正常启动并处于 `S (sleeping)` 事件循环状态。
- **关键子线程清单**：
  - `alsarecord` / `alsa-filter`：ALSA 6 通道麦克风录音（`pcmC0D4c`，16kHz `S16_LE`）实时采集中（`hw_ptr` 与 `appl_ptr` 同步递增，delay 仅 64 frames）。
  - `elevoc_kws` / `elevoc_core`：大象声科 4 麦语音唤醒模型（`/etc/speech/elevoc/homa/4MIC/ckpt-851-...EM2`）与前端降噪/AEC 运行正常，唤醒词 `hello_homa` 可稳定触发（置信度 `0.999+`）。
  - `livekitai`：LiveKit 实时语音交互客户端线程。
  - `gmain` / `gdbus` / `default-executo` / `grpc_global_tim`：D-Bus 与 gRPC 通信线程。
- **协同服务状态**：`ai_manager`、`audio_focus_manager`、`net_music_player`、`alarmService`、`guard` 均已正常启动。

#### 2. 错误分析：为什么能唤醒语音助手，却不能回答问题？（对应问题 #1 & #2）

**（1）端侧与云端链路差异**：
- **唤醒（本地离线）**：麦克风阵列采集 $\rightarrow$ `elevoc_kws` 本地识别 `hello_homa` $\rightarrow$ 发送 `SPEAKER_MESSAGE_WAKE` $\rightarrow$ `GstPlayer` 播放本地 `/usr/share/voice-assistance/greet.wav`。全程无需联网，因此每次都能唤起。
- **问答（云端实时）**：当前配置 `aiSpeakerMode=livekit`（日志打印 `SpeechToTextClient::init out (LiveKit passthrough, Google ASR skipped)`），需由 `LiveKitAiClient` 向 Skyway 云端请求实时房间 Token，建立 WebRTC 连接后才能传输语音和接收回答。

**（2）阻塞点 A：云端 Token 申请返回 `HTTP 503 / 404 NOT_FOUND`（设备 SN 为全 `0`）**
- **日志证据**（`/log/speaker_2026-11-09-02-18-28.log`）：
  ```text
  [info] Manual JWT parsing successful: {"aud":"0000000000000000",...,"sn":"0000000000000000","tenantCode":"1060",...}
  [info] get sn from token 0000000000000000
  [info] [LiveKitAiClient] ADK token request url=https://asia.skywayplatform.com/application/skyway-adk-nexus-application/application/realtime/token
  [info] [LiveKitAiClient] channelType=speaker_ai deviceSn=0000000000000000 region=us agent=t1292__speaker_ai_device_20260803
  [info] HTTP Response content: {"businessCode":"000000503","code":100,"message":"404 NOT_FOUND","time":1794191058828}
  [error] [LiveKitAiClient] ADK token HTTP status=503 url=https://asia.skywayplatform.com/application/skyway-adk-nexus-application/application/realtime/token
  [error] [15LiveKitAiClient] LiveKit credentials missing (url_len=0 token_len=0)...
  [warning] [15LiveKitAiClient] agent still not ready after 30000ms, stop keep-alive
  ```
- **附加错误日志**：
  - `/log/speaker1.log`：`[UnifyKey] usid = `（空）
  - `/log/speaker_2026-11-09-02-18-28.log`：`[error] can not get license from unifykey`、`[error] elevoc unauthorized !!!!!!!!!`
  - `ai_manager` 日志：持续刷屏 `SN: 0000000null000` 及 `connect_skyway_mqtt failed!`
- **根因**：板端 UnifyKey 未烧写 `usid`（设备序列号），且 `/etc/ble_revd/usertoken.txt` 中的 JWT 凭证使用了假序列号 `0000000000000000`（同时 `usertoken.txt` 内 `tenantCode` 为 `1060`，而 `/etc/speech/config.json` 中为 `1293`）。云端查不到该设备或对应 Agent 绑定关系，返回 `404 NOT_FOUND`。
- **解决方案**：
  1. **出厂/样机烧号**：向 UnifyKey `usid` 烧录在 Skyway 平台注册过的合法设备 SN，并写入大象声科授权 license；随后通过手机 App 重新走一次配网绑定，生成包含真实 `sn` 的 `/etc/ble_revd/usertoken.txt`。
  2. **开发阶段快速绕过验证（通过 Redis 注入凭证）**：
     `LiveKitAiClient` 支持从本机 Redis 读取覆盖参数，可在板端执行 `redis-cli` 注入合法凭证后重启 `speaker`：
     ```sh
     # 方式 A：指定已注册的合法设备 SN 与 Bearer Token
     redis-cli set VA_LIVEKIT_DEVICE_SN "<真实注册的SN>"
     redis-cli set VA_LIVEKIT_CES_BEARER "<合法的JWT_Token>"
     redis-cli set VA_LIVEKIT_CES_BASE_URL "https://asia.skywayplatform.com"

     # 方式 B：直接指定测试 LiveKit WebSocket 地址与房间 Token（跳过 ADK 接口）
     redis-cli set VA_LIVEKIT_BRIDGE_WS "wss://<livekit-server-url>"
     redis-cli set VA_LIVEKIT_TOKEN "<livekit-room-token>"
     ```

### 3.2 Wi-Fi 与网络板块

#### 1. 【严重 Bug】按音量键导致 `input_eventd` 崩溃，连带杀死 `wpa_supplicant` 造成断网（问题 #2）
- **复现过程与日志证据**（`journalctl` & `dmesg`）：
  1. 通过 BLE 配网脚本 `/etc/bluetooth/wifi_tool.sh` 连上热点 `dvbspeaker`（获取 IP `192.168.50.173`）。
  2. 按下板子音量键（`key 115`），`input_eventd` 尝试向 MQTT 发布音量变化事件，因 MQTT 未连接，重试失败后抛出未捕获的 `std::runtime_error` 异常并 `SIGABRT` 崩溃：
     ```text
     Nov 08 18:24:34 input_eventd[2865]: [INFO] [events_process.cpp:799 ProcessKey] 音量键释放：115
     Nov 08 18:24:34 input_eventd[2865]: MQTT loop error: The client is not currently connected.
     Nov 08 18:24:35 input_eventd[2865]: terminate called after throwing an instance of 'std::runtime_error'
     Nov 08 18:24:35 input_eventd[2865]:   what():  Publish failed after retries
     Nov 08 18:24:35 systemd[1]: input-eventd.service: Main process exited, code=killed, status=6/ABRT
     ```
  3. 同一毫秒，内核打印 `wlan0` 发送 `deauth (reason 3)` 断开连接，`wpa_supplicant` 和 `udhcpc` 进程彻底消失：
     ```text
     Nov 08 18:24:35 kernel: vm_cfg80211_disconnect 3133 <wlan0> reason_code=3
     Nov 08 18:24:35 kernel: <wlan0> wifi_mac_send_deauth 2714 mac[36:c5:99:91:6a:85] send station deauthenticate (reason 3)
     Nov 08 18:24:35 systemd-networkd[2805]: wlan0: Lost carrier
     ```
- **根因分析**：
  1. 配网脚本 `/etc/bluetooth/wifi_tool.sh` 是作为 `input_eventd` 的子进程被调用的。脚本内部执行了 `killall wpa_supplicant; killall dhcpcd`，然后用 `start-stop-daemon` 启动了新的 `wpa_supplicant` 和 `udhcpc`。这使得**新启动的 `wpa_supplicant` 和 `udhcpc` 在 systemd 中归属于 `input-eventd.service` 的 CGroup**（而非 `wifi.service`）。
  2. `/lib/systemd/system/input-eventd.service` 未配置 `KillMode=process`（默认为 `KillMode=control-group`）。当 `input_eventd` 因 MQTT 异常崩溃时，**systemd 自动清理整个 CGroup，将里面的 `wpa_supplicant` 和 `udhcpc` 一并 `SIGKILL` 杀死**。
  3. 5 秒后 systemd 仅重启了 `input_eventd`，导致系统处于无 `wpa_supplicant` 的永久断网状态，后续每次唤醒语音助手均报错 `network is unavailable!!!` 并播报 `network_unavailable.wav`。
- **解决方案**：
  - **板端立即修复（修改 `/lib/systemd/system/input-eventd.service`）**：
    在 `[Service]` 段下增加 `KillMode=process`，防止 `input_eventd` 异常退出时连带杀死子进程：
    ```ini
    [Service]
    Type=simple
    ExecStart=/usr/bin/input_eventd
    KillMode=process
    Restart=always
    RestartSec=5
    ```
    修改后执行 `systemctl daemon-reload`。
  - **源码级根治修复（2 处）**：
    1. **`input_eventd` C++ 源码**：在 MQTT `publish` 调用外层增加 `try { ... } catch (const std::exception& e)` 异常捕获，避免因 MQTT 断连导致按键守护进程直接 `abort()`。
    2. **`/etc/bluetooth/wifi_tool.sh`（及 `/var/www/cgi-bin/wifi/wifi_tool.sh`）**：配网时不要粗暴执行 `killall wpa_supplicant` 后自行后台拉起，而应复用 `wifi.service` 已启动的 `wpa_supplicant`（直接通过 `wpa_cli` 配置网络），或通过 `systemctl restart wifi.service` 由独立 systemd 服务管理生命周期。

#### 2. `wlan1` AP 接口抢占默认路由与 `regulatory.db` 缺失（问题 #7）
- **现象与证据**：
  - `ip route` 显示 `wlan1` 被 `dhcpcd` 分配了 `169.254.129.189/16` 并生成默认路由 `default dev wlan1 scope link src 169.254.129.189 metric 1003004`。
  - `dmesg` 报错：`[0.428061] failed to load regulatory.db`、`[10.990923] aml_read_macaddr_from_file read from /etc/wifi/wifimac.txt fail`。
- **解决方案**：
  1. 在 `/etc/dhcpcd.conf` 末尾添加 `denyinterfaces wlan1 ap0`，禁止 `dhcpcd` 在 AP 接口上请求地址。
  2. 将 `wireless-regdb`（`/lib/firmware/regulatory.db` 与 `regulatory.db.p7s`）打包进 Yocto 根文件系统。

### 3.3 蓝牙功能板块

#### 1. 手机将音箱蓝牙识别为“车载设备”（问题 #4）
- **现象与证据**：
  `hciconfig -a` 显示：
  ```text
  Name: 'AIspeaker-e58c'
  Class: 0x240408
  Service Classes: Rendering, Audio
  Device Class: Audio/Video, Hands-free
  ```
  检查 `/usr/bin/bluez_tool.sh` 第 222 行（`A2DP_SINK_SERVICE` 函数内）：
  ```sh
  hciconfig hci0 class 0x240408
  ```
- **根因分析**：
  根据 Bluetooth SIG 规范，CoD `0x240408` 的 Minor Device Class 为 **`0x08`（`Hands-free Device`，免提设备）**。iOS 和 Android 系统看到非耳机形态的独立 `Hands-free` 设备且开启了 `hfp-hf` 时，默认将其归类为**车载免提套件（Car Kit / 车载立体声）**。
- **解决方案**：
  将 CoD 修改为音箱/扬声器对应的 **`0x240414`（`Audio/Video - Loudspeaker`）**：
  1. 修改 **`/usr/bin/bluez_tool.sh`**：
     - 将 `A2DP_SINK_SERVICE()` 中的 `hciconfig hci0 class 0x240408` 改为 `hciconfig hci0 class 0x240414`。
     - 在 `BLE_COEXIST_SERVICE()` 的 `hciconfig hci0 up` 之后补充一行 `hciconfig hci0 class 0x240414`（防止 BLE 配网重置 `hci0` 后丢失 Class 配置）。
  2. 修改 **`/etc/bluetooth/main.conf`**：
     - 在 `[General]` 段下增加 `Class = 0x240414`。
  3. **手机端验证注意**：修改后需在手机蓝牙设置中**“忽略此设备/取消配对”**并重开一次手机蓝牙，清除手机对旧 MAC 地址的设备类型缓存。

#### 2. 内核未开启 `CONFIG_BT_RFCOMM` 导致 HFP 免提服务注册失败（问题 #5）
- **现象与证据**：
  `systemctl status bluez` 中 `bluetoothd` 报错：
  ```text
  bluetoothd[3000]: ../bluez-5.79/src/profile.c:ext_start_servers() RFCOMM server failed for Hands-Free unit: socket(STREAM, RFCOMM): Protocol not supported (93)
  ```
  检查板端内核配置 `zcat /proc/config.gz | grep CONFIG_BT_RFCOMM`：
  ```text
  # CONFIG_BT_RFCOMM is not set
  ```
- **根因与解决方案**：
  - **若产品需要蓝牙通话免提功能**：需在内核 defconfig 中开启 `CONFIG_BT_RFCOMM=y`（及 `CONFIG_BT_RFCOMM_TTY=y`）。
  - **若儿童音箱仅作为蓝牙音乐音箱（不需要接打电话）**：修改 `/usr/bin/bluez_tool.sh` 的 `A2DP_SINK_SERVICE()`，将 `bluealsa --a2dp-volume -p a2dp-sink -p hfp-hf` 中的 **`-p hfp-hf` 去掉**，并注释掉 `hfp_ctl &`。这样还能彻底避免手机在来电时把通话声音切到音箱上。

#### 3. 蓝牙 MAC 地址每次重启随机变化（问题 #6）
- **现象**：重启前 `hci0` MAC 为 `22:22:55:98:2F:9F`，重启后变为 `22:22:A1:05:0E:65`。
- **根因与解决方案**：UnifyKey 中 `mac_bt` 未烧录，`aml_hciattach` 每次生成 `22:22:...` 随机地址。量产与样机调试需在 UnifyKey 中写入固定 `mac_bt`。

### 3.4 底层硬件驱动与系统服务板块

#### 1. I2C-2 总线外设 Probe 失败与 `i2c_key` 日志风暴（问题 #3）
- **现象与证据**：
  1. **内核 `dmesg` 报错**：I2C-2 总线（`fe06a000.i2c`）挂载了 3 个外设，其中 2 个通信失败：
     - `2-005b` (`aw9523_led` / `amlogic,aw9523b_led`)：连续 5 次 I2C 读取失败（`aw9523_i2c_read: cnt=0..4 error=-6` 即 `ENXIO` 无应答），`probe of 2-005b failed with error -5`。
     - `2-001f` (`aml_ledring` / `aml,pca9557`)：`led init reg3 fail!`，`probe of 2-001f failed with error -12`。
     - `2-0034` (`aw21036_led` / `seirobotics,aw21036_led`)：硬件复位失败切换至软复位（`aw21036_hw_reset: failed, switch to SW_RSTN!`），工作正常。
  2. **应用层 `i2c_key` 报错刷屏**：
     `/usr/bin/i2c_key` 每 200ms 重试读取 I2C 按键状态失败，每秒向 `journald` 输出约 25 条错误日志：
     ```text
     i2c_key[3033]: [USER I2C] read operation failed, error = Unknown error -1 (-1)
     i2c_key[3033]: [USER I2C KEY] cannot read key status, I2C error, retry after 200ms
     systemd-journald[1498]: Forwarding to syslog missed 565 messages.
     ```
     注：当前板上的音量键（`key 115`）、静音键（`key 113`）实际走的是内核 `input0`（ADC Key / GPIO Key，由 `input_eventd` 处理），而非 `i2c_key`。
- **根因分析**：
  当前板卡硬件 BOM 已采用 `AW21036 (0x34)` 灯效芯片 + ADC/GPIO 按键方案，未贴装旧版方案的 `AW9523 (0x5b)` 和 `PCA9557 (0x1f)`，但设备树（DTS）和 rootfs 仍保留了旧外设节点与 `/usr/bin/i2c_key` 服务。
- **解决方案**：
  1. **硬件/设备树确认**：与硬件工程师核对原理图，若当前板型确实未贴装 `AW9523 (0x5b)` 与 `PCA9557 (0x1f)`，在对应板级 DTS 中将其 `status` 设为 `"disabled"`。
  2. **停用冗余 `i2c_key` 进程并增加错误退避**：在无需 I2C 按键的板型上禁用 `i2c_key` 启动；并在 `i2c_key` 源码中增加连续失败指数退避（或连续失败 N 次后退出），严禁无上限高频刷屏。

#### 2. `alarmService` 日志刷屏与 Systemd 失败服务清理（问题 #8）
- **`alarmService` 刷屏**：在设备未联网完成 NTP 校时前，`alarmService` 每秒打印数十条 `[WARNING] [Alarm.cpp:1054 checkAlarms] NTP time has not been synchronized yet!`。建议在 `Alarm.cpp` 和 `AutomationTimerScheduler.cpp` 中将该日志改为状态跳变时打印一次或每 60 秒限频打印一次。
- **`swupdate.service` 失败状态**：当前通过 `ExecStartPre=/bin/sh -c 'grep -qE "recovery_part=recovery(_a|_b)?" /proc/cmdline || exit 1'` 拦截正常启动，导致 `systemctl --failed` 常に显示 `swupdate.service failed`。建议改为在 `[Unit]` 段使用 `ConditionKernelCommandLine=recovery_part`，非 recovery 模式下会优雅跳过（skipped）而不计入 failed。

## 四、 常用调试与验证命令速查（SOP）

接手工程师可通过以下 `adb` 命令快速检查各项状态：

```sh
# 1. 查看蓝牙名称、MAC 与 Class of Device (CoD)
adb shell "hciconfig -a && bluetoothctl show"

# 2. 检查 speaker 进程及其内部 61 个子线程状态
adb shell "ps -ef | grep -E 'speaker|ai_manager|guard' && head -n 100 /proc/\$(pidof speaker)/task/*/comm"

# 3. 检查 ALSA 录音 (pcm4c) 与播放 (pcm1p) 硬件流运行状态
adb shell "grep -H '' /proc/asound/card0/pcm*/sub0/status"

# 4. 实时查看语音助手唤醒与 LiveKit 云端交互日志
adb shell "tail -f \$(ls -t /log/speaker_*.log | head -n 1)"

# 5. 查看大象声科 (Elevoc) 4 麦唤醒日志
adb shell "tail -f /elevoc_log.txt"

# 6. 检查 Wi-Fi 连接状态与路由
adb shell "wpa_cli -i wlan0 status && ip addr show wlan0 && ip route"

# 7. 查看系统日志（过滤掉 i2c_key 刷屏干扰）
adb shell "journalctl -f | grep -v 'i2c_key'"
```
