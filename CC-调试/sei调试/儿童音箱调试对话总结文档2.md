## 二、 关键调试专题详解与日志铁证

### 专题 1：按下音量键导致 Wi-Fi 断网 Bug 复现与根因（问题 #1）

#### 1.1 复现过程与现象
在开发板 `wlan0` 正常连接 Wi-Fi（如 `dvbspeaker` 或测试路由器）状态下，按下机身物理音量加（`key 115`）或音量减（`key 114`）按键，或通过 `input_eventd` 触发按键事件：
- 按键提示音 `/media/tip/key.wav` 播放、ALSA `AVS_Auto_Volume` 音量调整完成；
- 约 1 秒后，`input_eventd` 进程崩溃退出；
- **同一毫秒内**，`wpa_supplicant` 与 `udhcpc` 进程消失，内核 `wlan0` 发送 `deauthenticate (reason 3)`，`wlan0` IP 地址丢失且永远不再重连。

#### 1.2 核心日志证据
```text
Nov 09 00:54:14 input_eventd[2838]: [INFO] [events_process.cpp:794 ProcessKey] 音量键按下：114
Nov 09 00:54:14 input_eventd[2838]: MQTT loop error: The client is not currently connected.
Nov 09 00:54:15 input_eventd[2838]: terminate called after throwing an instance of 'std::runtime_error'
Nov 09 00:54:15 input_eventd[2838]:   what():  Publish failed after retries
Nov 09 00:54:15 systemd[1]: input-eventd.service: Main process exited, code=killed, status=6/ABRT
Nov 09 00:54:15 systemd[1]: input-eventd.service: Failed with result 'signal'.
```
当 `wpa_supplicant` 是由 `input_eventd` 调用 `/etc/bluetooth/wifi_tool.sh` 拉起时，其进程树归属于 `/system.slice/input-eventd.service`：
```text
Nov 08 18:24:35 kernel: vm_cfg80211_disconnect 3133 <wlan0> reason_code=3
Nov 08 18:24:35 kernel: <wlan0> wifi_mac_send_deauth 2714 mac[36:c5:99:91:6a:85] send station deauthenticate (reason 3)
Nov 08 18:24:35 systemd-networkd[2805]: wlan0: Lost carrier
```

#### 1.3 修复方案
1. **Systemd 服务级隔离（立即阻断连坐杀进程）**：
   修改 `/lib/systemd/system/input-eventd.service`，在 `[Service]` 段增加 `KillMode=process`，防止 `input_eventd` 退出时 `systemd` 清空整个 CGroup。
2. **C++ 源码修复（`input_eventd`）**：
   - 在 `mqtt_client` 的 `publish()` 调用处捕获 `std::runtime_error`，避免因本地 MQTT 断连导致守护进程 `SIGABRT`；
   - 修复 MQTT 断线自动重连逻辑（`mosquitto_reconnect_async`）；
   - 将启动时的 `init_network_monitor`（调用 `adckey_function.sh net1`）改为异步非阻塞，消除重启后长达 46 秒的无响应窗口。
3. **配网脚本修复（`/etc/bluetooth/wifi_tool.sh`）**：
   不要在 `wifi_tool.sh` 中 `killall wpa_supplicant` 后自行 `start-stop-daemon` 启动，而应通过 `wpa_cli` 动态下发配置或通过 `systemctl restart wifi.service` 交由独立的服务 CGroup 管理。

### 专题 2：UnifyKey 写入 SN（`usid`）重启后丢失的内核根因与解决（问题 #2）

#### 2.1 现象还原
用户直接执行：
```sh
echo "usid" > /sys/class/unifykeys/name && echo "GZ12331010211111" > /sys/class/unifykeys/write
```
写入后当前未重启时读取可能看似成功，但执行整机 `reboot` 后，`cat /sys/class/unifykeys/read` 再次变为空，且 ADB 序列号退回默认的 `ap22216110d44721a3a`。

#### 2.2 内核 `dmesg` 铁证：256KB 连续物理内存分配失败（`order:6`）
直接执行上述写入命令时，板端 `dmesg` 抛出内核内存分配失败调用栈：
```text
[ 1521.432110] sh: page allocation failure: order:6, mode:0x40cc0(GFP_KERNEL|__GFP_COMP), nodemask=(null),cpuset=/,mems_allowed=0
[ 1521.432158] Call trace:
[ 1521.432180]  dump_backtrace+0x94/0x11c
[ 1521.432210]  show_stack+0x18/0x24
[ 1521.432230]  dump_stack_lvl+0x48/0x60
[ 1521.432255]  warn_alloc+0x118/0x1a8
[ 1521.432280]  __alloc_pages_slowpath.constprop.0+0x8c4/0x918
[ 1521.432305]  __alloc_pages+0x1f0/0x260
[ 1521.432325]  __kmalloc_large_node+0x6c/0x108
[ 1521.432345]  __kmalloc+0x10c/0x150
[ 1521.432370]  amlnf_key_write+0x68/0x234
[ 1521.432395]  aml_key_write+0x48/0x90
[ 1521.432415]  key_write_store+0x168/0x270
[ 1521.432510] amlnf_key_write:1969 malloc keybuf failed
[ 1521.432525] aml_unifykeys: write unifykey fail
```
- **根因**：Amlogic NAND UnifyKey 驱动 `amlnf_key_write()` 在写入 Flash 时，每次都会动态 `kmalloc` 一块 **Order-6（$2^6 \times 4\text{KB} = 256\text{KB}$）的连续物理内存**作为 `keybuf`。而该音箱为 256MB 小内存版本，系统启动并运行 `speaker`、`ai_manager` 等服务几分钟后，物理内存产生碎片（`/proc/buddyinfo` 中 `order 6` 空闲块为 `0`），导致 `kmalloc` 返回 `NULL`，数据根本没有写入底层 NAND Flash。

#### 2.3 标准写入 SOP（已在板端成功固化 `GZ12331010211111`）
在写入任何 `unifykeys`（包括 `usid`、`mac_bt`、`mac_wifi`、`elevockey`）前，**必须先释放页缓存并触发内核内存规整（Memory Compaction）**：
```sh
# 1. 释放缓存并触发内核物理内存碎片规整，腾出 Order-6 (256KB) 连续物理页
sync
echo 3 > /proc/sys/vm/drop_caches
echo 1 > /proc/sys/vm/compact_memory

# 2. 检查 /proc/buddyinfo 第 7 列（order 6）大于 0 后执行写入
echo 1 > /sys/class/unifykeys/attach
echo "usid" > /sys/class/unifykeys/name
echo -n "GZ12331010211111" > /sys/class/unifykeys/write

# 3. 立即读回校验并检查 dmesg 无 malloc keybuf failed
cat /sys/class/unifykeys/read
sync && reboot
```
- **驱动源码长期优化建议**：在内核 `drivers/amlogic/unifykey/` 及 `amlnf_key_write()` 中，将 256KB `keybuf` 改为驱动 `probe` 初始化时预分配的静态缓冲区，或改用 `kvmalloc()` / `vmalloc()`（若底层 DMA 支持 scatter-gather），避免运行期因内存碎片导致写号失败。

### 专题 4：“无法唤醒 + 蓝牙音乐无声 + 灯一直变换”复合 Bug 深度解析（问题 #4 ~ #7）

在 `16:49` 与 `17:04` 两次观察到的异常现象，经板端日志逐秒比对，是由以下 4 个底层机制缺陷共同造成：

#### 4.1 为什么重启前（`16:32` ~ `16:50`）完全无法唤醒？—— 大象声科算法 37 分钟未授权试用期超时
- **日志证据**（`/log/speaker_2026-11-08-23-55-39.log` & `/log/speaker1.log-2026-11-09-00-50-12`）：
  1. 启动时读取 `unifykeys` 中的 `elevockey` 失败：
     ```text
     [2026-11-08 23:55:40.293] [11830] [error] elevoc active fail !!!!
     [2026-11-08 23:55:40.517] [11830] [error] elevoc unauthorized !!!!!!!!!
     ```
  2. 运行满 **37 分钟**后（板端时间 `00:32:39 PST` / 北京时间 `16:32:39`），`libElevocMeetingVoice.so` 触发试用期保护，以 **100 次/秒** 刷屏至 5.03MB：
     ```text
     2026-11-09 00:50:08.437 [11830][11874][DEBUG] [elevoc_framework.cpp:932] elevoc algo use timeout!!!
     ```
  3. 超时后前端算法停止向唤醒模块输送音频，导致重启前 100% 无法唤醒。

#### 4.2 为什么重启后（`16:54` ~ `17:00`）蓝牙音乐没声音？—— `VoiceAssistanStateStack` 状态栈翻转 Bug + 音频焦点互锁
- **完整事故时间线**（`/log/speaker_2026-11-09-00-52-31.log`）：
  1. **`00:54:23.800`（唤醒暂停蓝牙）**：语音唤醒触发，`speaker` 记录 `Bluetooth status before wakeup: playing, need resume after dialog: true`，并暂停蓝牙播放（`00:54:24.273 Bluetooth play status: paused`），状态栈变为 `[IDLE, BLUETOOTH_PLAYING, WAKEUP]`。
  2. **`00:54:43.855` & `01:00:13.002`（状态栈去重逻辑 Bug）**：当收到蓝牙 `onPlayStatusChanged playing` 回调时，因为栈中已存在 `BLUETOOTH_PLAYING`（打印 `state BLUETOOTH_PLAYING exist`），**`VoiceAssistanStateStack` 非但没有保持蓝牙播放状态，反而将 `BLUETOOTH_PLAYING` 从栈中移除**，甚至在 `01:00:13` 直接把状态栈清空回 `IDLE (state0)`：
     ```text
     [2026-11-09 01:00:13.002] [3610] [info] onPlayStatusChanged playing
     [2026-11-09 01:00:13.003] [3610] [info] state BLUETOOTH_PLAYING exist
     [2026-11-09 01:00:13.003] [3610] [info] Speaker::onStateChanged in
     [2026-11-09 01:00:13.003] [3610] [info] voice assistant new state0
     [2026-11-09 01:00:13.005] [3610] [info] VoiceAssistanStateStack contents:
     [2026-11-09 01:00:13.005] [3610] [info]   IDLE
     ```
  3. **`00:55:06.760` ~ `00:59:54.853`（拒绝恢复蓝牙）**：随后 4 次语音对话超时（`TIME_OUT` / `SLEEP`）时，`speaker` 均打印：
     ```text
     [2026-11-09 00:55:06.760] [3609] [info] Skip bluetooth resume because it was not playing before wakeup
     ```
  4. **音频焦点死锁（`audio_focus_manager` & `bluealsa-aplay`）**：
     `speaker`（`spk_music`）与 `ai_manager`（`bluetooth`）在 `audio_focus_manager` 焦点栈中堆积为 `[spk_music, bluetooth, spk_music]`，互相向对方下发 `"action": "pause"`：
     ```text
     [AudioFocusManager.cpp:135] currentClientId: bluetooth, clientId: spk_music
     [AudioFocusManager.cpp:200] Notify client: bluetooth, payload: { "action" : "pause" }
     [AudioFocusManager.cpp:33]  focusStack: not empty, elements: [spk_music, bluetooth, spk_music]
     ```
     导致 `/etc/bluetooth/bluealsa-aplay.log` 中蓝牙 A2DP 播放流被反复标记为 `inactive`：
     ```text
     bluealsa-aplay: aplay.c:346: Device marked as inactive: 64:9D:38:C4:39:B4
     ```
     从而出现**手机蓝牙已连接甚至显示播放，但音箱完全不出声**的现象。

#### 4.3 为什么语音助手也没出声，但灯却一直在变？—— LiveKit 本地打断（`local_barge_in`）毫秒级横跳 + 双进程写 LED 冲突
- **LiveKit 毫秒级自打断**：
  在 `00:56:18` ~ `01:00:02 PST` 期间，LiveKit 一直处于后台会话中。每当云端 Agent 切为 `speaking`（下发 `SPEAKER_MESSAGE_TTS_START` -> **切 LED 模式 14**）时，环境底噪、回声或按键音立即触发了 `local_barge_in`（本地打断）或再次唤醒，`AlsaPlayer` 随即执行 `hard flush requested (queue cleared, hw drop pending)` 清空硬件播放队列，并在 **23 毫秒** 内切回 `listening`（**切 LED 模式 15**）：
  ```text
  [00:59:41.733] [LiveKitAiClient] attr changed 'lk.agent.state'='speaking'
  [00:59:41.735] Speaker get a message from 15LiveKitAiClient, type:SPEAKER_MESSAGE_TTS_START (切灯 mode 14)
  [00:59:41.745] [LiveKitAiClient] user packet: {"type": "AGENT_INTERRUPTED", "source": "local_barge_in"}
  [00:59:41.756] [LiveKitAiClient] attr changed 'lk.agent.state'='listening' (仅 23ms 后切回 mode 15!)
  ```
- **双进程同时写 `/sys/class/leds/aw_led/mode` 互相打架**：
  内核 `dmesg`（`AW21036` 驱动日志）证明，每次语音状态变化时，有两个进程同时写 LED 节点：
  1. `speaker` 内部的 `T3686` 线程直接写 `/sys/class/leds/aw_led/mode`（如写入 `14` 或 `15` 或 `7`）；
  2. 同时 `speaker` 通过 MQTT 发布 `state/play`；
  3. `input_eventd` 收到 `state/play` 后，派生两个 `sh` 子进程（如 `T5090`、`T5091`），**先写 `echo 0 > /sys/class/leds/aw_led/mode`（强制灭灯 100ms），再写一遍目标模式**：
     ```text
     [  492.394748][T3686 (speaker)]      aw21036_mode_store ... state_mode=14 (闪烁周期50, 指令61)
     [  492.501966][T5090 (input_eventd)] aw21036_mode_store ... state_mode=0  (灭灯重置!)
     [  492.609942][T5091 (input_eventd)] aw21036_mode_store ... state_mode=14 (再次写14)
     [  493.395218][T3686 (speaker)]      aw21036_mode_store ... state_mode=15 (切15)
     [  493.504367][T5094 (input_eventd)] aw21036_mode_store ... state_mode=0  (再次灭灯重置!)
     ```
  4. 叠加按音量键时的 `state_mode=4`、2 秒倒计时恢复线程（`countdown_thread_func`）以及 `input_eventd` 崩溃重启阻塞 46 秒后一次性回放积压的 `14 -> 15 -> 14 -> 15` 消息，直接造成 LED 灯效不停变换闪烁。
